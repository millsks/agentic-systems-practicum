Capstone 1: Research Agent

Build a tool-using research agent that searches a small library, reads the sources it needs, and writes an answer where every claim cites a document it actually read. It is the whole of Level 1 in one program: tool contracts, the agent loop, errors as data, stop conditions, and tool design, graded against a scripted model so every edge case is tested offline.

⏱ ~5–7 hoursPrerequisites: M09, M10, M11, M12
  • Write three tool definitions whose descriptions tell the model when to use each tool
  • Implement keyword search and document reading as plain, separately tested Python functions
  • Drive a complete agent loop from stop_reason, including parallel tool calls
  • Turn unknown tools, invalid input, and bad ids into is_error results the model can recover from
  • End every run with a structured result: answer, citations, steps, tokens, and why it stopped
  • Verify citations against what the agent read, so an answer cannot cite a source it never opened
  • Run the same code against the real Claude API from the command line

What you'll build

A science writer is preparing an article about honeybees and wants a research assistant that answers questions from a vetted library, not from whatever the model half-remembers. The library is 14 short documents (the corpus) on colony life, the waggle dance, swarming, varroa mites, beekeeping history, and more. The writer has one hard rule: every claim must point to a document, and the assistant must have actually read that document. A citation to a source nobody opened is worse than no citation, because it looks trustworthy.

You will build research, a Python package with three tools and an agent loop. The model never sees the library directly. It can only ask your code to search it, read one document, or list_sources. Your loop runs each request, sends the results back, and repeats until the model writes an answer or a limit is hit. Then your code parses the [doc-id] citations in the answer and checks each one against the list of documents read during that run.

$ pixi run python -m research "How do honeybees tell each other where food is?"
Foragers perform a waggle dance on the vertical comb. The angle of the waggle run relative to
vertical gives the direction of the food relative to the sun, and the length of the run gives
the distance [waggle-dance]. Followers also learn the flower scent from the dancer [waggle-dance].

Sources: waggle-dance
[3 steps, 4180 input / 160 output tokens, stopped: end_turn]

The token counts above are illustrative. The graded tests use agentlab.MockClient, which estimates tokens at about four characters each; the real API reports exact counts in response.usage.

How the pieces fit

The design keeps three concerns apart so each can be tested alone. The tools know nothing about the model: they take Python arguments and return text or raise ToolError. The loop knows nothing about bees: it moves blocks between the client and the toolbox. The citation check is a pure function over three lists. This is the same split you practiced in M12: tools you can unit-test without a model, and a loop you can test with a scripted one.

flowchart LR
  Q[question] --> L
  subgraph L[run: the agent loop]
    C[client.messages.create] -->|stop_reason = tool_use| X[execute_tool_calls]
    X -->|all tool_result blocks in one user message| C
  end
  X --> T[Toolbox.dispatch]
  T --> V{agentlab.validate}
  V -->|ok| S[search / read / list_sources]
  V -->|problems| E[ToolError]
  S --> K[(corpus: 14 documents)]
  S -->|read records doc id| R[read_ids]
  E -->|is_error: true| X
  C -->|end_turn, max_tokens, refusal, or max_steps| A[Answer]
  R --> CC[check_citations]
  A --> CC

Step through a run of this exact shape (search, read, answer) in the visualizer before you write the loop. Watch the message list grow: each assistant turn is followed by a user turn carrying the tool results.

Why does read record ids instead of letting the citation check look at search results too? Because a search snippet is one sentence chosen by keyword overlap. A model that answers from snippets is answering from fragments it never saw in context. Requiring a read is how the agent earns the right to cite.

The required interfaces

The tests call these names directly. Signatures and docstrings are in the starter; this is the contract at a glance.

Tools (tools.py)

NameBehavior
tool_definitions() -> list[dict]Three definitions in the order search, read, list_sources. Each has a description of at least 40 characters and an object input_schema with additionalProperties: false. search requires query (string) and accepts limit (integer 1 to 10); read requires doc_id; list_sources takes nothing.
ToolErrorException for failures the model can fix. Its message becomes the is_error result.
Toolbox(corpus=None)Tools for one run. read_ids lists documents read successfully, in first-read order.
Toolbox.search(query, limit=5)Hits {"id", "title", "snippet", "score"}: 3 points per query word in the title, 1 per word in the body, plural s ignored, score-0 documents dropped, sorted by score then id. A query with no keywords raises ToolError.
Toolbox.read(doc_id)Returns the title, the id, and the body; records the id. Unknown ids raise a ToolError that repeats the id and says to use search or list_sources.
Toolbox.list_sources(){"id", "title"} for every document, sorted by id.
Toolbox.dispatch(name, input) -> strUnknown name: ToolError naming the real tools. Input checked with agentlab.validate against the tool's schema; problems raise ToolError. Search results are formatted one per line as [doc-id] Title (score N): snippet.

The loop (agent.py)

def run(client, question, *, corpus=None, max_steps=8, max_tokens=2048, model=MODEL) -> Answer: ...

@dataclass
class Answer:
    text: str                       # final text (partial if the run stopped early, "" on max_steps)
    citations: list[str]            # [doc-id]s in the text, first-seen order
    citation_problems: list[str]    # from check_citations; checked only when stopped_because == "end_turn"
    read_ids: list[str]             # documents read in this run
    steps: int                      # messages.create calls made
    usage: Usage                    # input_tokens / output_tokens summed over every response
    stopped_because: str            # "end_turn", "max_tokens", "refusal", "max_steps", ...
    detail: str | None = None       # e.g. the refusal's stop_details.explanation
    messages: list[dict] = ...      # full history, for al.format_transcript

    @property
    def ok(self) -> bool: ...       # end_turn and no citation problems

Every request is client.messages.create(model=model, max_tokens=max_tokens, system=SYSTEM_PROMPT, tools=tool_definitions(), messages=messages). Nothing else. That is what lets the same function run on the mock and on anthropic.Anthropic().

Milestones

Milestone 1: the tools

Write tool_definitions and the four Toolbox methods. Test them in a Pixi shell before any model is involved: if toolbox.search("waggle dance") does not put waggle-dance first, no prompt will save the agent. Revisit M07 for schemas and M12 for result formatting.

  • Descriptions say what each tool returns and when to use it (and when not to)
  • search ranks by title and body matches and returns ids the model can cite
  • read on an unknown id raises a ToolError that tells the model what to do next
  • dispatch validates input with agentlab.validate before running anything
  • pixi run practicum grade c1 -k "tools" passes

Milestone 2: citations you can trust

Write parse_citations and check_citations. They are pure functions over strings and lists, so they are quick to finish, and the loop tests in the next milestones rely on them: a run is only ok when its citations are sound.

  • Citations are unique and in first-seen order; [Note] is not a citation
  • An answer with no citations is flagged
  • A citation of a real document that was only seen in search results is flagged as never read
  • -k test_citations passes

Milestone 3: the loop

Write Usage.add, text_of, execute_tool_calls, and run. This is the ~50-line agent from M09, driven by stop_reason. Append response.content itself (the blocks, text included) as the assistant turn, and put every tool_result for that turn in one user message, in the order of the tool_use blocks. When the run ends with end_turn, fill Answer.citations and Answer.citation_problems with your milestone 2 functions; a truncated or refused run already reports why it is incomplete, so skip the check there.

  • A single search followed by an answer takes exactly two requests
  • Search, read, answer works as a three-request chain
  • Two parallel read calls come back in one user message, in order
  • Every request carries the system prompt, the tools, and the full history
  • An answer citing a document that was only searched is not ok
  • -k "single or chained or parallel or well_formed or usage or citing" passes

Milestone 4: errors and stop conditions

Make the loop survive a bad model and end every run on purpose (M10, M11). A ToolError is data: it becomes {"type": "tool_result", ..., "is_error": True} and the loop continues. A non-tool stop reason ends the run and is recorded, never ignored.

  • A bad id, an unknown tool, and invalid input each produce an is_error result with an actionable message
  • The agent recovers when the model corrects its call
  • max_steps caps the number of requests and reports stopped_because="max_steps"
  • max_tokens and refusal stop the run, keep partial text and stop_details
  • -k "error or unknown or invalid or max_steps or refusal or max_tokens" passes, and pixi run grade c1 shows all 25 tests passing

Milestone 5: a live run

The CLI is provided. Run it against Claude (see below), then read the transcript of one run line by line with agentlab.format_transcript(answer.messages) and check that you can explain every block.

  • The agent answers three different questions with sound citations
  • At least one question made the model call tools in parallel
  • You found one question the library cannot answer and the agent said so instead of guessing
  • No API key appears in your code, your shell history file, or any commit

The heart of it: one step of the loop

This is the shape the tests expect. Study why each line is there before you write yours.

response = client.messages.create(
    model=model, max_tokens=max_tokens, system=SYSTEM_PROMPT, tools=tools, messages=messages
)
usage.add(response.usage)
if response.content:                                   # a refusal has no content to append
    messages.append({"role": "assistant", "content": response.content})
if response.stop_reason != "tool_use":                 # end_turn, max_tokens, refusal, ...
    stopped = response.stop_reason
    ...                                                # record it and leave the loop
messages.append({"role": "user", "content": execute_tool_calls(toolbox, response.content)})

And the error path inside execute_tool_calls, which is what keeps one bad call from ending the run:

result = {"type": "tool_result", "tool_use_id": block.id}
try:
    result["content"] = toolbox.dispatch(block.name, dict(block.input))
except ToolError as exc:
    result["content"] = f"Error: {exc}"
    result["is_error"] = True
    log.warning("tool_error", tool=block.name, error=str(exc))

Never print inside the agent. Log with structlog (log = structlog.get_logger(__name__)). The provided CLI sends log lines to stderr as key=value pairs and keeps stdout for the answer, so pixi run python -m research "..." > answer.txt captures only the answer.

How grading works

pixi run grade c1 runs 25 pytest tests in projects/c1_research_agent/tests/ against your work copy. Nothing touches the network. Each agent test builds an agentlab.MockClient with a script, one step per messages.create call, runs your agent, and then inspects both your Answer and client.requests, the list of every request your code sent. For example:

client = al.MockClient([
    al.tool_calls([("read", {"doc_id": "swarming"}), ("read", {"doc_id": "waggle-dance"})], ids=["t_a", "t_b"]),
    "Scouts dance for nest sites [swarming] [waggle-dance].",
])
answer = run(client, "How do swarms pick a home?")
last = client.requests[1].messages[-1]
assert [b["tool_use_id"] for b in last["content"]] == ["t_a", "t_b"]   # one user message, in order
assert answer.ok

The mock validates every request the way the API does, so a malformed history fails loudly with the same BadRequestError the real API would raise: a tool_use with no matching tool_result or a history ending in an assistant turn. It is stricter in one place: results split across two user messages fail here, while the real API merges them. Send them in one message anyway; splitting discourages parallel calls.

Running against the real API

The agent calls only client.messages.create, so switching to Claude changes one line: the client. The provided CLI does it for you with agentlab.get_client(), which returns anthropic.Anthropic(). This repository's Pixi environment already includes the anthropic SDK.

export ANTHROPIC_API_KEY=...             # or sign in with `ant auth login`
cd work/c1_research_agent
pixi run python -m research "How does a swarm choose a new home?" -v

Where the package is missing (for example, a copy of the agent in another workspace) the CLI exits with code 2 and explains how to add it instead of crashing. In your own scripts the equivalent is:

import anthropic
from research import run

client = anthropic.Anthropic()           # reads ANTHROPIC_API_KEY from the environment
answer = run(client, "Why do honeybee colonies die?", max_steps=8)

A typical run makes three to five requests. Each request re-sends the system prompt, the tool definitions, and the whole history, so input tokens grow with every step; this is the cost of a stateless API (M02). At Opus 5.5 prices ($4 per million input tokens, $20 per million output) a five-step run with 20,000 input and 600 output tokens in total costs about $0.08 + $0.012 = $0.092. Try the same question with --model claude-haiku-5-5 and compare the answers and the token line.

Never paste an API key into code, a test, or a notebook, and never commit one. The SDK reads it from the environment.

Hints

BadRequestError: tool_use ids were found without tool_result blocks

You appended the assistant turn but sent a result for only some of its tool_use blocks, or sent them in separate messages. Build all results first, then append one user message with the whole list.

BadRequestError: the final message must not be an assistant message

Your loop called the model again right after appending the assistant turn, without adding the tool results. Only tool_use continues the loop, and only after the results are appended.

The text before a tool call disappears from the history

Append response.content, not a dict you built from the tool call alone. The assistant turn must hold every block the model produced, text included.

The max_steps test hangs or raises MockScriptError

The loop must count requests, not tool calls, and stop after max_steps of them, even when the model keeps asking for tools.

My citation check passes answers that only searched

Only Toolbox.read appends to read_ids, and only after the id was found. Search results must not count.

Stretch goals

  • Add "strict": True to the tool definitions. Explain what it guarantees and why dispatch still validates (hint: the mock and the API are not your only callers).
  • Add a token budget and a cost budget that stop the run with their own stopped_because, and detect a model repeating the identical call (M11).
  • Build an eval set: ten questions with the ids that should be cited. Score citation precision and recall against the real API, and track the numbers when you change the system prompt.
  • A grounding check: every sentence citing [x] shares at least two keywords with document x; flag the ones that do not.
  • Replace keyword scoring with BM25 and show on your eval set whether it helps.
