The Agent Loop

An agent is a model in a loop with tools. In M08 you did one round trip by hand. Here you put that round trip inside a loop that keeps going until the model says it is done, handle several tool calls in one turn, and finish with a complete agent of about fifty lines that you can write from a blank file. Every agent framework you will meet is built around this loop.

Why one round trip is not enough

The M08 function made at most two requests: ask, run the tool, answer. That works when one tool call is enough. Many real questions need more, and the model cannot know how many until it sees results.

Take "Is it warmer where I am or in Oslo?" The model does not know where you are. It must first call get_location. Only after reading that result ("Lisbon") can it ask for the weather in Lisbon. The second call depends on the first call's output. That dependency is what forces a loop: each result can lead to another question, and only the model knows when it has enough to answer.

This gives us the working definition of an agent used throughout the course: a model that decides, step by step, which tool to call next, running in a loop that your code controls. The model chooses what to do; your loop decides whether it keeps going, runs the tools, and records the history.

The visualizer below plays the chain scenario: one question, three requests, four tool calls. Notice two things. The model asks for two independent lookups in a single response (parallel calls, covered later in this module), and the second batch of calls exists only because of what the first batch returned.

Count the requests in the visualizer. How many times was the full message list sent? How long was the list on the last request? Every one of those blocks is paid for as input tokens on every request that includes it.

Remember: the number of steps depends on tool results, so it cannot be fixed in advance. An agent is a loop that runs until the model stops asking for tools.

stop_reason is the control flow

Each response tells you why the model stopped generating, in stop_reason (M03 covers every value). Inside an agent loop, that one field decides what happens next:

stop_reasonMeaningWhat the loop does
tool_useThe model wants one or more tools runRun them, append the results, go around again
end_turnThe model finished its answerReturn the final text
max_tokensThe response hit your max_tokens limit and was cut offStop and report it (handling it gracefully is M11)
refusalThe model declined; details are in stop_detailsStop and report it
anything elseFor example stop_sequence, or pause_turn from server toolsStop and report it; this module's tools never produce these
 
flowchart TD
    A[messages = task] --> B[call the model]
    B --> C{stop_reason}
    C -- tool_use --> D[append assistant turn
run every tool
append all results]
    D --> B
    C -- end_turn --> E[return the text]
    C -- other --> F[stop and report]

Why drive the loop by stop_reason instead of something that looks easier, such as "loop while the response has no text"? Because text and tool calls can appear in the same response. The model often writes "Let me check both cities." and then two tool_use blocks. A loop that stops at the first text would return that sentence as the answer, with the tools never run. stop_reason is the one field defined to answer the question "is the model done?"

Predict the loop's decision for each response before running the cell.

The first response contains text, yet the right action is to run tools. That is the case a text-based check gets wrong.

Remember: tool_use → run tools and continue; end_turn → return; anything else → stop and say why. Never decide "done" by looking for text.

The first loop

Take the M08 round trip and wrap it in while True. The body is the same five moves; the only new idea is that after sending results we go back to the top instead of stopping.

messages = [{"role": "user", "content": task}]
while True:
    response = client.messages.create(model=al.MODEL, max_tokens=4096, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": response.content})
    if response.stop_reason != "tool_use":
        break
    results = [run_one(block) for block in response.content if block.type == "tool_use"]
    messages.append({"role": "user", "content": results})

Three details matter:

  • Append the assistant turn every time, before deciding anything. It holds the tool_use blocks the next results must answer, and on the final step it holds the answer, which keeps the history complete if you want to ask a follow-up later.
  • messages only grows. Each iteration adds an assistant turn and (if tools ran) a user turn of results. Each request re-sends the whole list, because the API is stateless.
  • The same tools go on every request. Tools are part of the request, not remembered by the API.

Here is that loop running a chained task. The model must find your location before it can ask for the weather. The script has three steps, so the loop makes exactly three requests.

This is a working agent. It has two weaknesses we will fix while building the final version: it treats any non-tool_use stop as success (a max_tokens cut-off would be returned as if it were a full answer), and while True has no limit. If the model kept asking for tools forever, this loop would run forever, spending money on every iteration.

Remember: the agent loop is the M08 round trip repeated: call, append the assistant turn, stop unless tool_use, run the tools, append the results, repeat.

Parallel tool calls: all results in one message

When the model needs several pieces of information that do not depend on each other, it can ask for all of them in one response. This is called parallel tool use, and it is on by default. "Is it warmer in Lisbon or Oslo?" usually produces one response with two tool_use blocks, each with its own id.

The rule for answering is strict: every tool_result goes in one user message, each with the tool_use_id of its call, before any text. The loop you just wrote already does this, because it collects a results list across all blocks and appends it once.

The tempting mistake is to append one user message per result inside the loop over blocks. Run it and read the error.

The error names toolu_mock_0002: the first user message after the assistant turn answered only the Lisbon call, so the Oslo call had no result "immediately after". The fixed transcript shows the right shape: two tool_use lines in one assistant turn, then two tool_result lines in one user turn, ids matching.

Some practical points about parallel calls:

  • Order. Returning results in the same order as the calls is the clearest choice, and the natural result of looping over response.content. The ids, not the order, do the pairing.
  • Running them. The calls are independent, so you may run them concurrently (for example, several slow HTTP requests at once). Running them one after another is also correct and is what this module does. Concurrency is an optimization for later stages.
  • Never drop one. If one of the calls fails, you still return a result for it, marked as an error. That is the subject of M10; for now, every call gets a result.
  • Splitting results teaches the model a bad habit. Even where a split would be accepted, returning results across several messages makes the model less inclined to make parallel calls later. One message, every result.

Remember: one assistant turn with N tool_use blocks is answered by one user message with N tool_result blocks, each carrying its call's id.

Building run_agent step by step

Now we turn the loop into a reusable function with a clear contract. This is the Level 1 centerpiece: by the end of the module you should be able to write it without looking.

def run_agent(client, task, tools, registry, max_steps=10) -> str:
    """Run the model with tools until it answers; return the final text."""
  • client: anything with messages.create, a MockClient or a real anthropic.Anthropic(). Passing it in (rather than creating it inside) is what lets tests give it a script.
  • task: the user's request, a string.
  • tools: the tool definitions sent to the model.
  • registry: tool name → Python function, the allow-list from M08.
  • max_steps: the most model calls this run may make.

Step 1: two small helpers

Keep the loop readable by pulling out the two things it does to responses: read the text, and run the tools. run_tools is M08's dispatch and result-building, applied to every tool_use block, returning the list that becomes one user message.

def text_of(response) -> str:
    return "".join(block.text for block in response.content if block.type == "text")


def run_tools(response, registry) -> list[dict]:
    results = []
    for block in response.content:
        if block.type != "tool_use":
            continue
        output = registry[block.name](**block.input)
        content = output if isinstance(output, str) else json.dumps(output)
        results.append({"type": "tool_result", "tool_use_id": block.id, "content": content})
    return results

Step 2: start the history

    messages = [{"role": "user", "content": task}]

The list belongs to your code. It is the agent's whole memory: nothing else is carried between requests.

Step 3: a bounded loop

    for step in range(max_steps):
        response = client.messages.create(
            model=al.MODEL, max_tokens=4096, tools=tools, messages=messages,
        )
        messages.append({"role": "assistant", "content": response.content})

for step in range(max_steps) replaces while True. It reads as "at most max_steps model calls", and it cannot spin forever. One step here means one call to the model, together with the tools that response asked for.

Step 4: branch on stop_reason

        if response.stop_reason == "end_turn":
            return text_of(response)
        if response.stop_reason != "tool_use":
            raise RuntimeError(f"agent stopped early: stop_reason={response.stop_reason}")

Success is end_turn only. Everything that is neither end_turn nor tool_use raises, with the stop reason in the message, so a truncated or refused run is never mistaken for an answer. Raising is deliberately blunt; M11 replaces it with a structured run result that reports why the run stopped.

Step 5: run the tools and continue

        messages.append({"role": "user", "content": run_tools(response, registry)})

All results, one user message. Then the for loop goes around.

Step 6: what happens when steps run out

    raise RuntimeError(f"agent did not finish within {max_steps} steps")

If the loop finishes without returning, the model was still asking for tools after max_steps calls. Raising makes that impossible to miss. The next section shows why this matters.

The complete agent

Here are all the pieces together, with a verbose flag that prints the transcript at the end. Run it: the demo task needs a location lookup first, then three lookups at once (two weather calls and a time call), then the answer. That is three model calls.

Without the demo and docstrings, the agent is under forty lines. Everything an agent framework adds (retries, budgets, logging, memory, sub-agents) is built around exactly this core. The rest of Stage 2 hardens it: M10 makes tool failures and API errors survivable, M11 adds budgets and a structured result, and M12 improves the tools themselves.

Notice what run_agent does not know: which tools exist, what the task is, or how many steps it takes. All of that is data passed in. Keeping the loop generic is what lets you test it with scripted runs and reuse it for every agent you build.

Remember: history list → bounded for loop → call → append response.content → end_turn returns, other non-tool_use raises → append all results → repeat → raise when steps run out.

The max_steps guard

Why insist on a limit? Because the loop's exit is controlled by the model. If the model keeps asking for tools (a confusing tool result, a task it cannot complete, a tool that returns the same unhelpful answer), the loop keeps calling it. Each call costs money and time, and the history grows, so each call costs more than the last. A loop with no limit turns a confused model into an unbounded bill.

The mock can simulate that with a responder: a function that answers every request after the script runs out. This one always asks for the weather again.

Five requests, then a clear error. The message counts (1, 3, 5, 7, 9) show the cost growing: each step re-sends everything before it. Without the guard, the loop would never end.

How big should max_steps be? Large enough for real tasks, small enough to stop a runaway quickly. For the small agents in this stage, 10 to 20 is reasonable. A step limit is the simplest budget; M11 adds token, cost, and time budgets and detects a model calling the same tool with the same input over and over.

Never ship while True around a model call. Every agent loop needs at least a step limit, even in a prototype; prototypes are where runaway loops happen.

Remember: the model controls when the loop wants to end; your code controls when it must end. for step in range(max_steps) plus a final raise is the minimum.

Reading the transcript

When an agent gives a wrong answer, the question is always "what did it see, and what did it ask for?" The answer is in the message list. al.format_transcript(messages) prints it one block per line, as introduced in M00; you can pass a response not yet appended as a second argument. Here is the transcript from the complete agent's demo run:

user: Is it warmer here or in Oslo, and what time is it here?
assistant: tool_use get_location {} [toolu_mock_0001]
user: tool_result [toolu_mock_0001] Lisbon
assistant: Let me check all three.
assistant: tool_use get_weather {"city": "Lisbon"} [toolu_mock_0003]
assistant: tool_use get_weather {"city": "Oslo"} [toolu_mock_0004]
assistant: tool_use get_time {"city": "Lisbon"} [toolu_mock_0005]
user: tool_result [toolu_mock_0003] {"temp_c": 21, "sky": "sunny"}
user: tool_result [toolu_mock_0004] {"temp_c": 4, "sky": "cloudy"}
user: tool_result [toolu_mock_0005] 14:05
assistant: It's warmer where you are: 21°C and sunny in Lisbon against 4°C in Oslo. It's 14:05 in Lisbon.

(The ids skip toolu_mock_0002 because the mock numbers response ids and tool ids from one counter. Never rely on an id's format; just copy it.)

How to read it:

  • Each run of assistant: lines is one model call. Consecutive lines with the same role are blocks of one message. Here there are three assistant turns, so three requests.
  • Count tool calls by tool_use lines: four, in two batches. The second batch was a parallel call of three.
  • Pair ids by eye. Every bracketed id on a tool_use line appears on a tool_result line in the next user turn. If one is missing, you have found your bug.
  • Check that inputs follow from results. Lisbon in the second batch came from the first result. If the model asked for a city that appears nowhere in the transcript, it guessed, and the tool description or prompt needs work (M12).
  • Read the results as the model did. The model only knows what the tool_result lines say. A vague or truncated result explains many wrong answers.

Tests (and you, while debugging) can also read what each request carried through the mock's client.requests. Each entry has .messages, .tools, and .tool_results (the results in its last message). Predict the three printed lines before running this loop.

Three requests. The first carries no results; the second carries two (the parallel batch, in one message); the third carries one. The message counts grow 1, 3, 5: a reminder that the whole history rides along on every call.

Remember: one assistant turn per model call; count tool_use lines for tool calls; match bracketed ids; check that each tool input is justified by something earlier in the transcript.

What the SDK tool runner automates

The Anthropic Python SDK has a beta helper, the tool runner, that runs this loop for you. You decorate plain Python functions with @beta_tool; the SDK builds each tool's input schema from the function's signature and docstring, calls the model, runs the requested functions, sends the results back, and repeats until the model stops asking for tools.

import anthropic
from anthropic import beta_tool

client = anthropic.Anthropic()


@beta_tool
def get_weather(city: str) -> str:
    """Get the current weather for one city.

    Args:
        city: City name, for example "Paris".
    """
    return "18°C, light rain"


runner = client.beta.messages.tool_runner(
    model="claude-opus-5-5",
    max_tokens=4096,
    tools=[get_weather],
    messages=[{"role": "user", "content": "What's the weather in Paris?"}],
)
for message in runner:            # one message per model call
    print(message.stop_reason)

Map it onto what you built:

Your run_agentThe tool runner
Hand-written TOOLS schemasGenerated from the decorated function's signature and docstring
registry dictThe tools=[...] list of decorated functions
for step in range(max_steps) + stop_reason checkThe runner's iteration, ending when the model stops calling tools
run_tools: dispatch, stringify, pair ids, one user messageDone for you on each iteration
messages.append(...) twice per stepDone for you

So why write the loop by hand first? Because the runner hides exactly the parts that break. When an agent misbehaves you will be reading a transcript, and you can only debug what you understand: a missing pairing, a result the model could not read, a loop that should have stopped. You now know every step the runner takes for you. In production, the runner (or a framework) is often the right choice; your manual loop is the right choice when you need control the helper does not give you, and it is always the right mental model.

The tool runner is part of the regular anthropic package, reached via client.beta.messages. It is not the same thing as the Claude Agent SDK, which is a separate product with its own built-in tools. Both appear in later stages.

Remember: the tool runner automates schema generation, dispatch, result pairing, and looping. It does not change the protocol; it runs the same loop you just wrote.

The centerpiece. Write run_agent(client, task, tools, registry, max_steps=10) without looking back. It must:

  1. Start the history with task as the only user message.
  2. Make at most max_steps calls to client.messages.create, each with model=al.MODEL, an explicit max_tokens, tools=tools, and the full history.
  3. Append each response's content as an assistant turn.
  4. On end_turn, return the joined text of the response.
  5. On tool_use, run every tool_use block through registry (non-string outputs through json.dumps) and append all results in one user message.
  6. On any other stop reason, raise RuntimeError naming it.
  7. If max_steps calls happen without an end_turn, raise RuntimeError.

The tests run five scripted scenarios: a single tool, chained tools, parallel tools, no tools, and a model that never stops.

Hint

Write it in the order of the section: messages = [...]; for step in range(max_steps):; create; append response.content; if end_turn: return text; if not tool_use: raise; build results and append one user message; after the loop, raise.

Mini-project: a file-question agent

Mini-projectnotes_agent.py: answer questions about a folder of notes

Build a local agent that answers questions about a folder of text files, using your own run_agent. Questions like "Which note mentions the budget, and what does it say?" need a chain (list files, then read the right one) and often parallel reads, which is exactly what the loop is for.

pixi init
pixi add python=3.14 anthropic structlog
mkdir notes   # put three or four short .txt files here
# write agent.py and notes_agent.py, then:
pixi run python notes_agent.py "Which note mentions the budget?"

What to build

  • agent.py: your run_agent(client, task, tools, registry, max_steps=10), the same contract as exercise 4.
  • Two tools in notes_agent.py: list_notes() returning the file names in notes/, and read_note(name) returning one file's text. read_note must refuse names outside the folder (reject anything containing / or ..): the model chooses the argument, so the tool enforces the boundary.
  • A client chooser: al.get_client() for the real API, falling back to an al.MockClient script (list, then two parallel reads, then an answer) when it raises al.LiveModelUnavailableError.
  • structlog events for each model call (step number, stop_reason, input and output tokens from usage) and each tool call (name, input, id). Structured events let you reconstruct a run later without re-running it.
  • run_agent lives in its own module and knows nothing about notes
  • The loop is bounded by max_steps and raises when steps run out
  • Parallel read_note calls are answered in one user message
  • read_note("../secret.txt") is refused by the tool itself
  • The mock fallback run makes exactly the number of requests its script has steps
  • Each model call and tool call produces one structlog event
  • Works against the real API with model="claude-opus-5-5", with the key only in the environment

Stretch goals: add a --trace flag that prints al.format_transcript of the final history (return the history from a variant of run_agent); total the input and output tokens across the run and print the cost at Opus 5.5 prices ($4 and $20 per million tokens); add a search_notes(term) tool and see whether the model prefers it to reading every file.

Quiz

Recap

  • An agent is a model in a loop with tools. The loop exists because later tool calls depend on earlier results, so the number of steps is unknown in advance.
  • stop_reason drives the loop: tool_use continues, end_turn returns, anything else stops and reports. Never decide "done" by looking for text.
  • Each step: call with the full history and tools, append response.content, run every tool_use block, append all results in one user message.
  • Parallel calls: N tool_use blocks in one turn are answered by N tool_result blocks in one message, paired by id.
  • Bound the loop: for step in range(max_steps) and a final raise. The history, and so the cost per call, grows every step.
  • Debug with al.format_transcript: one assistant turn per call, ids paired by eye, inputs justified by earlier results.
  • The SDK's beta tool runner automates this loop; knowing the manual loop is what lets you debug it.
