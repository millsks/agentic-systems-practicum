Tools as Contracts

A model on its own can only write text. Tools let it ask your code to do things: look something up, compute, read a file. But the model never sees your code. All it sees is a name, a description, and a schema. That definition is a contract between you and the model, and an agent can only be as good as the contracts it is given.

What a tool is to the model

In everyday speech a "tool" is a function your program can call. To the model, a tool is something much smaller: a description of a function. You send a list of tool definitions with the request. Each one has three parts:

  • name: an identifier the model uses to ask for the tool, such as get_weather;
  • description: plain-language text saying what the tool does and when to use it;
  • input_schema: a JSON Schema (M05) describing the arguments the tool accepts.

When the model decides a tool would help, it does not run anything. It ends its turn with a tool_use block: a structured request that says "please call get_weather with {"city": "Paris"}". The response's stop_reason is "tool_use". Your code reads that block, runs the real function, and sends the result back in the next request. The model then continues with the result in view.

sequenceDiagram
    participant C as Your code
    participant M as Model (via the API)
    C->>M: messages + tools (name, description, input_schema)
    M-->>C: tool_use {name: "get_weather", input: {"city": "Paris"}}
stop_reason = "tool_use"
    Note over C: You run get_weather("Paris")
(M08 builds this step)
    C->>M: tool_result with the output
    M-->>C: final text answer, stop_reason = "end_turn"

This division of labor is the most important idea in Stage 2:

The model decides

  • whether a tool would help
  • which tool to ask for
  • what arguments to pass

Your code decides

  • which tools exist at all
  • whether to actually run a requested call
  • what the function really does, and what result to send back

Because the model only sees the definition, the definition is the whole interface. A vague description, a misleading name, or a loose schema leads to wrong calls even when the Python function behind it is perfect. That is why this module calls tools contracts: the definition promises what the tool does and what input it accepts, and the model holds you to it.

The mock's script decided that the "model" would ask for the tool; the real model makes that choice from your definitions and the conversation. Either way, the response shape is the same: a tool_use block with an id (which your result must echo back), the tool name, and the input, already parsed into a Python dict. In this module you only define tools and read what comes back. Running the function and returning the result is M08.

Remember: a tool is a name, a description, and a schema. The model asks; your code runs. The definition is the only thing the model knows about your function.

Anatomy of a valid definition

The API checks tool definitions before the model sees them, and rejects the whole request with a 400 BadRequestError if one is malformed. The rules worth knowing by heart:

FieldRuleWhy
name1 to 64 characters from letters, digits, _ and - (the pattern ^[a-zA-Z0-9_-]{1,64}$); unique within the request The model writes this name back in tool_use; it must be an unambiguous identifier.
descriptionPlain text; not checked for quality by anyone but you It is the model's main guide to when and how to use the tool.
input_schemaA JSON Schema whose top level is {"type": "object", ...} Tool input is always a JSON object of named arguments, never a bare string or list.

The error messages name the field by its position (tools.0.name) the way the real API does, so when you see one in a log you can go straight to the offending definition. These are fix, do not retry errors: the same request will fail the same way every time (M10 covers which errors to retry).

Naming tools

Valid is the minimum. A good name is a verb and a noun in snake_case that says what the tool does: search_orders, get_order, cancel_order. Avoid names that only make sense inside your codebase (handler2, run_query_v3) and names that overlap (find_customer next to lookup_customer): if you cannot tell from the names which one to use, neither can the model. M12 goes deeper into designing a tool set.

Remember: names match ^[a-zA-Z0-9_-]{1,64}$ and are unique; input_schema is an object schema. A bad definition is a 400 you fix, never one you retry.

Writing the input schema

The input_schema uses the same JSON Schema you met in M05. For tools, a small subset does almost all the work:

KeywordExampleUse it for
type"string", "integer", "number", "boolean", "array", "object"Every property
description"ISO date, such as 2026-03-01"Format, units, examples for one argument
enum["low", "normal", "high"]A closed set of choices
minimum / maximum1 / 50Numeric bounds such as page size
items{"type": "string"}The type of each array element
required["query"]Arguments the call cannot do without

Here is a complete schema for a note-search tool. Read it as a list of promises: query must be present and a string; limit is optional and between 1 and 20; sort, if given, is one of two words; tags is a list of strings.

{
  "type": "object",
  "properties": {
    "query": {"type": "string", "description": "Words to search for in note titles and bodies"},
    "limit": {"type": "integer", "minimum": 1, "maximum": 20, "description": "Maximum notes to return; default 5"},
    "sort":  {"type": "string", "enum": ["relevance", "newest"], "description": "Result order; default relevance"},
    "tags":  {"type": "array", "items": {"type": "string"}, "description": "Only return notes with all of these tags"}
  },
  "required": ["query"]
}

required is where the contract gets precise. An argument with a sensible default (here limit and sort) should be optional, and the description should say what the default is, because the model cannot see your Python default values. An argument the function cannot work without must be required, or the model will sometimes leave it out.

al.validate returns a list of problems (empty means valid). You will use exactly this check in M10 to validate the model's tool input before running a tool, and to send the problems back as an error result the model can correct.

Two schema mistakes the API will not catch for you: listing a name in required that is not in properties (no valid input can satisfy it), and an enum whose values do not match the declared type ("type": "integer" with "enum": ["1", "2"]). Both make a tool impossible to call correctly. A unit test that validates one known good input against each schema catches them.

Remember: type every property, use enum and bounds to close off bad values, describe formats and defaults, and require exactly the arguments the function cannot do without.

Descriptions that say when, and when not

Everything in M06 applies here: a tool description is a prompt. It is the model's main evidence for whether to call the tool and how. One line is almost never enough; several sentences is normal for any tool that matters. A good description answers:

  1. What does it do? In concrete terms, including what it returns.
  2. When should it be used? The kinds of user requests it serves.
  3. When should it not be used? Especially when another tool is the better choice.
  4. What are its limits? Data it cannot see, ranges it cannot handle, side effects it has.
{"name": "search_orders",
 "description": "Searches orders.",
 "input_schema": {"type": "object",
                  "properties": {"q": {"type": "string"}},
                  "required": ["q"]}}

Search by what? Customer name, order number, product? What comes back? Should the model use this to look up a single known order? What is q? The model will guess, and guesses differently each time.

{"name": "search_orders",
 "description": (
     "Search a customer's orders by product name or date range and return up to "
     "10 matches, newest first, each with order_id, date, status and total. "
     "Use it when the user describes an order but does not know its id. "
     "If the user gives an order id (like 'A-10442'), call get_order instead. "
     "Only orders from the last 24 months are searchable."
 ),
 "input_schema": {
     "type": "object",
     "properties": {
         "customer_id": {"type": "string", "description": "Customer id, such as 'C-2201'"},
         "product": {"type": "string", "description": "Words from the product name"},
         "since": {"type": "string", "description": "ISO date (YYYY-MM-DD); only orders on or after it"},
     },
     "required": ["customer_id"],
 }}

What, what it returns, when, when not (with the alternative named), and the limit. The property names and descriptions remove the rest of the guessing.

Notice that the "when not" sentence points at another tool by name. When two tools could plausibly answer the same request, the descriptions are where you draw the line between them. If you cannot write that sentence clearly, the tools probably overlap and should be merged or renamed.

Your agent has get_weather(city) and get_forecast(city, days). A user asks "Should I bring an umbrella tomorrow?" Which tool should be called, and which sentence in which description makes that obvious to the model?

Reveal

get_forecast, with days=1 or similar. The deciding sentence belongs in get_weather's description: "Current conditions only; for tomorrow or later, use get_forecast." Without it, "weather" in the name is a strong pull toward the wrong tool.

Remember: a description is a prompt. Say what the tool does and returns, when to use it, when not to (naming the alternative), and its limits.

Strict tools: schema-valid input, guaranteed

By default the schema is guidance. The model almost always follows it, but "almost always" means your code must still check every input: a missing required field or a string where you expected an integer is possible. Adding "strict": true to a tool definition changes that. With strict tool use, the API guarantees that the input in every tool_use block for that tool is valid against its schema.

Strict mode asks more of the schema in return. Every object in it must set additionalProperties: false (no undeclared keys), and must say which properties are required. That makes the schema a closed, precise description the guarantee can be built on.

SET_ALARM = {
    "name": "set_alarm",
    "description": "Set an alarm on the user's phone for a time today, in 24-hour local time.",
    "strict": True,
    "input_schema": {
        "type": "object",
        "properties": {
            "hour": {"type": "integer", "minimum": 0, "maximum": 23},
            "minute": {"type": "integer", "minimum": 0, "maximum": 59},
            "label": {"type": "string", "description": "Short label shown with the alarm"},
        },
        "required": ["hour", "minute"],
        "additionalProperties": False,
    },
}

The mock models the guarantee from the other side. It will not hand you invalid input for a strict tool: if a script tries to, it raises MockScriptError, which always means "the script is wrong", never "your code is wrong". With a non-strict tool the same bad input comes straight through, and it is your job to catch it.

When should you use strict? Whenever a malformed call would be expensive or confusing: tools with side effects, tools whose input goes straight into another system, and agents where you want one less failure mode to handle. A guaranteed shape does not make the values sensible, though. Strict guarantees hour is an integer from 0 to 23; it does not guarantee it is the hour the user meant. Your tool still checks business rules.

Remember: "strict": true guarantees schema-valid input and requires additionalProperties: false and a required list on every object. It guarantees shape, not meaning.

Generating a definition from a Python function

Writing schemas by hand works for three tools. With twenty, the definitions drift away from the functions: someone adds a parameter and forgets the schema, or renames one in only one place. The fix is to make the function the single source of truth and generate the definition from it. A well-written Python function already contains everything a tool definition needs:

Tool definitionComes from
namefunc.__name__
descriptionthe docstring, without its Args: / Returns: sections
property namesthe parameter names, from inspect.signature(func)
property typesthe type hints, from typing.get_type_hints(func)
requiredparameters with no default value
enumLiteral["a", "b"] type hints

Step 1: read the signature

inspect.signature returns the parameters in order. Each Parameter has a default, which is the special marker inspect.Parameter.empty when there is none. That is how you tell required from optional. typing.get_type_hints returns the annotations as real type objects (it resolves string annotations too, which is why it is safer than reading __annotations__ directly).

Note tags: its hint is the union list[str] | None, the usual way to write an optional list without a mutable default. The generator below supports only the simple cases and will reject it with a TypeError; handling X | None is a stretch goal in the mini-project.

Step 2: map Python types to JSON Schema

The core is a small, recursive function. Simple types map one to one. Generic types such as list[str] and Literal["a", "b"] are taken apart with typing.get_origin (the outer type: list or Literal) and typing.get_args (what is inside: (str,) or ("a", "b")). Anything unsupported raises TypeError: a generator that silently guesses would produce exactly the drifting, misleading contracts it was meant to prevent.

Why check bool by identity rather than with issubclass? In Python, bool is a subclass of int, so issubclass(bool, int) is True. A generator that tested "is it an int?" first would describe a bool flag as an integer. Looking the exact type up in a dict avoids the trap.

Step 3: assemble the definition

The docstring gives the description. Google-style docstrings put a summary first and then sections such as Args:; the summary (everything before the first section header) is what the model needs. The Args: section can supply per-property descriptions too, which is the last exercise in this module.

Run it and compare the output with the function. room, hours, and attendees have no defaults, so they are required; projector and priority are optional; priority became an enum. The description kept the "use this only after" sentence and dropped the Args: section. Change the function and the definition follows.

The SDK's beta tool runner includes a @beta_tool decorator that builds the definition from a decorated function in the same spirit, and Pydantic models can produce JSON Schema for complex inputs. Writing a small generator yourself first means you know exactly what such helpers produce, and you can read the schema they send when a call goes wrong.

Remember: make the function the source of truth. Name from __name__, description from the docstring summary, properties from the signature and type hints, required from parameters without defaults, and fail loudly on anything you cannot map.

tool_choice: letting the model decide

The tool_choice parameter controls whether the model may call tools on a request:

  • {"type": "auto"} (the default when you send tools): the model decides whether to call a tool or answer in text.
  • {"type": "none"}: the tools are in the request, but the model must answer in text. Useful for a final "summarize what you found" turn where you keep the same tool list (so the request stays consistent) but do not want more calls.
  • {"type": "any"} (must call some tool) and {"type": "tool", "name": ...} (must call this tool) force a call. Forcing is rejected on Claude Opus 5.5 with a 400 error.

So how do you make the model use a tool when it should? The same way you steer everything else on current models: with words. A description that says clearly when the tool applies, and a system prompt rule such as "Always look up the order with get_order before answering questions about an order; never answer from memory", are what make tool use reliable. If you need a JSON object rather than an action, you do not need a tool at all: use structured output.

Remember: auto is the default and none disables calls for one request. Forcing a call is rejected on Opus 5.5; steer with descriptions and the system prompt.

Reading what comes back

When the model asks for a tool, the response looks like this. It may start with a text block (the model saying what it is about to do), followed by one or more tool_use blocks:

{
  "stop_reason": "tool_use",
  "content": [
    {"type": "text", "text": "I'll look up that order."},
    {"type": "tool_use", "id": "toolu_01A9...", "name": "get_order", "input": {"order_id": "A-10442"}}
  ]
}

Three habits to build now, before you start running tools in M08:

  1. Check stop_reason first. "tool_use" means the turn ended because the model wants a call; "end_turn" means it answered.
  2. Find blocks by type, not by position. The tool call is not always content[0]; text may come first, and there may be several calls.
  3. Treat input as untrusted until checked, unless the tool is strict. It is a dict the model wrote, and the same caution from M06 applies.

The transcript shows the conversation so far: the user's question, then the assistant's text and its tool_use, then the stop reason. This is where this module stops. The conversation is now waiting for a tool_result; sending the next request without one is an error, and M08 shows exactly which one and how to build the result correctly.

Remember: check stop_reason, select blocks by type, keep the id, and validate input unless the tool is strict.

The same definitions with the real SDK

Tool definitions are plain dicts, so they are identical for the mock and the real API. Locally, the only change is the client:

import anthropic

client = anthropic.Anthropic()           # reads ANTHROPIC_API_KEY from the environment

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    tools=[tool_from_function(book_room), GET_ORDER],
    messages=[{"role": "user", "content": "Book Aurora for two hours for me and Sam."}],
)
for block in response.content:
    if block.type == "tool_use":
        print(block.name, block.input)

Tool definitions count as input tokens on every request, because they are part of what the model reads (you can see the difference with count_tokens, as in M01). Long, precise descriptions are worth their tokens; twenty barely-used tools are not. That trade-off is a theme of M12.

Remember: the same dicts work with the mock and the real client, and every definition you send costs input tokens on every request.

Write json_type(annotation) that returns the JSON Schema for one Python type hint:

  • str, int, float, bool map to {"type": "string" | "integer" | "number" | "boolean"};
  • list[X] maps to {"type": "array", "items": json_type(X)};
  • Literal[...] maps to {"type": ..., "enum": [values in order]}, with the type taken from the values; if the values do not all share one of the four simple types, raise TypeError;
  • anything else (dict, list with no item type, None, a class) raises TypeError.
Hint

Look the annotation up in a dict of the four simple types first. Then use typing.get_origin (which is list for list[str] and Literal for Literal["a"]) and typing.get_args. For a Literal, collect {type(v) for v in values} and check it has exactly one member that is in your dict. Bare list has no origin, so it falls through to the final raise.

Show solution 
import typing
from typing import Literal

SIMPLE = {str: "string", int: "integer", float: "number", bool: "boolean"}

def json_type(annotation):
    if annotation in SIMPLE:
        return {"type": SIMPLE[annotation]}
    origin = typing.get_origin(annotation)
    if origin is list:
        (item,) = typing.get_args(annotation)
        return {"type": "array", "items": json_type(item)}
    if origin is Literal:
        values = list(typing.get_args(annotation))
        kinds = {type(v) for v in values}
        if len(kinds) != 1 or next(iter(kinds)) not in SIMPLE:
            raise TypeError(f"Literal values must share one simple type: {values!r}")
        return {"type": SIMPLE[type(values[0])], "enum": values}
    raise TypeError(f"unsupported annotation: {annotation!r}")

The centerpiece. Write tool_from_function(func) that returns a complete tool definition:

  • name: the function's name;
  • description: the docstring (via inspect.getdoc) up to, not including, the first line that is exactly Args:, Returns:, or Raises: (after stripping), with surrounding whitespace stripped;
  • input_schema: {"type": "object", "properties": {...}, "required": [...]}, one property per parameter in signature order (using json_type from the previous exercise, included in the starter), and required listing the parameters with no default, in signature order.

Raise ValueError if the function has no docstring, and TypeError if any parameter has no type hint. Ignore the return annotation.

Hint

Get doc = inspect.getdoc(func) and hints = typing.get_type_hints(func). Loop over inspect.signature(func).parameters.items(); a parameter is required when param.default is inspect.Parameter.empty. For the description, collect lines until one whose .strip() is in {"Args:", "Returns:", "Raises:"}, then join and strip.

Show solution 
import inspect
import typing
from typing import Literal

SIMPLE = {str: "string", int: "integer", float: "number", bool: "boolean"}
SECTIONS = {"Args:", "Returns:", "Raises:"}

def json_type(annotation):
    if annotation in SIMPLE:
        return {"type": SIMPLE[annotation]}
    origin = typing.get_origin(annotation)
    if origin is list:
        (item,) = typing.get_args(annotation)
        return {"type": "array", "items": json_type(item)}
    if origin is Literal:
        values = list(typing.get_args(annotation))
        return {"type": SIMPLE[type(values[0])], "enum": values}
    raise TypeError(f"unsupported annotation: {annotation!r}")

def tool_from_function(func):
    doc = inspect.getdoc(func)
    if not doc:
        raise ValueError(f"{func.__name__} has no docstring")
    kept = []
    for line in doc.splitlines():
        if line.strip() in SECTIONS:
            break
        kept.append(line)
    hints = typing.get_type_hints(func)
    properties, required = {}, []
    for name, param in inspect.signature(func).parameters.items():
        if name not in hints:
            raise TypeError(f"parameter {name!r} has no type hint")
        properties[name] = json_type(hints[name])
        if param.default is inspect.Parameter.empty:
            required.append(name)
    return {
        "name": func.__name__,
        "description": "\n".join(kept).strip(),
        "input_schema": {"type": "object", "properties": properties, "required": required},
    }

Write make_strict(tool) that returns a new definition ready for strict mode, without changing the one passed in:

  • the result has "strict": True;
  • every object schema in it (the top-level input_schema, any property whose type is "object", and any array items that are objects, at any depth) gets "additionalProperties": False;
  • every object schema has a required list: keep an existing one, or add an empty list.
Hint

Deep-copy the tool, then write a recursive helper fix(schema): if schema.get("type") == "object", set additionalProperties, setdefault("required", []), and call fix on each value in properties; if it has a dict items, call fix on that.

Show solution 
import copy

def make_strict(tool):
    result = copy.deepcopy(tool)

    def fix(schema):
        if schema.get("type") == "object":
            schema["additionalProperties"] = False
            schema.setdefault("required", [])
            for child in schema.get("properties", {}).values():
                fix(child)
        if isinstance(schema.get("items"), dict):
            fix(schema["items"])

    fix(result["input_schema"])
    result["strict"] = True
    return result

Per-property descriptions help the model fill arguments correctly, and a Google-style docstring already has them. Write parse_args_section(doc) that returns a dict from parameter name to description:

  • entries start after a line that is exactly Args: (after stripping) and end at the next line that is exactly Returns: or Raises:, or at the end;
  • an entry line looks like name: description, indented under Args:;
  • a line indented more than the entry lines continues the previous description; join it with a single space;
  • blank lines are ignored; a docstring without Args: returns {}.

The tests pass docstrings already cleaned by inspect.getdoc (common indentation removed).

Hint

Walk the lines with a flag that turns on at Args: and off at Returns:/Raises:. Measure indentation with len(line) - len(line.lstrip()). Remember the indentation of the first entry line; a line indented further continues the last entry, otherwise split it once on ": ".

Show solution 
def parse_args_section(doc):
    result = {}
    in_args = False
    entry_indent = None
    last = None
    for line in doc.splitlines():
        stripped = line.strip()
        if stripped == "Args:":
            in_args = True
            continue
        if stripped in {"Returns:", "Raises:"}:
            in_args = False
            continue
        if not in_args or not stripped:
            continue
        indent = len(line) - len(line.lstrip())
        if entry_indent is None:
            entry_indent = indent
        if indent > entry_indent and last is not None:
            result[last] += " " + stripped
        else:
            name, _, description = stripped.partition(":")
            last = name.strip()
            result[last] = description.strip()
    return result

What to build

  • toolspec/schema.py: json_type and tool_from_function(func, *, strict=False), including property descriptions from the Args: section and a make_strict step when strict=True.
  • toolspec/registry.py: a Registry class with a register decorator that stores the function and its generated definition, a definitions() method returning the list to pass as tools=, and a check that rejects duplicate or invalid names at registration time.
  • toolspec/tools.py: three example tools (for instance get_weather, search_notes, convert_currency) with Google-style docstrings that say when and when not to use each.
  • toolspec/demo.py: sends one request with the registry's definitions using al.get_client() when available, falling back to an al.MockClient script; logs the returned tool_use block (name, id, input) with structlog. Do not execute the call yet.

Why structlog: a log event per tool request (event="tool_requested" tool=... input=...) is what you will search when an agent misbehaves, and it is machine-readable from day one.

  • Every tool definition is generated from a function; none is written by hand
  • Registering two functions with the same name raises an error before any request is sent
  • Unsupported type hints and missing docstrings raise clear errors at registration time
  • A test validates one known-good input against every generated schema with al.validate
  • With strict=True, every object schema has additionalProperties: false and a required list
  • The demo request is accepted by the mock and logs the tool_use block with structlog
  • No API key appears in code or in the repository

Quiz

Recap

  • To the model, a tool is a name, a description, and an input schema. It asks with a tool_use block; your code runs the function.
  • Names match ^[a-zA-Z0-9_-]{1,64}$ and are unique; input_schema is an object schema. Violations are 400s you fix.
  • Schemas type every property, close off bad values with enum and bounds, and require exactly what the function needs.
  • Descriptions are prompts: what it does and returns, when to use it, when not to, and its limits.
  • "strict": true plus additionalProperties: false and required guarantees schema-valid input; it does not guarantee sensible values.
  • Generate definitions from functions: inspect.signature, typing.get_type_hints, get_origin/get_args, and the docstring.
  • tool_choice is auto by default; none disables calls; forcing is rejected on Opus 5.5.
  • Check stop_reason, select blocks by type, keep the id, and validate non-strict input.
