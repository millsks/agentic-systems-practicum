An agent is a language model running in a loop, with tools it can ask your program to use. This module shows you that loop, the path the course takes through it, and the two clients you will use: an offline mock that runs in this page, and the real Claude API on your own machine.

What an agent is

A large language model (LLM) is a program that reads text and writes more text. On its own it can only answer: you send a request, it sends back a response, and that is the end of it. Nothing happens in the world.

An agent adds two things around the model:

  • Tools. A tool is a function in your program (search the web, read a file, query a database) that you describe to the model by name, purpose, and input format. The model never runs code. It can only ask for a tool call by writing a structured request.
  • A loop. Your program sends the conversation to the model. If the model asks for a tool, your program runs it, appends the result to the conversation, and asks again. When the model answers without asking for anything, the loop ends.
flowchart LR
  U([Task from a user]) --> P[Your program]
  P -- "conversation so far" --> M[Model]
  M -- "answer: done" --> P
  M -- "please call search(...)" --> P
  P -- "runs the function" --> T[(Tool)]
  T -- "result" --> P
  P --> O([Final answer])

That is the whole idea. Frameworks add conveniences, but under every one of them is a loop like this, usually fifty lines or fewer. By M09 you will write it yourself from a blank file.

Think: in the diagram, which box decides which tool to call, and which box actually executes it? Hold on to the answer; it explains most agent bugs you will ever debug. (The model decides; your program executes. If a tool does something wrong, the bug is in your code or your tool description, not "in the AI".)

Remember: agent = model + tools + loop. The model proposes, your program disposes.

Stage 1 · Talking to a model

One request, one response. Tokens and cost (M01), the Messages API (M02), limits and stop reasons (M03), streaming (M04), structured output (M05), and prompts that hold up (M06).

Stage 2 · Tool use and the agent loop

Tools as contracts (M07), one tool call by hand (M08), the loop itself (M09), errors (M10), budgets (M11), and tool design (M12). Then you build a research agent in Capstone 1.

The order matters. Stage 1 teaches the single request so thoroughly that, in Stage 2, the agent loop is just "do that again, carefully". Skipping ahead works poorly: almost every agent bug is a single-request bug repeated in a loop.

Remember: Level 1 takes you from your first call to a working, budgeted, tool-using agent you can explain line by line. Budget about 25-30 hours including the capstone.

Your first call, with the mock

The browser cannot reach the Claude API, and you should not need an API key or a budget to learn. So every cell and exercise in this course uses agentlab, the course's teaching library. Its MockClient has the same shape as the real SDK client: you call client.messages.create(...) with the same arguments and get back an object with the same attributes. The difference is where the answer comes from. You give the mock a script: a list of responses it returns in order, one per request.

Three arguments are required on every request, here and against the real API:

  • model: which model answers. al.MODEL is the string "claude-opus-5-5", so the code ports unchanged.
  • max_tokens: the most output the model may produce. A token is a chunk of text, roughly four characters of English; M01 covers tokens properly.
  • messages: the conversation, a list of dicts with a role ("user" or "assistant") and content. M02 takes this apart.

The response's content is a list of blocks, not a string, because a response can contain text, tool calls, and more. stop_reason says why the model stopped ("end_turn" means it finished its answer). usage counts tokens, which is how you are billed.

The mock checks your requests

The mock is not a rubber stamp. It validates each request the way the API does and raises the same exception classes the real SDK raises. That makes it a safe place to make mistakes. Run this and read each error:

The first three are real API errors: BadRequestError (HTTP 400, the request itself is wrong) and NotFoundError (404, no such model). The last one is different. MockScriptError means the script ran out: the code made a second request but the script held only one response. It is never something the real API raises. When you see it in your own work, count your create calls against your script steps.

Common mistake: reading response.text in code meant for the real API. The mock offers .text as a shortcut that joins all text blocks; the real SDK's response has no such attribute. Use response.content[0].text (or loop over the blocks) so your code ports.

Remember: one script step per create call. API errors (BadRequestError, NotFoundError) mean fix your request; MockScriptError means fix your script. The full API is in the agentlab reference.

The real client

On your own machine, with the anthropic package installed and an API key in your environment, the same request looks like this:

import anthropic

client = anthropic.Anthropic()   # reads ANTHROPIC_API_KEY from the environment

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=256,
    messages=[{"role": "user", "content": "Say hello."}],
)
print(response.content[0].text)

The only change from the mock is the line that creates client. Everything after it (the arguments, response.content, stop_reason, usage, the exception names) is the same. That is the point of the mock: you learn the real interface, offline and for free, and every answer is predictable so the exercises can grade you.

agentlab also has a helper, al.get_client(), that returns a real anthropic.Anthropic() when the package is installed and raises al.LiveModelUnavailableError when it is not. In this browser it is never installed:

MockClient

  • Runs anywhere, including this page
  • Returns exactly what you scripted
  • Validates requests like the API
  • Free, instant, deterministic
  • Used by every cell, exercise, and capstone test

anthropic.Anthropic()

  • Runs locally, needs an API key and network
  • Returns what the model actually writes
  • Costs money per token
  • Output varies run to run
  • Used in mini-projects, optionally

Remember: write code against the interface, not the client. If a function takes client as a parameter, you can pass a MockClient in tests and a real client in production. Every exercise in this course is shaped that way.

Local setup with Pixi

Pixi is the one tool this course uses to install Python, install packages, and run code. A Pixi workspace is a folder with a pixi.toml file that lists its dependencies and tasks; Pixi builds a private environment for it in .pixi/ and records exact versions in pixi.lock. Two people with the same lock file get the same environment.

To run the course itself locally:

git clone https://github.com/millsks/agentic-systems-practicum.git
cd agentic-systems-practicum
pixi install          # builds the environment: Python 3.14, agentlab, test tools
pixi run serve        # opens the course at http://127.0.0.1:8000/
pixi run projects     # lists the capstones

For your own experiments, start a separate workspace and add the real SDK. The anthropic package is on conda-forge, which is where Pixi looks first:

pixi init first-call
cd first-call
pixi add python=3.14 anthropic
pixi run python first_call.py

Always run code with pixi run python file.py, not bare python. pixi run executes inside the workspace's environment, so the packages you added are the ones you get. Use pixi add to install, never pip install, so the dependency is recorded in pixi.toml and the lock file. pixi shell opens a shell with the environment active if you want to stay in it.

Remember: pixi init creates a workspace, pixi add installs into it, pixi run runs inside it.

API key hygiene

An API key is a secret string that identifies you to the API and is billed to your account. Anyone who has it can spend your money. Treat it like a password, with one extra danger: keys leak through code, and code gets shared, pasted, and committed.

The SDK finds credentials in the environment: the ANTHROPIC_API_KEY environment variable, or a profile created with ant auth login. So the key never needs to appear in your code at all.

# set it for the current shell session only
export ANTHROPIC_API_KEY="paste-your-key-here"
pixi run python first_call.py

Do

  • Keep the key in an environment variable or an ant auth login profile
  • If you use a .env file, add .env to .gitignore before you create it
  • Use a separate key per project so you can revoke one without breaking the rest
  • Revoke and replace a key the moment you suspect it leaked

Never

  • Write a key in a .py file, even "just for a test"
  • Paste a key into a notebook, a lesson cell, a chat, or a screenshot
  • Commit a key; deleting it in a later commit leaves it in history
  • Print or log the key, or a request object that contains it

If a key reaches a commit, assume it is compromised. Revoke it first, then clean up. Removing it from the repository does not remove it from clones, forks, or caches.

Remember: the key lives in the environment, never in code. The line anthropic.Anthropic() with no arguments is the correct, safe form.

Reading a transcript

Professionals debug agents by reading what was said, in order. A transcript is the conversation printed one block per line. al.format_transcript(messages, response) renders one for you: messages is the history you sent, and the optional response is a reply you have not appended yet.

Below is a complete two-request tool run. You are not expected to write this yet (that is M08); just run it and read the output.

Read the second transcript line by line:

  1. user: What's the weather in Paris? The task.
  2. assistant: tool_use get_weather {"city": "Paris"} [toolu_mock_0001] The model asks for a tool, with its input and an id. It did not run anything.
  3. user: tool_result [toolu_mock_0001] 18°C, sunny Your program ran the tool and sent the result back as a user turn, tagged with the same id.
  4. assistant: It's 18°C and sunny in Paris. The model answers using the result.
  5. (stop_reason=end_turn) It is done, so the loop would stop.

Think: the first printout ends with (stop_reason=tool_use). What would happen if the program ignored that and treated the response as the final answer? (It would show the user nothing: the response has no text, only a request to call a tool.)

Remember: when an agent misbehaves, print the transcript first. Ask of every line: who said it, what did they ask for, and did the next line answer it?

Practice

Three short exercises to get comfortable with the mock. They are graded by tests in the page.

Write ask(client, question) that sends question as a single user message with model=al.MODEL and a max_tokens of your choice, and returns the text of the first content block. Use response.content[0].text, not the mock-only .text.

Hint

Call client.messages.create(model=..., max_tokens=..., messages=[{"role": "user", "content": question}]) and return response.content[0].text.

Show solution 
import agentlab as al

def ask(client, question):
    response = client.messages.create(
        model=al.MODEL,
        max_tokens=256,
        messages=[{"role": "user", "content": question}],
    )
    return response.content[0].text

This request has four problems, and the mock reports them one at a time. Run it, read the error, fix that one thing, and run again until it prints Bonjour. Keep the variable name client.

Hint

The four problems: max_tokens is missing, temperature is rejected, the model id is not a Claude model, and the first message must come from the user.

Show solution 
import agentlab as al

client = al.MockClient(["Bonjour"])
response = client.messages.create(
    model=al.MODEL,
    max_tokens=100,
    messages=[{"role": "user", "content": "Translate 'hello' to French."}],
)
print(response.content[0].text)

The program below is finished; only the script is missing. Replace ... with a two-step script so that the program runs without error and its last line of output is 2 + 3 = 5. Step one must be a call to the add tool with a=2 and b=3; step two is the final answer. Do not change anything below the script.

Hint

Use al.tool_call("add", {"a": 2, "b": 3}) for step one and a plain string for step two.

Show solution 
import agentlab as al

client = al.MockClient([
    al.tool_call("add", {"a": 2, "b": 3}),
    "2 + 3 = 5",
])

TOOLS = [{
    "name": "add",
    "description": "Add two integers.",
    "input_schema": {
        "type": "object",
        "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}},
        "required": ["a", "b"],
    },
}]

messages = [{"role": "user", "content": "What is 2 + 3?"}]
response = client.messages.create(model=al.MODEL, max_tokens=200, tools=TOOLS, messages=messages)
call = response.content[0]
result = call.input["a"] + call.input["b"]
messages.append({"role": "assistant", "content": response.content})
messages.append({"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": call.id, "content": str(result)},
]})
response = client.messages.create(model=al.MODEL, max_tokens=200, tools=TOOLS, messages=messages)
print(al.format_transcript(messages, response))
print(response.content[0].text)
