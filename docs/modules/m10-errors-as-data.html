Errors as Data

The loop you wrote in M09 works when nothing goes wrong. Real tools fail, the model sometimes sends bad arguments, and the API itself returns errors. This module shows how to turn each failure into something the agent can read and recover from, and how to tell the errors you retry from the errors you fix.

⏱ ~1.5 hoursPrerequisites: M09 The Agent Loop
  • Wrap tool execution so any exception becomes a tool_result with "is_error": True instead of a crash
  • Write error messages that tell the model what went wrong and what to do next
  • Validate tool input against its schema with al.validate before running the tool
  • Handle unknown tool names and slow tools without breaking the tool_use/tool_result pairing
  • Classify API errors into "fix the request" (400, 401, 404) and "retry later" (429, 5xx, connection)
  • Write a retry helper with exponential backoff that only retries retryable errors and is testable without sleeping

Three places an agent fails

In M09 you built run_agent(client, task, tools, registry, max_steps): call client.messages.create, append response.content as the assistant turn, run each tool_use block with registry[name](**input), send every tool_result back in one user message, and repeat until stop_reason is not "tool_use". That loop has three places where something can go wrong, and each needs a different response.

  1. The tool fails. Your Python function raises: a file is missing, a city is unknown, an HTTP call times out, a bug divides by zero. This is your code failing.
  2. The model asks for something invalid. It calls a tool that does not exist, or passes arguments that break the schema (a string where you wanted an integer, a missing required field, a value out of range). Your code has not run yet; the request for it is bad.
  3. The API call fails. messages.create itself raises: your request was malformed, your key is wrong, you hit a rate limit, or the service had a transient problem. No model output exists at all.

The first two have the same answer: report the failure back to the model as data. The model is good at reading an error and trying something else, but only if it sees the error. The third has two answers depending on the kind of error: some you retry, some you must fix, because sending the same request again can only fail the same way.

flowchart TD
  F[Something failed] --> Q{Where?}
  Q -->|tool raised| T[Catch it. Send tool_result with is_error true and a helpful message]
  Q -->|bad tool name or input| V[Do not run anything. Send tool_result with is_error true listing the problems]
  Q -->|messages.create raised| A{Which error?}
  A -->|400 / 401 / 404| X[Fix the request or config. Do not retry]
  A -->|429 / 5xx / connection| R[Wait and retry with backoff]
  T --> M[The model reads the error and adapts]
  V --> M

Remember: tool failures and bad tool requests go back to the model as data. API failures are either retried or fixed. A loop that lets any of them escape as an exception ends the run and loses the conversation.

The is_error tool result

A tool_result block has an optional field, "is_error". Setting it to True tells the model that the call failed and that content describes the failure, not a result. Everything else is the same as a normal result: the same tool_use_id, sent in the same user message as the other results, before any text.

{
    "type": "tool_result",
    "tool_use_id": "toolu_01A...",      # must echo the tool_use block's id
    "content": "ZeroDivisionError: division by zero",
    "is_error": True,
}

The pattern is small. Put the call in a try block, and in the except branch build an error result instead of a normal one. Catching the broad Exception is correct here, and rare elsewhere: this is a boundary, the line between your tools and the loop, and the loop's job is to keep going no matter what a tool does. You are not hiding the error; you are routing it to the one reader that can act on it.

Step through the visualizer to see the shape of a recovery: the tool fails, the error result goes into the message list in red, and the model's next request corrects itself.

Now the same divide-by-zero task with the boundary in place. The scripted model is a function step: it reads request.tool_results and answers differently when it sees is_error, which is how a real model behaves too.

Change "b": 0 to "b": 4 in the script and run again: the same function now takes the success branch. The loop did not change at all; only the data did.

  • Dropping the failed call. Skipping a tool_use because its tool raised leaves it unanswered, and the next request fails with BadRequestError. Every call gets a result.
  • Sending the error as plain text. A user text block saying "the tool failed" does not answer the tool_use id. Use a tool_result with is_error.
  • Catching BaseException or using bare except:. That also swallows KeyboardInterrupt and SystemExit. Catch Exception.
  • Hiding it from yourself. The model sees the error; you should too. In real code, log every error result (the mini-project uses structlog for this).

Remember: wrap each tool call in try/except Exception, and on failure return a tool_result with the same tool_use_id, "is_error": True, and a message as its content.

Error messages the model can act on

The model only knows what the error message says. "error" tells it nothing. "KeyError: 'pariss'" tells it a little. A good message answers three questions:

  1. What failed? Name the tool and the input that caused it.
  2. Why? In words, not a stack trace.
  3. What next? Valid values, a suggestion, or "do not retry this".
Weak messageActionable message
KeyError: 'pariss'Unknown city 'Pariss'. Did you mean 'Paris'? Known cities: Paris, Lisbon, Oslo.
FileNotFoundErrorNo file 'notes/2024.md'. Use list_files to see what exists in notes/.
Traceback (most recent call last): ... (40 lines)search failed unexpectedly (TimeoutError: upstream took too long). Try a shorter query.
invalidInvalid input for get_forecast: $.days: value 14 is above maximum 7.

A useful way to organize this is to separate expected failures from unexpected ones. Expected failures are part of the tool's contract: an unknown city, a missing file, an empty search. Raise a dedicated exception class for them, and write the message for the model. Unexpected failures are bugs or outages; you did not write a message for them, so report the exception type and text, and say not to repeat the same call.

The third call is a bug (the tool should have rejected None earlier; the next section shows how). Even so, the model gets one readable line instead of a traceback.

Tool results go to the model and are stored in the conversation, which may be logged or shown to users. Never include secrets, API keys, connection strings, full file system paths you would not show a user, or raw stack traces. Log those details on your side, and give the model a short summary.

A tool returns an empty list for a search with no matches. Is that an error? Usually not: "0 results for 'atlantis census'" is a valid answer, and marking it is_error would suggest the tool is broken. Reserve is_error for calls that could not do their job.

Remember: say what failed, why, and what to do next. Raise a ToolError with a model-ready message for expected failures; summarize unexpected ones by type and text. Keep secrets and stack traces out.

Validate tool input before you run it

In M07 you wrote an input_schema for each tool. Without "strict": True, the schema is guidance: the model usually follows it, but nothing guarantees that the input matches. With strict, the API guarantees schema-valid input, but your registry may also be called from tests, other code, or a future tool definition that forgot the flag. Checking input at the boundary costs one function call and turns a confusing crash deep inside a tool into a precise message.

al.validate(value, schema) is a small JSON Schema validator. It returns a list of problems, one string per problem, and an empty list when the value is valid. Each problem names its location with a path: $ is the whole input, $.days is its days field. Predict the output before running.

Those problem strings are already good error messages. Join them, add the tool name and a short instruction, and send them back as an error result. Crucially, do not run the tool when validation fails. A tool that receives bad input might do something partial or wrong before it raises.

Build the schema lookup once from the same TOOLS list you send to the API, as SCHEMAS does here. Then the schema the model sees and the schema you enforce can never drift apart.

A schema checks shape: types, required fields, ranges. It cannot check meaning, such as whether a file path stays inside the folder you allow, or whether a customer id belongs to the current user. Those checks live in the tool itself and raise ToolError with a clear message. Later stages return to this when they cover permissions and safety.

Remember: call al.validate(block.input, schema) before the tool. If the list is not empty, return an error result built from the problems and skip the call. Derive the schemas from the same tool list you send.

Unknown tools and the pairing rule

The model only calls tools you offered, so an unknown name should be rare. It still happens in practice: your registry and your tool list drift apart after a rename, a tool is offered but its function was never registered, or a test script calls a name you removed. registry[block.name] then raises KeyError outside any try block you wrote for the tool body. Look the name up with registry.get(...) first and answer a missing one with an error result that lists what does exist.

The order of checks inside one execute_tool function is worth fixing in your head, because each check protects the next:

  1. Known tool? If not, error result listing available tools.
  2. Valid input? If not, error result listing the problems.
  3. Run it inside try. ToolError passes its message through; any other exception becomes "failed unexpectedly".
  4. Success: a normal result with str(output) (or JSON) as content.

Remember: look tools up with registry.get, answer unknown names with the list of real ones, and give every tool_use exactly one result, success or failure, in the same user message.

Slow tools and timeouts

A tool that never returns is worse than one that fails: the loop waits forever and the user sees nothing. A timeout is a limit on how long an operation may take before you give up on it. Your agent needs one wherever a tool waits on something outside your process: a network call, a database query, a subprocess, a long scan.

Most of the time you do not need threads for this. You set limits where the waiting happens:

  • Pass a timeout to the library that does I/O. HTTP clients, database drivers and subprocess.run all accept a timeout argument. When it expires they raise, and your boundary turns that into an error result.
  • Check a deadline inside long loops. If a tool pages through results, compute deadline = time.monotonic() + limit before the loop and stop when you pass it. time.monotonic() is a clock that only moves forward, which makes it right for measuring durations (wall-clock time can jump when the system clock is adjusted).
  • Return what you have. A timeout message that includes partial results and a suggestion ("narrow the query") lets the model make progress instead of starting over.

The cell below uses a fake clock, a callable that returns a number you control, so the example runs instantly and gives the same answer every time. Injecting the clock as a parameter (now=) is the same trick you will use for sleep in the retry helper.

Change time_limit=10.0 to 20.0 and the tool finishes all four pages. In real code the default for now would be time.monotonic.

The model call can also be slow. A request that never gets an answer surfaces as a connection error (APIConnectionError), which is retryable; the next sections cover it. Long generations are a separate topic: M04 explained why streaming keeps long outputs from timing out.

Remember: every tool that waits on the outside world needs a limit. Use the library's timeout argument or a time.monotonic() deadline, and report a timeout as an error result with partial results and a next step.

API errors: fix or retry

So far every failure happened after the model answered. Now look at the call to messages.create itself. When it fails there is no response, no content, and nothing to send back to the model. Your code has to decide what to do, and the decision depends on the HTTP status code the API returned. The SDK raises a different exception class for each, and agentlab uses the same names.

ExceptionStatusMeaningWhat to do
BadRequestError400The request is malformed: bad message order, unanswered tool_use, a rejected parameter like temperatureFix the code. Never retry.
AuthenticationError401Missing or invalid API keyFix the configuration. Never retry.
NotFoundError404Unknown model id or endpointFix the model id. Never retry.
RateLimitError429Too many requests or tokens per minuteWait, then retry. Honor the server's wait hint.
InternalServerError500+A transient failure on the serverRetry with backoff.
OverloadedError529The API is temporarily overloadedRetry with backoff.
APIConnectionErrornoneThe request never got an answer: network failure or timeoutRetry with backoff.

The rule underneath the table: retry when the same request could succeed later; fix when it cannot. A 429 or 500 is about the moment, not the request. A 400 is about the request: the mock (like the API) checked it and found it wrong, and it will find it wrong again on every attempt. Retrying a 400 only wastes time and hides the bug.

In the mock, script an API failure with al.fail(error). The step raises that exception instead of answering, and is consumed like any other step. The cell prints each error class with its status code, then shows a scripted rate limit followed by a success.

The class hierarchy helps you write the check. Every error derives from APIError. Errors with a status code derive from APIStatusError and carry status_code. APIConnectionError has no status code because no response arrived. So "is this retryable?" becomes: a connection error, or a status error whose code is 408 (request timeout), 409 (conflict), 429, or 500 and above. That is the same set the real SDK retries automatically.

The anthropic client retries 408, 409, 429 and 5xx errors twice by default, with backoff, before raising. You can change that with max_retries:

import anthropic

client = anthropic.Anthropic(max_retries=5)       # more patience for a batch job
client = anthropic.Anthropic(max_retries=0)       # you handle retries yourself

try:
    response = client.messages.create(model="claude-opus-5-5", max_tokens=1024, messages=messages)
except anthropic.RateLimitError:
    ...                                           # still limited after the SDK's own retries
except anthropic.BadRequestError as exc:
    raise                                         # a bug in the request: fix it

Pick one layer to own retries. If the SDK retries twice and your helper retries four times around it, one logical call can become twelve HTTP requests. Writing the helper yourself is still worth it: it is how you learn what the SDK hides, it works with the mock, and it lets you add policies the SDK does not know about, such as logging each retry or giving up when a run's budget (M11) is spent.

Remember: 400, 401 and 404 mean fix something; never retry them. 429, 5xx, 529 and connection errors are transient; retry them after a delay. al.fail(...) scripts any of them in the mock.

Retry with exponential backoff

"Retry after a delay" leaves two questions: how long, and how many times. Exponential backoff answers the first: wait a base delay after the first failure, then double it after each further failure (1 s, 2 s, 4 s, 8 s...), up to a cap. Doubling backs off quickly from a service that is struggling, so thousands of clients do not hammer it at once, while still retrying fast after a one-off blip. A maximum attempt count answers the second: after that many tries, give up and raise the last error so the caller knows.

A rate limit adds one detail. The server may say how long to wait (in the mock, RateLimitError.retry_after, in seconds). Waiting less than that is pointless, so use the larger of the backoff delay and the server's hint.

The last design decision makes the helper testable: inject the sleep function. The helper takes sleep=time.sleep as a keyword argument. Production code uses the default. Tests pass waits.append, which records each requested delay and returns immediately, so a test of four retries takes microseconds and can assert the exact delays.

Read the delays: 1 s and 2 s from doubling, then 5 s because the rate limit's hint (5) beat the backoff (4). Four scripted steps, four requests. The helper takes a function (make_request), not a response, because it has to be able to make the call again. A lambda with no arguments is the usual way to package "this exact call".

Now the error that must not be retried. The request below passes temperature, which the API (and the mock) rejects with a 400. The helper raises on the first attempt.

Production retry code usually adds jitter: a random amount added to or taken from each delay, such as delay * random.uniform(0.5, 1.0). If a thousand clients all failed at the same instant, pure doubling makes them all retry at the same instants too; jitter spreads them out. The lesson code leaves it out so the delays are exact and testable. If you add it, inject the random source as well.

Wrap only the messages.create call. Do not append anything to messages until the call succeeds. Then a retry sends exactly the same request, and a failure leaves the history valid. Never wrap tool execution in the API retry helper: a tool that sends an email should not run four times because the model call after it hit a 529.

Remember: backoff = base × 2attempt−1, capped; take the larger of that and a rate limit's hint; stop after max_attempts and re-raise; raise non-retryable errors immediately; inject sleep so tests never wait.

Putting it together: a loop that survives

Here is the M09 loop with both layers added. execute_tool is the boundary around tools: unknown name, invalid input, expected failure, unexpected failure, success. call_with_retry is the boundary around the API. The scripted run reproduces the visualizer's scenario and adds a rate limit in the middle: the model misspells a city, gets an error result, the next API call hits a 429 and is retried, and the model corrects itself.

Count the script: four steps for four requests. The failed request is recorded in client.requests too, because the mock validated it before the scripted failure fired. The transcript shows no trace of the 429: retries are invisible to the conversation, which is exactly what you want. Error results, on the other hand, are part of the conversation forever, which is why their wording matters.

This loop still returns None when it runs out of steps, and it ignores max_tokens and refusal stop reasons. It also has no idea how much it has spent. Those are stop conditions, and they are the whole of M11.

Remember: two boundaries make a loop robust: execute_tool around every tool call and call_with_retry around every model call. Errors from the first become conversation; errors from the second are retried or raised.

Write execute_tool(block, registry). block is a tool_use block (with .id, .name, .input); registry maps names to functions. It must never raise, and always return a tool_result dict with "type": "tool_result" and "tool_use_id": block.id:

  • Success: "content" is str(output), and there is no "is_error" key.
  • The function raises: "is_error": True, and the content contains the exception's class name and its message (for example "ZeroDivisionError: division by zero").
  • Unknown tool: "is_error": True, and the content contains the unknown name and every available tool name.
Hint

Use registry.get(block.name) and check for None first. Then wrap func(**block.input) in try / except Exception as exc and build the content with f"{type(exc).__name__}: {exc}". Unpacking the wrong keyword names raises TypeError inside the try, so it is handled for free.

Show solution 
import agentlab as al

def execute_tool(block, registry):
    func = registry.get(block.name)
    if func is None:
        available = ", ".join(sorted(registry))
        return {"type": "tool_result", "tool_use_id": block.id, "is_error": True,
                "content": f"Unknown tool {block.name!r}. Available tools: {available}."}
    try:
        output = func(**block.input)
    except Exception as exc:
        return {"type": "tool_result", "tool_use_id": block.id, "is_error": True,
                "content": f"{type(exc).__name__}: {exc}"}
    return {"type": "tool_result", "tool_use_id": block.id, "content": str(output)}

import agentlab as al

def run_agent(client, task, tools, registry, max_steps=10):
    messages = [{"role": "user", "content": task}]
    for _ in range(max_steps):
        response = client.messages.create(model=al.MODEL, max_tokens=1024, tools=tools, messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return response.text
        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            func = registry.get(block.name)
            if func is None:
                results.append({"type": "tool_result", "tool_use_id": block.id, "is_error": True,
                                "content": f"Unknown tool {block.name!r}. Available: {', '.join(sorted(registry))}."})
                continue
            try:
                output = func(**block.input)
            except Exception as exc:
                results.append({"type": "tool_result", "tool_use_id": block.id, "is_error": True,
                                "content": f"{type(exc).__name__}: {exc}"})
                continue
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(output)})
        messages.append({"role": "user", "content": results})
    return None

Write is_retryable(exc) that returns True only for errors where the same request could succeed later: any al.APIConnectionError, and any al.APIStatusError whose status_code is 408, 409, 429, or 500 and above. Everything else, including exceptions that are not API errors at all, returns False.

Hint

Check isinstance(exc, al.APIConnectionError) first. Then, for isinstance(exc, al.APIStatusError), test exc.status_code in (408, 409, 429) or exc.status_code >= 500.

Show solution 
import agentlab as al

def is_retryable(exc):
    if isinstance(exc, al.APIConnectionError):
        return True
    if isinstance(exc, al.APIStatusError):
        return exc.status_code in (408, 409, 429) or exc.status_code >= 500
    return False

Write call_with_retry(make_request, *, max_attempts=4, base_delay=1.0, max_delay=30.0, sleep=time.sleep). It calls make_request() and returns its result. When the call raises:

  • a non-retryable error (use is_retryable, provided in the starter): re-raise at once, without sleeping;
  • a retryable error on the last allowed attempt: re-raise it;
  • otherwise: call sleep(delay) and try again, where delay is base_delay * 2 ** (attempt - 1) for attempt 1, 2, 3..., capped at max_delay. For an al.RateLimitError, use max(delay, exc.retry_after).

Never call time.sleep directly; always the sleep argument. The tests pass a list's append and check the delays.

Hint

Loop with for attempt in range(1, max_attempts + 1):. Inside, try: return make_request(). In except al.APIError as exc:, re-raise with a bare raise when not is_retryable(exc) or attempt == max_attempts; otherwise compute the delay and call sleep(delay).

Show solution 
import time
import agentlab as al

def is_retryable(exc):
    if isinstance(exc, al.APIConnectionError):
        return True
    if isinstance(exc, al.APIStatusError):
        return exc.status_code in (408, 409, 429) or exc.status_code >= 500
    return False

def call_with_retry(make_request, *, max_attempts=4, base_delay=1.0, max_delay=30.0, sleep=time.sleep):
    for attempt in range(1, max_attempts + 1):
        try:
            return make_request()
        except al.APIError as exc:
            if not is_retryable(exc) or attempt == max_attempts:
                raise
            delay = min(base_delay * 2 ** (attempt - 1), max_delay)
            if isinstance(exc, al.RateLimitError):
                delay = max(delay, exc.retry_after)
            sleep(delay)

Quiz

Recap

  • Agents fail in three places: the tool, the model's request for a tool, and the API call. The first two become conversation; the third is retried or fixed.
  • A failed tool call returns a tool_result with the same tool_use_id, "is_error": True, and a message. Every tool_use gets exactly one result.
  • Good error messages say what failed, why, and what to do next. Use a ToolError for expected failures; summarize unexpected ones; never include secrets or tracebacks.
  • Validate input with al.validate before running a tool, and look tools up with registry.get.
  • Tools that wait on the outside world need a timeout or a time.monotonic() deadline.
  • 400, 401, 404: fix. 408, 409, 429, 5xx, 529, connection errors: retry with exponential backoff, honoring a rate limit's wait hint, up to a maximum number of attempts.
  • Inject sleep (and clocks, and randomness) so failure handling is testable in milliseconds.
  • Retry only the model call, and only one layer should own retries.
