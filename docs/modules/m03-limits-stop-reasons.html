Limits, Effort & Stop Reasons

Every response tells you why the model stopped writing. The answer might be finished, it might be cut off mid-sentence, the model might want a tool, or it might have declined. Code that reads content without checking first will eventually show a user half an answer or crash on an empty list. This module covers every stop reason and how to handle each one, the limits you set on a request, and the controls you have instead of the sampling settings older tutorials still show.

Check stop_reason first

Generation is the model writing its reply one token at a time (M01). It keeps going until something stops it. Every response carries a stop_reason field naming what that something was. There are six values:

stop_reasonWhat happenedWhat your code should do
end_turnThe model finished its reply naturally.Use the answer.
max_tokensThe reply hit the max_tokens limit you set and was cut off.Treat the text as incomplete: raise the limit, ask the model to continue, or report it.
stop_sequenceThe model generated one of your stop_sequences.Use the text up to the marker; response.stop_sequence says which one.
tool_useThe model wants your code to run a tool.Run it and send the result back (M08).
pause_turnA long turn using server-side tools was paused.Send the request again with the paused turn appended so the model can continue.
refusalThe model declined the request.Do not use content as an answer; read stop_details and tell the user.

The rule that follows from this table is short: always check stop_reason before you read content. Only end_turn (and, if you asked for it, stop_sequence) means "here is a complete answer". Only the first line is a complete answer you could show a user. The second stops mid-sentence. The third stopped where it was told to. The fourth has no text at all, only a tool request. The fifth has no content whatsoever. Code that does print(response.content[0].text) would show a broken sentence for the second, crash with AttributeError on the fourth (a tool block has no .text), and crash with IndexError on the fifth.

r.text is agentlab's mock-only shortcut for the joined text blocks (M02). It keeps lesson cells short. In code meant for the real SDK, join b.text for blocks where b.type == "text".

Remember: six stop reasons. Check stop_reason before content, every time. Only end_turn means a naturally finished answer.

max_tokens: a ceiling, not a target

max_tokens is the most tokens the model may generate in one reply. The model does not aim for it or pad its answer to reach it; a two-word answer under max_tokens=4000 is still two words. But if the model has more to say when it reaches the limit, generation stops right there, possibly in the middle of a word, and stop_reason is "max_tokens".

The mock simulates this by keeping about four characters of scripted text per token of max_tokens, the same rough ratio as al.estimate_tokens. Real tokenizers vary, but the behavior is the same: text past the limit is simply never generated.

The truncated reply reads as a plausible sentence fragment. That is the danger: nothing about the text itself tells you it is incomplete. Only stop_reason does. If you store or display it as if it were complete, you ship half an answer, and in M05 you will see that truncated JSON does not even parse.

What to do about a truncated reply

  1. Raise max_tokens if the limit was simply too low for the task. This is the usual fix. Current models can generate up to 128K tokens in one reply; very large values need streaming (M04) so the HTTP connection does not sit idle.
  2. Ask for a shorter answer in the prompt if long output is not what you want.
  3. Continue the reply. Append the partial reply as an assistant turn, then a user turn asking the model to continue from where it stopped, and join the pieces. The history still ends with a user turn, so this is valid. The seam between pieces is not always perfect, so prefer raising the limit when you can.
  4. Report it when none of the above apply: return an error or a clearly marked partial result, never a silent half-answer.

A max_tokens outside 1 to 128,000 is rejected with BadRequestError before anything is generated. Picking a value is a judgment call: generous enough for the longest useful answer, low enough that a runaway reply cannot cost you much.

Remember: stop_reason == "max_tokens" means the text is incomplete even if it looks fine. Raise the limit, ask for less, continue, or report it.

Stop sequences

A stop sequence is a string that ends generation as soon as the model produces it. You pass a list of them in stop_sequences. When one is hit, the response has stop_reason="stop_sequence", response.stop_sequence holds the string that matched, and the text ends just before it: the marker itself is not included.

Stop sequences are useful when you know exactly where useful output ends: a closing tag, a delimiter like END or ---, or the start of a section you do not want. They save output tokens (the model stops instead of writing commentary you would throw away) and they make the output easier to parse.

Choose markers that cannot appear inside a legitimate answer. A stop sequence of "." or "\n" cuts off almost everything. Each stop sequence must be a non-empty string; an empty one is rejected.

Remember: stop_sequences end the reply at a marker you choose. The marker is excluded from the text and reported in response.stop_sequence.

Refusals

Sometimes the model declines a request, for example one that asks for help with something harmful. The response then has stop_reason="refusal" and a stop_details object explaining why: a category (such as "cyber", or None) and a short explanation. The content may be empty or may hold only the start of a reply; either way it is not an answer. al.refusal(category) scripts one in the mock.

Three rules for handling a refusal:

  1. Do not index into content. Check stop_reason first, as the previous section said.
  2. Do not append the refusal to the history as an assistant turn. An empty assistant turn is itself a malformed request, so the next call fails. Roll back the user turn instead, the same way the M02 wrapper does on an error, and tell the user the request was declined.
  3. Do not retry the same request in a loop. A refusal is a decision about the content of the request, not a transient failure. Log the category so you can see patterns, and surface a clear message.

An agent running unattended gets a refusal on step 4 of 10. What should it return to whoever started it? M11 answers this with a structured run result that records the reason the run stopped.

Remember: a refusal has no usable content. Read stop_details, keep it out of the history, tell the user, and do not loop on it.

tool_use and pause_turn

The last two stop reasons are about tools, which Stage 2 covers in depth. You need to recognize them now so your handler does not mistake them for answers.

tool_use: your code has work to do

When you offer tools in the request (M07), the model can stop and ask your program to run one. The response then has stop_reason="tool_use" and its content holds one or more tool_use blocks, each with an id, a tool name, and an input dict. The reply is not finished: the model is waiting for your results. M08 completes the round trip and M09 turns it into a loop.

pause_turn: a long server-side turn, paused

Some tools run on Anthropic's side rather than in your program; these are called server tools (web search is a typical example). During a long turn that uses them, the API may stop and return stop_reason="pause_turn". Nothing is wrong. The model has not finished, and it is not asking you to run anything. To let it continue, send the request again with the paused assistant turn appended to the history exactly as you received it:

import anthropic

client = anthropic.Anthropic()
response = client.messages.create(model="claude-opus-5-5", max_tokens=4096, tools=tools, messages=messages)

while response.stop_reason == "pause_turn":
    messages.append({"role": "assistant", "content": response.content})   # the paused turn, unchanged
    response = client.messages.create(model="claude-opus-5-5", max_tokens=4096, tools=tools, messages=messages)

This looks like prefill (the history ends with an assistant turn), but it is different: you are handing back the model's own unfinished turn so it can resume, not writing words for it. The agentlab mock does not simulate server tools, so this snippet is for reading, not running. A loop like this should also have a limit on how many times it resumes, which is the kind of budget M11 teaches.

Remember: tool_use means "run these tools and send the results back". pause_turn means "send the same request again with my paused turn appended, and I will carry on". Neither is a finished answer.

One handler for every stop reason

Rather than scattering if response.stop_reason == ... checks through a program, put the decision in one function. handle(response) looks at the stop reason and returns a small, uniform outcome that the rest of your code can act on: a status, the text (when there is any), and a detail specific to that stop reason. Python's match statement fits this well, because each stop reason becomes one readable case.

Notice the design choices:

  • The last case raises. If a future API version adds a stop reason, this code fails at the exact place that needs updating, instead of silently treating the new reason as an answer. Failing loudly on the unknown is a habit worth keeping everywhere you branch on values that come from outside your program.
  • handle decides, it does not act. It does not call the API again, print, or change any history. That keeps it a pure function, trivial to test with scripted responses, and reusable in a chat wrapper, a batch job, or the agent loop of M09, each of which acts on the outcome differently.
  • The pause_turn step was fabricated with al.Message(..., stop_reason="pause_turn"). The mock accepts a hand-built Message as a script step, which is how you test code paths the mock does not simulate.

Here is how a caller might act on each outcome in a simple chat program:

outcome = handle(response)
if outcome.status in ("done", "stopped"):
    show(outcome.text)
elif outcome.status == "truncated":
    show(outcome.text + "\n[reply cut off: raise max_tokens or ask for less]")
elif outcome.status == "refused":
    show(f"The request was declined (category: {outcome.detail}).")
else:   # needs_tools, paused: this program has no tools, so this is a bug in the request
    raise RuntimeError(f"unexpected outcome: {outcome.status}")

Remember: one function maps every stop reason to an outcome. Handle all six explicitly, raise on anything else, and keep the function free of side effects so it is easy to test.

Effort and adaptive thinking

Effort tells the model how much work to put into a reply: how carefully to reason, how thoroughly to check, how much to write. You set it with output_config={"effort": level}, where level is one of "low", "medium", "high", "xhigh", or "max". If you leave it out, Claude Opus 5.5 uses medium.

LevelGood for
lowSimple, well-defined tasks where speed and cost matter most: classification, short extraction, quick lookups, high-volume pipelines.
medium (default)A balanced starting point for most work.
high, xhighHarder problems: multi-step reasoning, careful code changes, agent tasks where a wrong step is expensive.
maxThe hardest problems, where quality matters far more than time or cost.

The trade-off is the one you met in M01: more effort generally means more output tokens, so higher cost and longer latency, in exchange for better answers on hard problems. On an easy task, extra effort buys little. Start at the default, measure, and move up or down per task, not per application.

A mock cannot be smarter at high than at low, but it can show you the mechanics. The responder below reads the effort level from each request through request.effort (which reports medium when none was sent) and pretends that higher effort produces a longer answer, so you can watch output tokens move.

In real SDK code the parameter is identical:

import anthropic

client = anthropic.Anthropic()   # the only change from the mock
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    output_config={"effort": "low"},
    messages=[{"role": "user", "content": "Label this review positive, negative, or neutral: ..."}],
)

Adaptive thinking

Before answering, a model can reason internally; this is called thinking. On current models thinking is adaptive: the model decides for itself whether a request needs thinking and how much, guided by the effort level. You either omit the thinking parameter or send thinking={"type": "adaptive"}. Older APIs let you switch thinking off or give it a fixed token budget; on Opus 5.5 both forms are rejected. Effort is the control you use instead.

Remember: output_config={"effort": ...} with low, medium, high, xhigh, or max; Opus 5.5 defaults to medium. Thinking is adaptive; do not send disabled or budget_tokens.

Why temperature, top_p and top_k are rejected

Many tutorials and older code samples pass temperature (often temperature=0 "for determinism"), top_p, or top_k. These sampling parameters used to adjust how the next token was picked from the model's probabilities. On current models and API versions, all three are rejected with a 400 error:

The fix when you meet them in old code is simply to delete them. What you actually wanted from them has better tools now:

What the old setting was trying to doWhat to use
"Make answers consistent" (temperature=0)A precise prompt with examples (M06) and a fixed output format (M05). Output can still vary run to run (M01), so test properties of the answer, not exact strings.
"Make answers more focused or more careful"output_config.effort
"Make answers more creative or varied"Say so in the prompt: ask for several distinct options, a particular style, or an unusual angle.

Because the error is a 400, a retry loop will not help: the request is wrong and will fail identically every time. This is a common reason ported code "suddenly" fails. M10 builds the habit of telling fix-the-request errors from retry-later errors.

Remember: no temperature, top_p, or top_k. Steer with the prompt and output_config.effort, and test behavior rather than exact wording.

No prefill

Prefill was a technique of ending messages with a partial assistant turn, such as {"role": "assistant", "content": "{"}, so the model would continue from your words. People used it to force JSON output or to skip a preamble. On current models a history that ends with an assistant turn is rejected:

Each old use of prefill has a direct replacement:

  • Forcing a format such as JSON: use structured output, output_config={"format": {"type": "json_schema", ...}}, which guarantees the shape (M05).
  • Skipping a preamble or setting a voice: say so in the system prompt ("Reply with the answer only, no introduction").
  • Ending output at a known point: add a stop sequence.

Two patterns from this module end with an assistant turn and are not prefill. Continuing after max_tokens appends the partial reply and then a user turn, so the history ends with the user. Resuming after pause_turn hands back the model's own paused turn unchanged; you are not writing words for it.

Remember: never end messages with an assistant turn you wrote. Use structured output, the system prompt, or stop sequences instead.

Write ask_until_end(client, question) that sends question as the only user message with model=al.MODEL, max_tokens=150, and stop_sequences=["END"]. Return a tuple (text, stop_reason), where text is the joined text blocks with surrounding whitespace stripped.

Pass stop_sequences=["END"] to create. Join text blocks by filtering on b.type == "text" so an empty content list gives "", then .strip().

Show solution 
import agentlab as al

def ask_until_end(client, question):
    response = client.messages.create(
        model=al.MODEL,
        max_tokens=150,
        stop_sequences=["END"],
        messages=[{"role": "user", "content": question}],
    )
    text = "".join(b.text for b in response.content if b.type == "text")
    return text.strip(), response.stop_reason

Write handle(response) that returns a dict {"status": ..., "text": ..., "detail": ...} based on response.stop_reason. text is always the joined text blocks ("" if none).

stop_reasonstatusdetail
end_turn"done"None
max_tokens"truncated"None
stop_sequence"stopped"response.stop_sequence
tool_use"needs_tools"list of the tool names requested, in order
pause_turn"paused"None
refusal"refused"response.stop_details.category

For any other stop reason, raise ValueError. Do not use the mock-only response.text.

Hint

Compute text once at the top, then use match response.stop_reason: with one case per value and a final case other: that raises. For tools: [b.name for b in response.content if b.type == "tool_use"].

Show solution 
def handle(response):
    text = "".join(b.text for b in response.content if b.type == "text")
    match response.stop_reason:
        case "end_turn":
            return {"status": "done", "text": text, "detail": None}
        case "max_tokens":
            return {"status": "truncated", "text": text, "detail": None}
        case "stop_sequence":
            return {"status": "stopped", "text": text, "detail": response.stop_sequence}
        case "tool_use":
            names = [b.name for b in response.content if b.type == "tool_use"]
            return {"status": "needs_tools", "text": text, "detail": names}
        case "pause_turn":
            return {"status": "paused", "text": text, "detail": None}
        case "refusal":
            return {"status": "refused", "text": text, "detail": response.stop_details.category}
        case other:
            raise ValueError(f"unhandled stop_reason: {other!r}")

This sentiment classifier was copied from an old tutorial. It uses temperature and an assistant prefill, so every call now fails with BadRequestError, and it never checks the stop reason. Rewrite classify(client, review) so that it:

  • sends no temperature and no prefill (the history ends with the user message);
  • puts the instruction in a non-empty system prompt, asking for a single word: positive, negative, or neutral;
  • sends the review as the user message and uses output_config={"effort": "low"}, model=al.MODEL, and max_tokens=10;
  • returns the reply text stripped and lowercased when stop_reason is end_turn, and raises RuntimeError for any other stop reason.
Hint

Delete temperature=0 and the assistant dict. Add system="Classify the sentiment of the review. Reply with one word: positive, negative, or neutral." and output_config={"effort": "low"}. Check response.stop_reason != "end_turn" before touching content.

Show solution 
import agentlab as al

SYSTEM = "Classify the sentiment of the review. Reply with one word: positive, negative, or neutral."

def classify(client, review):
    response = client.messages.create(
        model=al.MODEL,
        max_tokens=10,
        system=SYSTEM,
        output_config={"effort": "low"},
        messages=[{"role": "user", "content": review}],
    )
    if response.stop_reason != "end_turn":
        raise RuntimeError(f"classification failed: stop_reason={response.stop_reason}")
    text = "".join(b.text for b in response.content if b.type == "text")
    return text.strip().lower()

Write complete(client, prompt, max_tokens=200, max_rounds=3) that keeps asking until the reply is complete:

  • Start with messages = [{"role": "user", "content": prompt}] and call create with model=al.MODEL and the given max_tokens.
  • Collect the text of every reply.
  • On end_turn, return all collected text joined with no separator.
  • On max_tokens, append the partial reply as {"role": "assistant", "content": response.content}, then append {"role": "user", "content": "Continue exactly where you stopped."}, and call again.
  • On any other stop reason, raise RuntimeError.
  • Make at most max_rounds requests; if the reply is still truncated after that, raise RuntimeError.
Hint

Use for _ in range(max_rounds):. Inside: call, append the text to a parts list, return on end_turn, extend the history on max_tokens, raise otherwise. After the loop, raise because the rounds ran out.

Show solution 
import agentlab as al

CONTINUE = "Continue exactly where you stopped."

def complete(client, prompt, max_tokens=200, max_rounds=3):
    messages = [{"role": "user", "content": prompt}]
    parts = []
    for _ in range(max_rounds):
        response = client.messages.create(model=al.MODEL, max_tokens=max_tokens, messages=messages)
        parts.append("".join(b.text for b in response.content if b.type == "text"))
        if response.stop_reason == "end_turn":
            return "".join(parts)
        if response.stop_reason != "max_tokens":
            raise RuntimeError(f"cannot continue after stop_reason={response.stop_reason}")
        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": CONTINUE})
    raise RuntimeError(f"reply still truncated after {max_rounds} rounds")

Mini-projectask.py: one question, every stop reason handled

Build a command-line tool that sends one question and handles whatever comes back, then use it to measure what effort levels cost on your own prompts.

Use al.get_client() when ANTHROPIC_API_KEY is set, and an al.MockClient otherwise. For the mock, write a responder that returns different scripted outcomes depending on a --simulate option (truncate, refuse, stop), so you can exercise every branch without the real API.

Spec

  • Options (via argparse): the question, --effort (choices: low, medium, high, xhigh, max; omitted means the model default), --max-tokens, --stop (repeatable, becomes stop_sequences), --continue-rounds.
  • A handle(response) function covering all six stop reasons and raising on anything else.
  • end_turn and stop_sequence print the answer. max_tokens continues up to --continue-rounds times, then prints the partial text with a clear "[truncated]" marker. refusal prints the category and exits with status 2. tool_use and pause_turn cannot happen without tools, so they exit with an error naming the stop reason.
  • Log one structlog event per request with stop_reason, effort, input_tokens, output_tokens, and elapsed seconds. Structured fields let you compare runs later without parsing text.
  • No temperature, top_p, top_k, prefill, or thinking budget anywhere.
  • Runs against the mock with no API key set, and against the real API when one is set
  • --simulate truncate, --simulate refuse, and --simulate stop each take the correct branch
  • A truncated reply is never printed without the "[truncated]" marker
  • A refusal exits with status 2 and never crashes on empty content
  • An unknown stop reason raises instead of printing anything
  • Every request logs stop_reason, effort, token counts, and latency as structured fields
  • You ran one real prompt at low, medium, and high effort and wrote down output tokens and latency for each

Stretch goals: write pytest tests for handle using scripted MockClient responses, including a hand-built pause_turn message; add a --json flag that prints the outcome as JSON for use in shell scripts; compute the cost of each run from usage with the prices from M01.

Quiz

Recap

  • Six stop reasons: end_turn, max_tokens, stop_sequence, tool_use, pause_turn, refusal. Check stop_reason before reading content.
  • max_tokens is a ceiling. A truncated reply can look complete; raise the limit, ask for less, continue with a user "continue" turn, or report it.
  • stop_sequences end the reply at a marker you choose; the marker is excluded and reported in stop_sequence.
  • A refusal has no usable content. Read stop_details, keep it out of the history, do not loop on it.
  • tool_use: run tools and send results. pause_turn: re-send with the paused turn appended.
  • One pure handle(response) covers every stop reason and raises on unknown ones.
  • output_config={"effort": ...} trades tokens and latency for quality; Opus 5.5 defaults to medium. Thinking is adaptive.
  • temperature, top_p, top_k, prefill, disabled thinking, and budget_tokens are rejected. Use the prompt, effort, structured output, and stop sequences.
