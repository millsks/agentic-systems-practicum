Structured Output

Prose is for people. Programs need data: fields with names, types, and rules. This module turns a model's answer into something your code can rely on, by describing the shape you want with JSON Schema, asking the API to follow it, and checking what comes back before you trust it.

⏱ ~2 hoursPrerequisites: M02 The Messages API, M03 Limits, Effort & Stop Reasons
  • Explain why parsing free-form text is fragile and what it means to treat JSON as a contract
  • Write JSON Schemas with type, properties, required, additionalProperties, enum, items, and nullable fields
  • Request schema-shaped output with output_config={"format": {"type": "json_schema", "schema": ...}}
  • Check stop_reason, parse with json.loads, and validate with al.validate before using the data
  • Convert validated dicts into dataclasses, and enforce business rules a schema cannot express
  • Recover from wrong output with a bounded re-ask loop that sends the error back to the model
  • Design extraction prompts and schemas that say "unknown" instead of guessing

Why free text breaks programs

Suppose your code asks a model to pull a customer's name and email out of a support message. You ask nicely for JSON. Most of the time you get it. Sometimes you get this:

The data is right there, wrapped in politeness. The usual first reaction is to write a regular expression that grabs everything between the first { and the last }. That fixes today's reply and fails on tomorrow's, which uses 'single quotes', or calls the field "e-mail", or nests the data under "customer", or leaves out the email because there was none. Each patch makes the parser longer and no more trustworthy.

The fix is to stop treating the answer as text you scrape and start treating it as a contract: an agreement, written down in a machine-checkable form, about exactly what shape the data will have. Both sides use the same document. You give it to the model so it knows what to produce, and you use it in your code to check what you received. The standard language for such contracts is JSON Schema.

This module walks along that pipeline from left to right. Each stage removes one way for bad data to reach the rest of your program.

Remember: do not scrape data out of prose. Write the shape down as a schema, ask for it, and check the reply against the same schema.

JSON Schema in one sitting

A JSON Schema is itself a JSON object (in Python, a dict) that describes what valid data looks like. You only need a handful of keywords for almost everything in this course:

KeywordMeaningExample
typeThe JSON type: object, array, string, integer, number, boolean, null; or a list of them{"type": "string"}, {"type": ["string", "null"]}
propertiesFor an object: a schema for each named field{"name": {"type": "string"}}
requiredFor an object: the fields that must be present["name", "email"]
additionalPropertiesFor an object: false forbids fields not listed in propertiesfalse
enumThe value must be one of a fixed list{"enum": ["low", "medium", "high"]}
itemsFor an array: the schema every element must match{"type": "array", "items": {"type": "string"}}
descriptionHuman-readable notes; the model reads them too"ISO 8601 date, e.g. 2026-03-01"

JSON's types map onto Python's in the way you would expect after json.loads: object to dict, array to list, string to str, integer to int, number to int or float, boolean to bool, null to None.

agentlab includes a small validator, al.validate(value, schema). It returns a list of problems, one string per problem, and an empty list when the value is valid. Each problem names the location with a path: $ is the root, $.email a field, $.tags[1] an array element.

Three design choices in that schema are worth copying:

  • Every field is required, and "might be missing" is spelled ["string", "null"]. A field that may be absent forces every reader to write data.get("email") and wonder whether missing means "no email" or "the model forgot". A required, nullable field makes the model say null explicitly.
  • additionalProperties: false. Without it, any extra field is allowed, so a typo such as "emial" passes validation and your code silently reads nothing.
  • enum for categories. If your code branches on priority, the model must choose from the values your code handles. Free text like "ASAP" or "Urgent!" would fall through every branch.

Predict what the validator reports for this value before you run it. Watch the integer-versus-boolean case: in Python True is technically an int, but JSON Schema treats booleans as their own type.

al.validate supports the keywords above plus const, minItems, maxItems, minLength, maxLength, minimum and maximum, and ignores anything else. In a real project you would use the jsonschema package or Pydantic (see the last section). The ideas are identical.

Remember: object schemas list properties, make every field required, use ["type", "null"] for "may be unknown", set additionalProperties: false, and use enum for categories.

Asking for a schema: output_config.format

Writing "reply in JSON with these fields" in the prompt helps, but it is only a request. The Messages API lets you attach the schema itself to the request, so the API constrains the model's reply to match it. You pass it inside output_config (the same object that holds effort from M03):

output_config={
    "format": {
        "type": "json_schema",
        "schema": CONTACT,          # your JSON Schema dict
    },
}

The reply is then a single text block whose text is JSON matching your schema: no greeting, no code fences, no trailing remarks. You parse it with json.loads.

The same request against the real API; only the client line changes:

import json
import anthropic

client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=512,
    messages=[{"role": "user", "content": f"Extract the sender's contact details and priority.\n\n{message}"}],
    output_config={"format": {"type": "json_schema", "schema": CONTACT}},
)
data = json.loads(response.content[0].text)

A few things people get wrong the first time:

  • The schema does not replace the instructions. It fixes the shape; the prompt still has to say what to put in it ("the sender, not people mentioned in the message", "urgent means customers are blocked"). Field descriptions are a good place for per-field rules.
  • The old parameter name. Older examples on the internet use a top-level output_format= argument. It is deprecated; use output_config={"format": ...}.
  • Keep output schemas simple. Types, properties, required, enum, items, nullable types, and additionalProperties: false cover nearly every case. Check numeric ranges and cross-field rules in your own code (the business rules section), and consult the structured output documentation before relying on more exotic schema keywords.

When a request sets output_config.format, the mock checks that the scripted reply is JSON matching the schema, because the real API guarantees that. If it is not, the mock raises al.MockScriptError: that means the script is wrong, not your code. So every scripted reply for such a request in this module is valid JSON. To practise handling bad output, examples below leave output_config off, which is exactly the situation where bad output really happens.

Remember: output_config={"format": {"type": "json_schema", "schema": SCHEMA}}, then json.loads(response.content[0].text). Instructions say what; the schema says what shape.

Check before you parse: stop reasons still matter

"The API guarantees valid JSON" has an important condition attached: the model has to finish. Recall the stop reasons from M03. If the reply hits max_tokens, the JSON is cut off mid-string. If the model declines, stop_reason is "refusal" and there may be no text at all. Parsing either one blindly crashes, or worse, half-works.

So every structured call goes through the same three gates, in this order:

  1. Stop reason. Only "end_turn" means a complete answer. Anything else is handled as in M03 (raise the limit, report the refusal) before you look at the text.
  2. Parse. json.loads, catching json.JSONDecodeError.
  3. Validate. al.validate(data, schema). With output_config.format this should never find a problem, and checking costs microseconds. Without it (an older code path, a different provider, a cached reply, a schema you changed last week), it is your only protection.

Notice the helper joins text blocks itself instead of using the mock's response.text shortcut, so it works unchanged with the real SDK. And it raises one specific exception type with a clear message. That message is about to become very useful: in the re-ask section you will send it back to the model.

Remember: stop reason, then parse, then validate. Turn every failure into one exception type with a message that says exactly what was wrong.

From dicts to dataclasses

A validated dict is safe, but it is still a dict: data["priorty"] is a KeyError at run time, your editor cannot autocomplete field names, and mypy cannot check types. The last step of the pipeline converts the dict into a dataclass, a class whose fields are declared with type hints and whose __init__ is generated for you.

Why validate first and convert second? Line(**line) trusts its input completely: an extra key raises a confusing TypeError, a missing key raises another, and a string where a number belongs is accepted silently (dataclasses do not check types at run time). Validation turns all of those into one clear message before construction, and conversion then cannot fail. Keep the two steps in that order.

frozen=True makes instances immutable, which suits data that came from outside: nobody downstream can "fix up" a field by accident. Derived values such as total are computed properties, so they can never disagree with the lines they come from. That last point matters: do not ask the model for numbers your code can compute.

Remember: validate, then build a dataclass with a from_dict classmethod. Compute derived values in code instead of asking the model for them.

Rules a schema cannot express

A schema checks shape: this field is a string, that one is one of three words. Many real rules are about meaning and relationships: the check-out date is after the check-in date; the stated total equals the sum of the lines; a discount is between 0 and 100 percent; the email the model extracted actually appears in the source text. These are business rules (also called semantic validation), and they live in a plain Python function that returns a list of problems, just like al.validate.

Look at the last rule. The model swapped .org for .com, a plausible-looking value that passes every type check. This kind of check, "is the extracted value actually in the source?", is one of the cheapest and most effective defences in extraction work, because it catches values the model made up rather than copied.

Write problem messages for two readers. A person debugging later wants to know what was wrong. The model, in the next section, needs to know how to fix it. "check_out must be after check_in" serves both; "invalid booking" serves neither.

Remember: schema validation checks shape; business rules check meaning. Return specific, fixable problem messages, and check that extracted values appear in the source.

When the output is wrong: re-ask with the error

When a reply fails validation or a business rule, the simplest recovery is to tell the model what was wrong and ask again, in the same conversation. Because the API is stateless (M02), "the same conversation" means you append two messages to the history and send it all again:

  1. the model's bad reply, as an assistant turn (response.content), so it can see what it produced;
  2. a user turn that lists the problems and asks for a corrected reply.

Then you loop, with a hard limit on attempts, because a loop without a limit is a bill without a limit.

flowchart TD
  A[send request] --> B{stop_reason end_turn?}
  B -- no --> X[raise: incomplete or refused]
  B -- yes --> C[parse + validate + business rules]
  C -- no problems --> D[return data]
  C -- problems --> E{attempts left?}
  E -- no --> Y[raise with the last problems]
  E -- yes --> F[append assistant reply + user message listing problems]
  F --> A

Here is the loop, with a script in which the model first replies with prose around the JSON, then with a value that breaks a business rule, and finally gets it right. There is no output_config here, so the bad replies are realistic.

Read the transcript from the bottom up and you can see why this works: each new request carries the original task, every earlier attempt, and the exact complaint about it. The model is not guessing what went wrong.

With output_config.format the real API guarantees schema-valid JSON on a completed reply, so you should not need to re-ask for shape problems there. The re-ask pattern earns its keep in two situations: business-rule failures (dates in the wrong order, a value not found in the source, totals that do not add up), which no schema can prevent; and code paths that do not use output_config at all. Do not re-ask on truncation or refusal: a max_tokens stop needs a bigger limit or a smaller task, and a refusal needs handling, not repetition.

Some practical rules for the loop:

  • Bound it. Two or three attempts. If the third fails, the prompt or schema is the problem, and more attempts just spend money. Raise an exception with the last problems so a person can see them.
  • Send specific errors. The validator's $.minutes: 600 is outside 5..240 is far more useful to the model than "invalid".
  • Count the cost. Every retry resends the whole history, so attempt three pays for the input of attempts one and two again. Track usage across attempts (M11 turns this into a budget).
  • Log rejections. A rising re-ask rate is an early warning that a prompt or a model version changed behaviour.

Remember: append the bad reply as an assistant turn and the problems as a user turn, then retry, at most two or three times. Re-ask for business rules or unconstrained output; never for truncation or refusal.

Extraction tasks done well

Extraction means turning unstructured text (emails, tickets, PDFs converted to text, chat logs) into records. It is one of the most common and most valuable things teams use models for, and it has one characteristic failure: the model fills in a plausible value when the source does not contain one. You prevent that with the schema, the prompt, and a check.

In the schema

  • Nullable types for anything the source may lack: ["string", "null"].
  • enum with an explicit fallback such as "other" or "unknown", so the model is never forced into a wrong category.
  • descriptions with formats: "ISO 8601 date", "amount in cents".

In the prompt

  • Say what to do when information is missing: "use null; never guess".
  • Separate the instructions from the document, for example inside <document> tags (M06 covers this in depth).
  • Say whose details you want when several people appear.

The order_id of None is the system working: the email has no order number, and your code can now ask the customer for one instead of looking up an invented ORD-0000.

Your manager asks you to add a confidence field from 0 to 1 so you can filter weak extractions. What would that number actually measure? A model's self-reported confidence is just more generated text, not a calibrated probability. Checks you can compute (the value appears in the source, the category is not "other", required fields are not null) are usually a more honest signal.

Remember: nullable fields, an "other" category, a prompt that says "null, never guess", and a check against the source text.

The production path: Pydantic and messages.parse

Everything so far uses plain dicts, json, al.validate, and dataclasses, so you can see every step. In production most Python teams use Pydantic, a library where one class definition is the schema, the validator, and the typed object at once. The Anthropic SDK builds on it: client.messages.parse(...) takes a Pydantic model class, sends its schema as the output format, and validates the reply into an instance of your class, available as response.parsed_output:

import anthropic
from pydantic import BaseModel

class Ticket(BaseModel):
    customer_name: str | None
    order_id: str | None
    category: str
    summary: str

client = anthropic.Anthropic()
response = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Extract a support ticket from: ..."}],
    output_format=Ticket,
)
ticket = response.parsed_output   # a validated Ticket instance

.parse() takes your Pydantic class through its own output_format argument and turns it into the request's output_config.format for you. That convenience argument is not the deprecated request-level output_format field mentioned earlier; on messages.create, always use output_config.

One class replaces the schema dict, the validator call, and the dataclass. That is why it is the production path. The stop-reason check and business rules are still yours to write: a schema-valid ticket can still name an order id that is not in the email.

You will meet schemas again, from the other direction, in M07: a tool's input_schema is the same JSON Schema language, describing the arguments the model sends to your code instead of the answer it returns.

Remember: production code usually defines one Pydantic model and lets client.messages.parse handle schema, parsing, and validation. Stop reasons and business rules remain your job.

Exercises run in the browser and are graded instantly. Tests build their own MockClient scripts and inspect client.requests.

Define USER_SCHEMA, a JSON Schema for a user record with exactly these fields, all required:

  • username: a string
  • email: a string, or null when unknown
  • plan: one of "free", "pro", "team"
  • roles: an array of strings

No other fields are allowed. The tests check your schema with al.validate.

Hint

Use "properties" with one entry per field, {"type": ["string", "null"]} for email, {"enum": [...]} for plan, {"type": "array", "items": {"type": "string"}} for roles, a "required" list, and "additionalProperties": False.

Write parse_structured(response, schema) that returns the reply's data as a dict, or raises ValueError with a helpful message when:

  • response.stop_reason is not "end_turn" (include the stop reason in the message);
  • the text is not valid JSON;
  • the data fails al.validate(data, schema) (include the problems in the message).

Join the text of every text block yourself (do not rely on the mock-only .text).

Hint

Check stop_reason first. Build the text with "".join(b.text for b in response.content if b.type == "text"). Wrap json.loads in try/except json.JSONDecodeError and re-raise as ValueError. Join the validator's problems with "; ".

Show solution 
import json
import agentlab as al

def parse_structured(response, schema):
    if response.stop_reason != "end_turn":
        raise ValueError(f"incomplete reply: stop_reason={response.stop_reason}")
    text = "".join(b.text for b in response.content if b.type == "text")
    try:
        data = json.loads(text)
    except json.JSONDecodeError as e:
        raise ValueError(f"reply is not JSON: {e.msg}") from e
    problems = al.validate(data, schema)
    if problems:
        raise ValueError("schema problems: " + "; ".join(problems))
    return data

The dataclasses below describe an order. Write order_from_dict(data) that builds an Order (with a list of Item objects) from an already validated dict, and complete the total property so it returns the sum of quantity * unit_price over all items, rounded to 2 decimals.

{"order_id": "A-17", "customer": "Lee",
 "items": [{"sku": "PEN", "quantity": 3, "unit_price": 1.25}, {"sku": "INK", "quantity": 1, "unit_price": 6.0}]}

becomes an Order whose total is 9.75.

Hint

Build the items with a list comprehension: [Item(**item) for item in data["items"]]. For the total, use round(sum(i.quantity * i.unit_price for i in self.items), 2).

Show solution 
from dataclasses import dataclass

@dataclass(frozen=True)
class Item:
    sku: str
    quantity: int
    unit_price: float

@dataclass(frozen=True)
class Order:
    order_id: str
    customer: str
    items: list[Item]

    @property
    def total(self) -> float:
        return round(sum(i.quantity * i.unit_price for i in self.items), 2)

def order_from_dict(data: dict) -> Order:
    return Order(
        order_id=data["order_id"],
        customer=data["customer"],
        items=[Item(**item) for item in data["items"]],
    )

Write extract_event(client, text) that asks the model to extract an event from text and returns an Event. Requirements:

  • Use model=al.MODEL, max_tokens=512, and one user message that contains text.
  • Request structured output with output_config={"format": {"type": "json_schema", "schema": EVENT_SCHEMA}}.
  • If stop_reason is not "end_turn", raise ValueError.
  • Otherwise parse the JSON and return Event(**data).
Hint

Build the prompt with an f-string that includes text, call client.messages.create(...) with output_config, check response.stop_reason, then Event(**json.loads(response.content[0].text)).

Show solution 
import json
from dataclasses import dataclass

import agentlab as al

EVENT_SCHEMA = {
    "type": "object",
    "properties": {
        "title": {"type": "string"},
        "date": {"type": ["string", "null"], "description": "ISO 8601 date, or null if not stated"},
        "city": {"type": ["string", "null"]},
    },
    "required": ["title", "date", "city"],
    "additionalProperties": False,
}

@dataclass(frozen=True)
class Event:
    title: str
    date: str | None
    city: str | None

def extract_event(client, text):
    response = client.messages.create(
        model=al.MODEL,
        max_tokens=512,
        messages=[{"role": "user", "content": f"Extract the event. Use null for anything not stated.\n\n{text}"}],
        output_config={"format": {"type": "json_schema", "schema": EVENT_SCHEMA}},
    )
    if response.stop_reason != "end_turn":
        raise ValueError(f"incomplete reply: stop_reason={response.stop_reason}")
    return Event(**json.loads(response.content[0].text))

Write ask_until_valid(client, prompt, schema, check, max_attempts=3). No output_config here: the model may reply with anything. On each attempt:

  1. send the conversation so far (model=al.MODEL, max_tokens=512); the first attempt sends just prompt as a user message;
  2. collect problems: not JSON (one problem describing the error), else al.validate(data, schema), else check(data) (a function returning a list of business-rule problems);
  3. no problems: return the data;
  4. problems: append the reply as an assistant turn (response.content) and a user turn that contains every problem string, then try again.

After max_attempts failed attempts, raise ValueError. You may assume every reply ends with end_turn.

Hint

Keep a history list starting with the prompt. Inside for attempt in range(max_attempts):, build problems step by step, calling check only when parsing and validation passed. On problems, append two messages: the assistant's response.content and a user message like "Fix these problems: " + "; ".join(problems).

Show solution 
import json
import agentlab as al

def ask_until_valid(client, prompt, schema, check, max_attempts=3):
    history = [{"role": "user", "content": prompt}]
    problems = []
    for _ in range(max_attempts):
        response = client.messages.create(model=al.MODEL, max_tokens=512, messages=history)
        text = "".join(b.text for b in response.content if b.type == "text")
        try:
            data = json.loads(text)
        except json.JSONDecodeError as e:
            problems = [f"reply is not valid JSON ({e.msg}); reply with only the JSON object"]
        else:
            problems = al.validate(data, schema) or check(data)
        if not problems:
            return data
        history.append({"role": "assistant", "content": response.content})
        history.append({"role": "user", "content": "Fix these problems and reply with only JSON:\n- "
                        + "\n- ".join(problems)})
    raise ValueError(f"no valid reply after {max_attempts} attempts: {problems}")

Mini-project

Mini-projectreceipts.py: a receipt extractor with checks

Build a command-line tool that reads a folder of plain-text receipts (one per file) and writes one JSON record per receipt to receipts.jsonl. It uses the real API when available and falls back to a MockClient with scripted replies for offline development and tests.

mkdir receipts && cd receipts
pixi init
pixi add python=3.14 anthropic structlog pytest
mkdir samples   # put three to five receipt .txt files here, including one with no date
pixi run python receipts.py samples/ --out receipts.jsonl

Spec

  • RECEIPT_SCHEMA: merchant (string), date (ISO date string or null), currency (enum of a few codes plus "other"), lines (array of objects with description, quantity, unit_price), and stated_total (number or null). All required, no extra properties.
  • Frozen dataclasses Receipt and Line, with a computed total.
  • check_receipt(receipt, source_text): business rules. The merchant appears in the source; if stated_total is not null it matches the computed total within 0.01; quantities are positive.
  • extract(client, text): request with output_config.format, check stop_reason, parse, validate, build, check. On business-rule problems, re-ask at most twice with the problems listed.
  • Log one structlog event per file (file, attempts, ok, problems, input_tokens, output_tokens) so a batch run can be audited afterwards.
  • Every request uses model, an explicit max_tokens, and output_config.format
  • Truncated or refused replies are reported, never parsed
  • A receipt with no date produces "date": null, not an invented date
  • A stated total that disagrees with the lines triggers a re-ask, and gives up after two retries
  • Records in receipts.jsonl are built from the dataclasses (dataclasses.asdict)
  • pytest tests cover the happy path, a business-rule re-ask, and a refusal, all with MockClient
  • No API key in the code; the tool runs offline with the mock fallback

Stretch goals: rewrite the schema and dataclasses as one Pydantic model; add a --effort flag and compare re-ask rates; write a summary line at the end with records processed, re-asks, failures, and total tokens.

Quiz

Recap

  • Scraping data out of prose is fragile. Treat output as a contract written in JSON Schema.
  • Schemas: type, properties, required (all fields), nullable types for unknowns, additionalProperties: false, enum for categories, items for arrays.
  • Request it with output_config={"format": {"type": "json_schema", "schema": ...}}; the reply is JSON text you json.loads. The old output_format parameter is deprecated.
  • Three gates: stop_reason == "end_turn", parse, validate. Truncated and refused replies are never parsed.
  • Validate first, then build frozen dataclasses; compute derived values in code.
  • Business rules check meaning (date order, totals, values present in the source) in plain Python.
  • Re-ask by appending the bad reply and a user message listing the problems; bound the attempts. With output_config, re-ask only for business rules.
  • In production, a Pydantic model with client.messages.parse replaces the schema dict, validator, and dataclass.
