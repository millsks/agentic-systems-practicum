Stop Conditions & Budgets

An agent loop ends when the model stops asking for tools, and nothing guarantees that it will. This module gives your loop its own reasons to stop: step limits, token and cost budgets, a clock, loop detection, and correct handling of truncated and refused responses. Every run then ends with a report that says what it produced, what it cost, and why it stopped.

⏱ ~1.5 hoursPrerequisites: M09 The Agent Loop, M10 Errors as Data
  • Explain why a loop that only checks stop_reason can run forever, and why each step costs more than the last
  • Enforce a step limit and a wall-clock deadline, and end a capped run gracefully
  • Track tokens from response.usage and convert them to dollars at published prices
  • Detect repeated identical tool calls and either nudge the model or stop
  • Handle max_tokens (including a dropped tool call) and refusal in the middle of a loop without corrupting the history
  • Return a RunResult dataclass with the answer, why the run stopped, steps, tokens, and cost

Why a loop needs its own brakes

The M09 loop has one exit: stop_reason != "tool_use". That is the model's decision. Usually it makes it after a few steps. But there are ordinary situations where it keeps going:

  • The task cannot be done with these tools. The model keeps searching with new wording, hoping the next query works.
  • A tool keeps failing. Error results (M10) invite a retry; a broken tool invites many.
  • The model repeats itself. It calls the same tool with the same input and gets the same result, again.
  • The task is simply large. A legitimate job that needs 200 steps when you budgeted for 20.

Step through a run with no natural end. The visualizer's loop stops only because a step limit exists.

Now measure what such a run costs. The API is stateless (M02), so every request re-sends the whole history. Each step adds an assistant turn and a tool result to that history, so each request has more input tokens than the one before. The cell runs eight steps of a model that never gives up and prints the usage of each.

The mock's numbers are small because its messages are short. A real agent's requests carry a system prompt, tool definitions, and tool results that may be thousands of tokens each, so the same shape reaches tens of thousands of tokens per request within a few steps. A stop condition is any rule, checked by your code, that ends the run regardless of what the model wants. A budget is a stop condition expressed as a quantity you are willing to spend: steps, tokens, dollars, seconds.

Remember: the model decides when it is done; your code decides when it has spent enough. Every production loop needs both, because history grows every step and so does the cost of the next request.

Step limits and deadlines

The simplest brake is a step limit: the maximum number of model requests in one run. One step means one messages.create call, plus running whatever tools it asked for. Your M09 loop already took a max_steps argument; what matters now is what the function returns when it hits the limit. Returning None or an empty string hides the reason. Return the reason explicitly.

How big should the limit be? Large enough that a legitimate run never hits it, small enough that a runaway is cheap. Look at real transcripts of successful runs and set the limit at a few times their typical step count. Hitting the limit should be rare, and when it happens it should be logged and investigated.

Ending gracefully

A hard stop throws away everything the model learned. A graceful stop spends one more request to collect a final answer. After the last tool results, add a text block (after the results, in the same user message) telling the model it is out of steps, and send the request with tool_choice={"type": "none"}, which tells the model it may not call tools on this turn. Then it can only answer with text.

Four scripted steps for four requests: three loop steps and the wrap-up. Keep sending tools on that last request; the history contains tool_use blocks, and tool_choice is what switches calling off. Remember that tool_choice can only be auto or none on Opus 5.5; forcing a call is rejected (M07).

Wall-clock deadlines

Steps do not bound time. One step might take a second; another, with a slow tool and a long answer, a minute. If a user is waiting, or a job must finish inside a scheduler's window, add a deadline: compute deadline = time.monotonic() + limit at the start and check it before each request. As in M10, inject the clock so you can test it.

A deadline checked between steps can overshoot by one step. That is usually fine; the per-tool timeouts from M10 bound how long a single step can take.

Remember: count one step per messages.create call, stop at max_steps, and say so in the return value. For a graceful end, append an instruction after the last results and make one more request with tool_choice={"type": "none"}. Check a time.monotonic() deadline before each request when time matters.

Token budgets from usage

Steps are a proxy. What you actually pay for, and what fills the context window, is tokens. Every response carries response.usage (M02) with input_tokens (everything the request sent) and output_tokens (everything the model generated). Add them up across the run and you have the run's exact token spend.

input_tokens = output_tokens = 0
while ...:
    response = client.messages.create(...)
    input_tokens += response.usage.input_tokens
    output_tokens += response.usage.output_tokens
    if input_tokens + output_tokens > max_total_tokens:
        ...   # stop with "token_budget"

Three details matter:

  • Check after each response, before running its tools. The response is already paid for, but nothing that follows is. Tools may be slow or have side effects, and their results only lead to another request you have decided not to make.
  • A budget checked after the fact can overshoot by one request. If that matters, estimate the next request first: al.estimate_request_tokens(messages, tools=tools) in the mock, or client.messages.count_tokens(...) on the real API (M01).
  • Separate input from output. They are priced differently, and they tell different stories: input that grows every step means history is piling up; large output means the model is writing a lot.

In this course the mock estimates usage at about four characters per token, so its numbers show the shape, not the exact counts a real tokenizer would give. The mock also always reports zero for the cache fields (cache_creation_input_tokens, cache_read_input_tokens); prompt caching is a later topic, and this module ignores those fields.

Your budget is enforced from outside: the model does not know it exists, so it cannot plan around it. The real API also offers task budgets (in beta), where you tell the model how many tokens it has for the whole task so it can pace its own work, for example by wrapping up when the budget runs low. Treat that as a model-aware complement to the hard limits in this module, not a replacement: the model's pacing makes a good ending more likely, and your loop's checks make a bounded bill certain.

Remember: sum usage.input_tokens and usage.output_tokens over the run. Check the budget right after each response and before running tools. Estimate the next request if overshooting by one step is not acceptable.

Cost budgets in dollars

Tokens become money at the model's published price, quoted in US dollars per million tokens, with separate prices for input and output:

ModelInput ($ / M tokens)Output ($ / M tokens)
claude-opus-5-54.0020.00
claude-sonnet-5-52.0010.00
claude-haiku-5-50.100.50

The formula is (input_tokens × input_price + output_tokens × output_price) / 1,000,000. Output is five times the price of input on every model here, but agent runs are usually dominated by input, because every step re-reads the history.

A cent or two per run looks harmless until you multiply: a runaway that costs five dollars, triggered by a scheduled job every ten minutes, is a large bill by the end of the month. A cost budget per run puts a ceiling on the worst case, and the total cost in your run report lets you add up spend across runs.

  • Dividing by 1,000 instead of 1,000,000. Prices are per million tokens.
  • Using one price for both directions. Output costs five times input here.
  • Pricing only the last request. Sum usage over every request in the run, including ones whose responses you then discard.
  • Hard-coding prices in the loop. Keep them in one table keyed by model id, so changing model or price is a one-line edit.

Remember: cost = (input × input price + output × output price) / 1,000,000, with prices per model. Check a dollar budget the same way and in the same place as a token budget.

Detecting repeated tool calls

Budgets stop a runaway eventually. Loop detection stops one of its most common causes early: the model calling the same tool with the same input again. Most tools are deterministic over a short run, so an identical call gets an identical result; repeating it cannot help.

To detect "identical", you need a key for each call: a value that is equal exactly when two calls are the same. The tool name plus the input serialized with json.dumps(input, sort_keys=True) works well. sort_keys=True matters: {"q": "x", "limit": 5} and {"limit": 5, "q": "x"} are the same call, and sorting makes their JSON identical (including nested dicts). A collections.Counter then counts each key.

When you detect a repeat, you have two responses, and good loops use both in order:

  1. Nudge. Do not run the tool. Send an error result that says the call is a repeat and suggests what to do instead. This is M10's "errors as data" applied to behavior: the model usually changes course when told.
  2. Stop. If the same call keeps coming after the nudge, end the run with a clear reason such as "repeated_call".

Not every repeat is a loop. Polling a job's status (get_status(job_id)) or reading the time legitimately repeats an identical call, because the answer changes. Exempt such tools, or give them a higher limit. Exact-match detection also misses near-repeats, like the runaway's slightly reworded searches; budgets catch those.

Remember: key each call by name plus json.dumps(input, sort_keys=True), count with a Counter, nudge with an error result on the first repeat, and stop when repeats exceed your limit.

Truncation and refusal in the middle of a loop

M03 covered every stop_reason for a single call. Inside a loop, two of them need extra care because they can leave you with a response you must not treat like a normal turn.

max_tokens: the response was cut off

If the model hits your max_tokens limit while writing, generation stops wherever it was. If it was in the middle of a tool call, that call is incomplete: its input is not usable JSON for your function. The mock models this by dropping a tool_use block that does not fit. You keep any text that came before it, the stop_reason is "max_tokens", and there is nothing to run.

A loop that checks only for "end_turn" treats that truncated response as a tool step, finds no tool_use blocks, and appends a user message with an empty list of results. Worse, if nothing at all fit, response.content is empty, and appending it creates an empty assistant turn. Either way the next request is invalid:

There are two sound responses to max_tokens in a loop:

  • Stop and report it with reason "max_tokens" and whatever text arrived as a partial answer. This is the right default: it is simple, and a recurring truncation is a configuration problem you want to see.
  • Retry the same request with a larger max_tokens, without appending the truncated response. Bound this (one retry, up to a ceiling) so it cannot become a loop of its own. Very large values need streaming (M04).

Never run a tool call from a response that stopped for max_tokens, and never append an empty content list.

refusal: the model declined

A refusal can arrive at any step, including after several successful tool calls: the task may turn into something the model will not do. The response has stop_reason="refusal", usually no content, and stop_details with a category and an explanation.

Stop the run with reason "refusal", record the category and explanation in your logs, and show the user a clear message. Do not retry the same conversation hoping for a different outcome, and do not append the empty turn.

Remember: branch on every stop_reason, not just end_turn. Only tool_use means "run tools and continue". On max_tokens and refusal, stop (or for max_tokens, retry the request with a bigger limit), and never append empty content.

A structured run result

With all these exits, "return the final text" is no longer enough. The caller needs to know whether the text is an answer, and what the run cost. Return a dataclass (a class whose fields Python turns into an __init__ and a readable repr for you):

from dataclasses import dataclass, field

@dataclass
class RunResult:
    answer: str            # final text; may be partial or empty when the run did not finish
    stopped_because: str   # "end_turn", "max_steps", "token_budget", "cost_budget",
                           # "repeated_call", "max_tokens", "refusal", "deadline", ...
    steps: int             # messages.create calls made
    input_tokens: int
    output_tokens: int
    cost_usd: float
    messages: list = field(default_factory=list, repr=False)   # the transcript, for debugging

The field is called stopped_because rather than stop_reason on purpose: the API's stop_reason describes one response, while this describes the whole run, and several of its values ("max_steps", "cost_budget") come from your code, not the model. Only stopped_because == "end_turn" means the model finished on its own.

The order of checks inside the loop is where the design lives:

flowchart TD
  S{steps < max_steps?} -->|no| MS[stop: max_steps]
  S -->|yes| C[messages.create, steps += 1, add usage]
  C --> R{stop_reason}
  R -->|end_turn, max_tokens, refusal, other| E[stop with that reason]
  R -->|tool_use| B{over cost or token budget?}
  B -->|yes| BB[stop: cost_budget / token_budget]
  B -->|no| P{identical call over the limit?}
  P -->|yes| PP[stop: repeated_call]
  P -->|no| T[run tools, append results] --> S

Four runs, four different reasons, and each report says exactly what happened. This version keeps the tool execution minimal so the stop logic stands out; a real agent would use M10's execute_tool and call_with_retry in those two places. (Retried requests that failed have no usage to add, so retries do not change the token count; they do cost time, which a deadline covers.)

When the loop stops on a budget or a repeat, the last assistant turn contains tool_use blocks with no results. That transcript cannot be sent again unchanged. If you want to continue later, first append a user message answering every pending call, for example with error results saying the run was paused.

Remember: return a RunResult with the answer, stopped_because, steps, input and output tokens, and cost. Check stop reasons first, then budgets, then repeats, then run tools. Only "end_turn" is a natural finish.

def cost_usd(model, input_tokens, output_tokens):
    if model not in PRICES:
        raise ValueError(f"no price for model {model!r}")
    price_in, price_out = PRICES[model]
    return (input_tokens * price_in + output_tokens * price_out) / 1_000_000

Write a class CallTracker with a method record(name, tool_input) that returns how many times this exact call (same tool name, same input) has now been recorded, including this time. Inputs that differ only in key order, at any nesting level, are the same call. Each tracker counts independently.

import json
from collections import Counter

class CallTracker:
    def __init__(self):
        self.counts = Counter()

    def record(self, name, tool_input):
        key = name + ":" + json.dumps(tool_input, sort_keys=True)
        self.counts[key] += 1
        return self.counts[key]

def run_agent(client, task, tools, registry, *, max_steps=10):
    messages = [{"role": "user", "content": task}]
    steps = input_tokens = output_tokens = 0

    def finish(why, answer):
        return RunResult(answer, why, steps, input_tokens, output_tokens,
                         cost_usd(al.MODEL, input_tokens, output_tokens), messages)

    while steps < max_steps:
        response = client.messages.create(model=al.MODEL, max_tokens=1024, tools=tools, messages=messages)
        steps += 1
        input_tokens += response.usage.input_tokens
        output_tokens += response.usage.output_tokens
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return finish("end_turn", response.text)
        results = [{"type": "tool_result", "tool_use_id": b.id, "content": str(registry[b.name](**b.input))}
                   for b in response.content if b.type == "tool_use"]
        messages.append({"role": "user", "content": results})
    return finish("max_steps", "")

import agentlab as al

PRICES = {"claude-opus-5-5": (4.00, 20.00), "claude-sonnet-5-5": (2.00, 10.00), "claude-haiku-5-5": (0.10, 0.50)}

    price_in, price_out = PRICES[model]
    return (input_tokens * price_in + output_tokens * price_out) / 1_000_000

@dataclass
class RunResult:
    answer: str
    stopped_because: str
    steps: int
    input_tokens: int
    output_tokens: int
    cost_usd: float
    messages: list = field(default_factory=list, repr=False)

def run_agent(client, task, tools, registry, *, max_steps=10, max_tokens=1024,
              max_total_tokens=50_000, max_cost_usd=0.50, max_identical_calls=2):
    messages = [{"role": "user", "content": task}]
    steps = input_tokens = output_tokens = 0
    seen = Counter()

    def finish(why, answer):
        return RunResult(answer, why, steps, input_tokens, output_tokens,
                         cost_usd(al.MODEL, input_tokens, output_tokens), messages)

    while steps < max_steps:
        response = client.messages.create(model=al.MODEL, max_tokens=max_tokens, tools=tools, messages=messages)
        steps += 1
        input_tokens += response.usage.input_tokens
        output_tokens += response.usage.output_tokens
        if response.content:
            messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return finish(response.stop_reason, response.text)
        if cost_usd(al.MODEL, input_tokens, output_tokens) > max_cost_usd:
            return finish("cost_budget", response.text)
        if input_tokens + output_tokens > max_total_tokens:
            return finish("token_budget", response.text)
        calls = [b for b in response.content if b.type == "tool_use"]
        for b in calls:
            seen[b.name + ":" + json.dumps(b.input, sort_keys=True)] += 1
        if max(seen.values()) > max_identical_calls:
            return finish("repeated_call", response.text)
        results = [{"type": "tool_result", "tool_use_id": b.id, "content": str(registry[b.name](**b.input))}
                   for b in calls]
        messages.append({"role": "user", "content": results})
    return finish("max_steps", "")

What to build:

Quiz

Recap

  • The model decides when it is done; your code decides when it has spent enough. Every loop needs both.
  • History grows every step, so each request costs more than the last.
  • A step is one messages.create call. Stop at max_steps, and end gracefully with one more request using tool_choice={"type": "none"} if you want a final answer.
  • Sum usage.input_tokens and usage.output_tokens; cost = (in × in price + out × out price) / 1,000,000. Check budgets after each response and before its tools.
  • Key tool calls by name plus json.dumps(input, sort_keys=True); nudge on a repeat, stop on repeated repeats.
  • Branch on every stop_reason. Never run a tool from a max_tokens response and never append empty content; stop on refusal.
  • Return a RunResult: answer, stopped_because, steps, tokens, cost. Only "end_turn" is a natural finish.
  • Task budgets on the real API let the model pace itself; they complement, not replace, your limits.
