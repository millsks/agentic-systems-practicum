Tool Design

Your agent loop is finished. From here on, most of an agent's quality comes from its tools: how many there are, what they are called, what their descriptions promise, and what their results look like when they come back. The model can only be as good as the interface you hand it. This module is about designing that interface on purpose.

⏱ ~2 hoursPrerequisites: M07 Tools as Contracts, M09 The Agent Loop, M10 Errors as Data
  • Explain why a toolset is a user interface for the model, and what it costs on every request
  • Consolidate overlapping tools into fewer, clearer ones with consistent names
  • Put usage guidance where it works best: in tool and parameter descriptions
  • Format tool results the model can read: concise, with stable ids, truncated with a note, and paginated
  • Separate read tools from write tools and enforce confirmation for writes in your own code
  • Recognize non-idempotent tools and redesign them so a repeated call is safe
  • Test tools in isolation, then review a toolset against a checklist

A toolset is an interface for the model

In M07 you learned what a tool is to the model: a name, a description, and an input schema. The model never sees your Python function. It never reads your docstring, your variable names, or your database layout. Everything it knows about a tool comes from those three fields, plus whatever the tool sends back as a tool_result.

That makes a toolset an interface in the same sense that a command-line program or a web form is an interface. A human user who meets a confusing form fills it in wrong. A model that meets a confusing toolset does the same: it picks the wrong tool, passes a malformed argument, calls a tool five times when once would do, or gives up and guesses. When an agent misbehaves, the first place to look is usually not the system prompt. It is the tools.

There is also a plain cost. Tool definitions are part of the request. Because the API is stateless (M02), they are sent again on every request in the loop, and so are all the tool results already in the history. A bloated toolset and chatty results make every step slower and more expensive.

The numbers are estimates (al.estimate_tokens assumes about four characters per token; real counts come from messages.count_tokens, see M01). The shape is what matters: tool definitions are a fixed tax on every step, and the tax grows with every tool you add. Paste a larger toolset into the meter below and change the number of calls to see how fast it adds up.

Think of a new teammate who can only learn your system from a one-page reference card. Every tool is a line on that card. Would a new teammate know which line to use, what to type, and what the answer means? If not, the model will not either.

Remember: the model sees only names, descriptions, schemas, and results. Tool definitions and results are re-sent on every step, so every word in them is paid for many times.

Fewer, clearer tools

A common first design maps one tool to every function or API endpoint you happen to have. For a notes app that might look like this:

get_note, fetch_note_by_id, find_notes_by_title, find_notes_by_tag, search_note_bodies,
list_all_notes, list_recent_notes, create_note, add_note_tag, remove_note_tag, update_note_text

Eleven tools, and three problems:

  1. Overlap. get_note and fetch_note_by_id do the same thing. The three find_/search_ tools differ only in which field they look at. Every overlap is a decision the model must make on every step, with nothing to decide it by.
  2. Fragmented workflows. To answer "what did I write about Pixi?", the model must guess whether "Pixi" is a title, a tag, or something in a body, and may call all three tools to be safe. That is three round trips where one would do.
  3. Dangerous neighbors. Listing every note (list_all_notes) can flood the context with thousands of entries. It exists because an endpoint exists, not because the model needs it.

The fix is to design tools around the tasks the agent performs, not around the functions you already have. Merge tools that differ only by a parameter, drop tools that only make things worse, and let one call do a whole unit of work:

Before: 11 tools

get_note(id)
fetch_note_by_id(id)
find_notes_by_title(title)
find_notes_by_tag(tag)
search_note_bodies(text)
list_all_notes()
list_recent_notes()
create_note(title, text)
add_note_tag(id, tag)
remove_note_tag(id, tag)
update_note_text(id, text)

After: 4 tools

notes_search(query, field="any",
             sort="relevance", limit=5)
notes_read(note_id)
notes_create(title, text, tags=[])
notes_update(note_id, text=None,
             tags=None)

notes_search replaces five tools: a field enum covers title, tag, and body, and sort="recent" covers "recent notes" without dumping everything. notes_update sets text and tags in one call instead of three. The model now has one obvious choice at each step.

Consolidation has a limit. Do not build one giant notes(action, ...) tool whose schema accepts every combination of fields; then the model must learn an internal mini-language from one description, and the schema can no longer say which fields go with which action. A good rule: one tool per distinct kind of action, with parameters for the variations of that action. Reading and writing are different kinds of action (more on that below); searching by title and searching by tag are not.

There is no magic number. A focused agent usually needs a handful. Warning signs that you have too many: two tools whose descriptions you cannot tell apart in one sentence, tools the model never calls in your test transcripts, and transcripts where the model calls several tools to do what is really one task. Stage 3 of the roadmap returns to this when context budgets get tight.

Remember: design tools around tasks, not endpoints. Merge tools that differ only by a parameter. Remove tools that invite floods. One tool per kind of action.

Names and descriptions that steer

Names

A tool name is the first thing the model reads, and it reads it in every transcript line. Good names follow a few conventions:

  • Verb and object, in snake_case: search_notes, read_note, create_issue. A name with no verb (notes) hides what the call does.
  • A shared prefix for related tools once you have more than one area: notes_search, notes_read, calendar_list_events. Prefixes group tools and make it obvious which system a call touches. Pick prefix-first or verb-first and use it everywhere.
  • The same word for the same thing. If one tool takes note_id, every tool takes note_id, not id in one place and noteId in another.
  • Only letters, digits, underscores, and hyphens, up to 64 characters. agentlab rejects anything else, and names must be unique within a request.

Rejected requests never reach the script, so the single scripted "ok" answers only the request that was valid.

Descriptions beat clever prompts

When a model misuses a tool, the tempting fix is a new line in the system prompt: "Always search before you read a note." That works for a while, then the system prompt grows into a list of special cases far from the tools they describe. Guidance about a tool belongs in that tool's description, because that is where the model looks when it is deciding whether and how to call it.

A description that steers well answers four questions:

  1. What does it do? One plain sentence.
  2. When should it be used, and when not? Name the neighbor tool if there is one.
  3. What does it return? The shape and size of the result, so the model knows what to expect and what to do next.
  4. What are the limits? Caps, required formats, side effects.

Vague

  "name": "notes_search",
  "description": "Searches notes.",
  "input_schema": {
    "type": "object",
    "properties": {
      "q": {"type": "string"},
      "n": {"type": "integer"}
    },
    "required": ["q"]
  }
}

Steering

{
  "name": "notes_search",
  "description": (
    "Find the user's notes by keyword. Use this first "
    "whenever you need a note but do not have its id; "
    "then call notes_read with an id from the results. "
    "Returns at most `limit` lines of the form "
    "'id | title | tags', newest first, plus a "
    "next_cursor when more results exist. Read-only."
  ),
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {"type": "string",
        "description": "One to five keywords, e.g. 'pixi tasks'."},
      "limit": {"type": "integer", "minimum": 1, "maximum": 10,
        "description": "Max results; default 5."}
    },
    "required": ["query"]
  }
}

Notice what the steering version does. It says when to use the tool and what to call next, so the search-then-read workflow lives right where the model needs it. It says what comes back, so the model is not surprised by a cursor. It names its parameters for what they mean (query, not q), gives an example of a good value, and puts the cap in the schema (maximum) as well as the prose. It also says "Read-only", which matters once writes enter the picture.

Descriptions are guidance, not enforcement. "Max 10" in a description does not stop a model from passing 500. Enforce limits in the schema (maximum, enum, and strict from M07) and in your function. The description explains the rule; the code keeps it.

Remember: verb-and-object names, one prefix style, the same parameter name everywhere. Put "when to use, what it returns, and what comes next" in the description, and keep the system prompt for the task itself.

Results the model can read

Designers spend hours on tool definitions and almost no time on tool results. Yet the result is what the model actually reasons over, and it stays in the history for every remaining step of the run. A good result is:

  • Concise. Only the fields that help the model decide what to do next. Internal fields such as owner_acl, etag, or row_version are noise.
  • Identifiable. Every item carries a stable id the model can pass to the next tool. A short readable id (n12) works better than a 36-character UUID, which costs tokens and is easy to garble when copied. If your system uses UUIDs, map them to short ids at the tool boundary.
  • Readable. Plain lines or compact JSON with meaningful keys. Dates as 2026-10-02, not epoch seconds.
  • Bounded. A known maximum size, with a note when something was cut (next section).
  • Self-explaining when empty. "No notes matched 'pixi'. Try fewer or different words." is far more useful than [], which the model may read as "the tool failed".

The formatted result keeps everything the model needs to pick a note (id, title, tags, a snippet) and drops the rest. If the model wants the full body, it calls notes_read("n1"): the search tool points to the next step instead of trying to be every step at once.

Let the model ask for more detail

Sometimes the model does need more. Rather than always returning everything, give the tool a small switch: a detail parameter with an enum such as ["brief", "full"], defaulting to "brief". The description says when "full" is worth it. The model then pays for detail only when it needs it.

Errors are results too

M10 showed that a failed tool returns a tool_result with "is_error": True. Design those messages as carefully as success results: say what went wrong and what to do instead. Compare KeyError: 'n99' with "No note with id n99. Ids look like n12; get them from notes_search." The second one teaches the model how to recover on the very next step.

Remember: return the fields that drive the next decision, short stable ids, readable values, a helpful sentence when empty, and errors that say how to recover. Point to a detail tool rather than inlining everything.

Truncation and pagination

Any tool that returns data you do not control (search results, file contents, logs, web pages) can return something enormous. One 200 KB log file in a tool result is roughly 50,000 tokens that ride along on every later step of the run. Every such tool needs a size cap, and every cap needs a note so the model knows it saw only part of the data.

A silent cut is worse than no cut: the model reasons as if it saw everything and may confidently report that an error "does not appear in the log". The note turns a hidden limit into information the model can act on.

Pagination with a cursor

For lists, the standard design is pagination: return one page of results plus a next_cursor value that the model passes back to get the next page. The cursor is opaque to the model; it just copies it. When there are no more results, next_cursor is None (null in JSON). Including the total count helps the model decide whether paging on is worth it.

The cell below runs a small agent loop (the one from M09). The second scripted step is a function: it reads the first tool_result, takes next_cursor out of it, and asks for the next page, which is exactly what a real model does when the result is designed well. Three script steps, three requests.

An integer offset is fine for a toy. Real back ends often page by an opaque token because the data can change between calls, and offsets then skip or repeat items. Calling the parameter cursor and treating it as an opaque string from day one means you can change how it works without changing the tool's contract.

Cap page_size or limit in code, not just in the schema. If a caller passes limit=10000, clamp it to your maximum and say so in the result.

Remember: every tool that returns external data needs a size cap and a visible truncation note. For lists, return a page, the total, and a next_cursor the model can pass back.

Read tools, write tools, and confirmation

A read tool only looks: search, read, list, get the weather. Calling it twice, or calling it by mistake, wastes a little time and nothing else. A write tool changes something outside the conversation: it creates, updates, deletes, sends, pays, deploys. A mistaken write can lose data or send an email you cannot unsend. The two kinds deserve different treatment.

  • Keep them separate. Never hide a write inside a read (search_notes that also "cleans up" duplicates). The tool name and description must make side effects obvious.
  • Say it in the description. End read tools with "Read-only." and write tools with what they change: "Permanently deletes the note. Cannot be undone."
  • Gate risky writes in your code. Before your dispatcher runs a write tool, it asks for confirmation: a human prompt in an interactive app, a policy check in an automated one. If confirmation is refused, the tool does not run and the model gets an is_error result saying so.

The last point is the important one. A system-prompt line such as "always ask before deleting" is a request to the model. A check in your dispatcher is a guarantee. The model never runs code; your code does, so your code is where the decision lives.

flowchart LR
  TU[tool_use block] --> K{known tool?}
  K -- no --> E1[is_error: unknown tool, list valid names]
  K -- yes --> W{write tool?}
  W -- no --> RUN[run the function]
  W -- yes --> C{confirm name, input}
  C -- declined --> E2[is_error: declined, do not retry]
  C -- approved --> RUN
  RUN -- raises --> E3[is_error: what failed, how to recover]
  RUN -- returns --> OK[tool_result with content]

Change say_no to return True and run it again: the note is deleted and the scripted model reports success. The model's request was identical both times. Only your dispatcher's decision changed.

Which tools in an agent you use daily would you gate? Reading a file: no. Overwriting a file: probably. Sending a message to another person: always. A useful test: "If the model called this by mistake, could I undo it in under a minute?" If not, gate it.

Confirmation is the first piece of a larger topic. Stage 6 of the roadmap covers permissions, sandboxing, human-in-the-loop design, and prompt injection, where text inside a tool result tries to talk the model into calling a write tool. Gating writes in code is also your first defense there.

Remember: separate reads from writes and say which is which in the description. Enforce confirmation in the dispatcher, not the prompt. A declined write returns an is_error result that tells the model not to retry.

Idempotency: safe to call twice

An operation is idempotent if doing it twice has the same effect as doing it once. Setting a light to "on" is idempotent; flipping the switch is not. In an agent, tools get called more than once more often than you would expect: the model repeats a call it is unsure about, your loop retries after a timeout without knowing whether the first attempt landed (M10), or a run restarts from a saved history.

The toggle undid itself. Three design moves make write tools safe to repeat:

  1. Set state, do not flip it. set_done(note_id, true) instead of toggle_done(note_id); set_quantity(item, 3) instead of add_one(item).
  2. Accept a caller-chosen key for creates. create_note(title, text, request_id) stores the request_id; a second call with the same key returns the existing note instead of making a duplicate.
  3. Make deletes tolerant. Deleting something already gone can report "already deleted" rather than failing, so a retry does not look like an error.
CREATED: dict[str, str] = {}   # request_id -> note id

def create_note(title: str, text: str, request_id: str) -> str:
    if request_id in CREATED:
        return f"Already created as {CREATED[request_id]} (same request_id); nothing new was made."
    note_id = store(title, text)
    CREATED[request_id] = note_id
    return f"Created {note_id}."

This is a preview. Idempotency keys, retries, and exactly-once side effects are a Stage 6 topic. For now, notice non-idempotent tools when you design them and prefer the "set" form.

Remember: assume every write tool may be called twice. Set state instead of toggling, give creates a request key, and let deletes of missing items succeed quietly.

Testing tools alone

A tool is an ordinary Python function with a JSON-shaped interface. You can test almost everything about it without any model, mock or real. That matters: when an agent misbehaves, you want to know immediately whether the tool is wrong or the model's use of it is. Test in layers:

  1. The function. Inputs to outputs, including empty results, caps, truncation, and the error messages for bad input. These are fast, deterministic unit tests.
  2. The definition. The schema is valid, required fields exist in properties, every parameter has a description, and an example input passes al.validate.
  3. The dispatcher. Unknown names, gated writes, and exceptions all become tool_result blocks with the right tool_use_id and is_error.
  4. One scripted run. A MockClient script drives a full loop, and the test inspects client.requests to check exactly what your code sent back to the model.

The dispatcher layer is the exercise "Fix the agent that deletes without asking" below. In a real project these functions live in tests/unit/test_tools.py and run with pixi run test; the mini-project sets that up.

Save transcripts of real runs that went wrong and turn them into scripted tests: script the model's calls exactly as they happened and assert on what your tools returned. Each bug you fix becomes a regression test. Stage 5 of the roadmap builds this into full evaluation suites.

Remember: test the function, the definition, the dispatcher, and one scripted run, in that order. Most tool bugs are caught by the first two layers, with no model involved.

A tool design review

Before you ship a toolset, review it the way you would review an API for other developers. This checklist collects the module in one place.

AreaCheck
ScopeEach tool maps to a task the agent performs. No two tools overlap. No tool exists only because an endpoint does.
NamesVerb and object, snake_case, one prefix style, the same parameter names everywhere.
DescriptionsWhat it does, when to use it (and its neighbor), what it returns, its limits, and whether it writes.
SchemaEvery parameter described, with an example. Enums for closed sets. minimum/maximum for numbers. strict: true with additionalProperties: false where valid input matters.
ResultsOnly useful fields, short stable ids, readable values, a helpful empty message.
SizeCapped, with a visible truncation note. Lists paginate with next_cursor.
Errorsis_error results that say what failed and how to recover.
WritesSeparate from reads, gated in the dispatcher, safe to repeat.
TestsFunction, definition, dispatcher, and one scripted run.

TOOLS = [
    {"name": "tickets", "description": "Ticket stuff.",
     "input_schema": {"type": "object", "properties": {
         "action": {"type": "string"}, "id": {"type": "string"}, "data": {"type": "object"}}}},
    {"name": "getCustomer", "description": "Gets a customer.",
     "input_schema": {"type": "object", "properties": {"customerId": {"type": "string"}}}},
    {"name": "get_customer_v2", "description": "Gets a customer (newer).",
     "input_schema": {"type": "object", "properties": {"cust": {"type": "string"}}}},
    {"name": "search_kb", "description": "Search the knowledge base. Returns all matching articles in full.",
     "input_schema": {"type": "object", "properties": {"q": {"type": "string"}}}},
]
Reveal the review
  1. tickets is a do-everything tool: action is a free string, data an untyped object. The model must guess valid actions, and reads and writes are mixed. Split into tickets_search, tickets_read, and tickets_update (gated).
  2. getCustomer and get_customer_v2 overlap. Keep one, named customers_read.
  3. Inconsistent names and parameters: camelCase next to snake_case; id, customerId, cust for similar things. Use ticket_id and customer_id.
  4. No descriptions say when to use a tool, what it returns, or whether it writes.
  5. No parameter descriptions, no required lists, no enums.
  6. search_kb returns every matching article in full: unbounded results. Return titles, ids, and snippets with a cap and a cursor; add kb_read(article_id).
  7. q says nothing; call it query and give an example.

Remember: run the checklist on every new toolset. Most fixes are small (rename, merge, add a cap) and pay off on every single step of every run.

Practice

Exercises run in the browser and are graded instantly. Start with the first and work down.

Write format_hits(hits, limit=3). Each hit is a dict with id, title, tags (a list of strings), and body. Return a single string:

  • One line per hit, for at most limit hits: "{id} | {title} | tags: {tags joined by ', '}". When a hit has no tags, write tags: -. Do not include the body.
  • If hits were left out, add a final line: "... {n} more not shown. Narrow the query or call again with offset={limit}."
  • If hits is empty, return exactly "No notes matched. Try fewer or different words."

Lines are joined with "\n".

Hint

Build a list of lines from hits[:limit], use ", ".join(tags) or "-", then append the note when len(hits) > limit.

Show solution 
def format_hits(hits, limit=3):
    if not hits:
        return "No notes matched. Try fewer or different words."
    lines = [f"{h['id']} | {h['title']} | tags: {', '.join(h['tags']) or '-'}" for h in hits[:limit]]
    hidden = len(hits) - limit
    if hidden > 0:
        lines.append(f"... {hidden} more not shown. Narrow the query or call again with offset={limit}.")
    return "\n".join(lines)

Write search_page(notes, query, cursor=None, page_size=2). notes is a list of dicts with id and title. A note matches when query appears in its title, ignoring case; keep the original order.

  • The cursor is a string holding the start offset; None means the first page.
  • Return a dict: {"results": [...], "total": n, "next_cursor": ...}, where results holds the matching notes for this page (as {"id", "title"} dicts), total is the number of matches overall, and next_cursor is the next start offset as a string, or None when this is the last page.
  • A cursor that is not a string of digits raises ValueError with a message that mentions next_cursor, so the model learns where valid cursors come from.
Hint

Filter with query.lower() in n["title"].lower(). Validate with cursor.isdigit(), then slice hits[start:start + page_size]. There is a next page when start + page_size < len(hits).

Show solution 
def search_page(notes, query, cursor=None, page_size=2):
    if cursor is None:
        start = 0
    elif isinstance(cursor, str) and cursor.isdigit():
        start = int(cursor)
    else:
        raise ValueError(f"Invalid cursor {cursor!r}: pass the next_cursor value from the previous page, or omit it.")
    hits = [{"id": n["id"], "title": n["title"]} for n in notes if query.lower() in n["title"].lower()]
    end = start + page_size
    return {
        "results": hits[start:end],
        "total": len(hits),
        "next_cursor": str(end) if end < len(hits) else None,
    }

Automate part of the design review. Write review_tool(tool) that returns a list of problem strings (empty when the tool passes). Each problem must start with the prefix shown:

  1. "name: ..." when the name does not match ^[a-z][a-z0-9_]*$ or is longer than 64 characters (lowercase snake_case only).
  2. "description: ..." when the description is missing or shorter than 40 characters.
  3. "property {key}: ..." for each property in input_schema["properties"] that has no "description".
  4. "required: ..." for each name in required that is not a property.
  5. "strict: ..." when tool["strict"] is true but the schema does not set additionalProperties to False, and another "strict: ..." problem when it is strict but has no required list.
Hint

Use re.fullmatch(r"[a-z][a-z0-9_]*", name) and len(name) <= 64. Read the schema with tool.get("input_schema", {}) and use .get everywhere so missing keys do not crash the linter.

Show solution 
import re

def review_tool(tool):
    problems = []
    name = tool.get("name", "")
    if not re.fullmatch(r"[a-z][a-z0-9_]*", name) or len(name) > 64:
        problems.append(f"name: {name!r} should be lowercase snake_case, at most 64 characters")
    description = tool.get("description", "")
    if len(description) < 40:
        problems.append("description: say what the tool does, when to use it, and what it returns (40+ characters)")
    schema = tool.get("input_schema", {})
    properties = schema.get("properties", {})
    for key, spec in properties.items():
        if "description" not in spec:
            problems.append(f"property {key}: missing description")
    for key in schema.get("required", []):
        if key not in properties:
            problems.append(f"required: {key!r} is required but is not a property")
    if tool.get("strict"):
        if schema.get("additionalProperties") is not False:
            problems.append("strict: set additionalProperties to False")
        if "required" not in schema:
            problems.append("strict: add a required list")
    return problems

Fix run_tool(block, confirm) so that:

  • An unknown tool name returns an is_error result whose content contains "Unknown tool" and lists the available names.
  • A write tool (in WRITE_TOOLS) first calls confirm(name, input). If it returns false, the tool does not run, and the result is an is_error result whose content contains "declined". Read tools never call confirm.
  • An exception raised by a tool becomes an is_error result whose content is the exception's message, instead of crashing the loop.
  • Successful calls return a plain tool_result (no is_error, or is_error false).

Leave run_agent as it is.

import agentlab as al

NOTES = {"n1": "Buy milk", "n2": "Pixi cheatsheet"}

def list_notes():
    return "\n".join(f"{k} | {v}" for k, v in NOTES.items())

def delete_note(note_id):
    if note_id not in NOTES:
        raise KeyError(f"No note with id {note_id}. Get ids from list_notes.")
    del NOTES[note_id]
    return f"Deleted {note_id}."

TOOLS = [
    {"name": "list_notes", "description": "List note ids and titles. Read-only.",
     "input_schema": {"type": "object", "properties": {}}},
    {"name": "delete_note", "description": "Permanently delete one note by id. Cannot be undone.",
     "input_schema": {"type": "object", "properties": {"note_id": {"type": "string"}}, "required": ["note_id"]}},
]
IMPLS = {"list_notes": list_notes, "delete_note": delete_note}
WRITE_TOOLS = {"delete_note"}

def run_tool(block, confirm):
    def error(text):
        return {"type": "tool_result", "tool_use_id": block.id, "content": text, "is_error": True}
    if block.name not in IMPLS:
        return error(f"Unknown tool {block.name}. Available: {', '.join(IMPLS)}.")
    if block.name in WRITE_TOOLS and not confirm(block.name, block.input):
        return error(f"The user declined {block.name}. Do not retry; tell the user it was not done.")
    try:
        result = IMPLS[block.name](**block.input)
    except Exception as exc:
        return error(str(exc.args[0]) if exc.args else str(exc))
    return {"type": "tool_result", "tool_use_id": block.id, "content": result}

def run_agent(client, task, confirm):
    messages = [{"role": "user", "content": task}]
    for _ in range(10):
        response = client.messages.create(model=al.MODEL, max_tokens=1024, tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return response.text
        results = [run_tool(b, confirm) for b in response.content if b.type == "tool_use"]
        messages.append({"role": "user", "content": results})
    return "stopped: step limit"

An agent has three overlapping tools: find_by_title(title), find_by_tag(tag), and search_bodies(text). Replace them with one strict tool.

Title and body match on a case-insensitive substring; tag matches when the query equals one of the note's tags, ignoring case. Return one line per match, "{id} | {title}", joined with "\n", at most limit lines, and never more than 10 even if a caller passes more. With no matches return "No notes matched {query!r} in {field}."

Hint

Clamp first: limit = max(1, min(limit, 10)). Pick a match test per field: q in note["title"].lower(), q in [t.lower() for t in note["tags"]], or q in note["body"].lower(), where q = query.lower().

            "field": {"type": "string", "enum": ["title", "tag", "body"], "description": "Where to look."},
            "limit": {"type": "integer", "minimum": 1, "maximum": 10, "description": "Max results; default 5."},
        },
    },

def search_notes(query, field, limit=5):
    limit = max(1, min(limit, 10))
    q = query.lower()
    def matches(note):
        if field == "tag":
            return q in [t.lower() for t in note["tags"]]
        return q in note[field].lower()
    hits = [f"{n['id']} | {n['title']}" for n in NOTES if matches(n)]
    if not hits:
        return f"No notes matched {query!r} in {field}."
    return "\n".join(hits[:limit])

Build a small toolkit for a notes agent as a real Pixi project, with the tools in their own module, unit tests that never touch a model, and a short agent script that runs against the real API when a key is available and against MockClient otherwise.

What to build

  • src/notes_tools.py: notes stored in a JSON file. Four tools: notes_search(query, field, limit, cursor), notes_read(note_id), notes_create(title, text, request_id), and notes_set_tags(note_id, tags). Each has a tool definition next to its function, and a REGISTRY maps names to (function, writes).
  • A dispatcher run_tool(block, confirm) that handles unknown tools, gates write tools, and turns exceptions into is_error results.
  • tests/unit/test_notes_tools.py: the four layers from Testing tools alone.
  • src/agent.py: the loop from M09 with the budgets from M11. Use al.get_client() and fall back to a scripted al.MockClient when it raises al.LiveModelUnavailableError or no key is set. confirm asks on the terminal with input().
  • Log every tool call with structlog (tool name, input, is_error, result size in characters) as key=value or JSON lines. Structured logs let you search a week of runs for "which tool errors most" without reading transcripts by hand.
  • Every tool passes your review_tool linter from exercise 3
  • notes_search returns id | title | tags lines, caps results at 10, and returns a next_cursor when more exist
  • A search with no matches returns a sentence that suggests what to try
  • notes_create called twice with the same request_id creates one note
  • notes_set_tags sets the full tag list (no toggling) and is gated by confirm
  • Declining a write returns an is_error result and leaves the file unchanged
  • Unit tests cover the function, definition, dispatcher, and one scripted run, and pass with pixi run pytest tests/unit
  • The API key comes only from the environment; it is not in any file in the project

Stretch goals

  • Add a detail enum ("brief"/"full") to notes_read and truncate brief results to 500 characters with a note.
  • Map internal UUIDs to short ids (n1, n2) at the tool boundary and back.
  • Run the real model on ten questions, save the transcripts, and count how often each tool is called. Remove or merge any tool that is never used.

Quiz

Recap

  • A toolset is the model's whole view of your system: names, descriptions, schemas, and results. Every word is re-sent on every step.
  • Design tools around tasks. Merge tools that differ only by a parameter; drop tools that invite floods; one tool per kind of action.
  • Verb-and-object snake_case names, one prefix style, one name per concept.
  • Descriptions say what the tool does, when to use it, what it returns, and what to call next. Enforce limits in the schema and code too.
  • Results: useful fields only, short stable ids, readable values, helpful empty and error messages.
  • Cap every result and say so when you cut. Paginate lists with next_cursor.
  • Separate reads from writes and gate writes in the dispatcher. Declined writes return is_error.
  • Assume writes can repeat: set rather than toggle, use request keys for creates.
  • Test tools alone first: function, definition, dispatcher, then one scripted run.
