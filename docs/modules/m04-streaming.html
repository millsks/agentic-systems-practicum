Streaming

A model writes its answer one token at a time, but a plain request makes you wait for the last token before you see the first. Streaming hands you each piece as it is generated. It is how chat interfaces feel fast, how long outputs avoid timeouts, and how an agent shows its work while it runs.

Why stream at all

In M01 you saw that a model generates output one token at a time: it predicts a token, appends it, and predicts the next. A response of 600 tokens is 600 small steps. With a plain messages.create(...) call, the API runs all 600 steps on its side and only then sends you the finished Message. Your program, and the person watching it, see nothing until the very end.

Streaming means the API sends the response in pieces over the same HTTP connection while it is still being generated. Each piece is a small event (a JSON object such as "here are three more words"). The technical format is server-sent events (SSE): one long-lived HTTP response that delivers a sequence of events. The SDK reads them for you and hands you Python objects.

Two time measurements make the difference concrete:

  • Time to first token (TTFT): how long from sending the request until the first piece of the answer is visible.
  • Total time: how long until the response is complete.

Notice what the picture does not show: streaming does not shorten the total time, and it does not change the tokens generated, the price, or the final text. The model does the same work. You simply get to use the output earlier. Reasons to stream:

  1. Perceived speed. A person reading a chat answer can start reading after a fraction of a second instead of waiting for the whole paragraph. This is the reason every chat product streams.
  2. Long outputs and timeouts. A response of tens of thousands of tokens can take minutes. A single HTTP response that sits silent for minutes is fragile: proxies and clients give up on idle connections. A stream keeps data flowing. Current models can produce up to 128K output tokens, and large max_tokens values need streaming; the SDK expects you to stream for them.
  3. Progress and early decisions. An agent that streams can show "thinking about X, calling tool Y" while it works, and your code can react to a tool call the moment its block is complete.

You run a batch job overnight that classifies 50,000 support tickets, one short answer each, and nobody watches it. Does streaming help? Mostly not: no one is waiting to read the first word, and the answers are short. Streaming is a tool for latency people can feel and for long outputs, not a default you must always switch on.

agentlab's MockClient has the real SDK's streaming surface, but it does not wait between events: it builds the full scripted response first and then replays it as events, splitting text at word boundaries. Everything about the shape of a stream is faithful; the timing is not. Later in this module you will simulate timing with a fake clock.

Remember: streaming cuts time to first token, not total time or cost. Stream when a person is watching, when outputs are long, or when your code wants to act on partial progress.

Printing text as it arrives

The SDK's streaming helper is client.messages.stream(...). It takes exactly the same arguments as messages.create: model, max_tokens, messages, and the optional fields from M02 and M03. Instead of a Message, it returns a stream object that you use as a context manager (a with block), so the connection is closed when you are done, even if your code raises.

The simplest thing to do with a stream is read stream.text_stream: an iterator that yields only the new pieces of text, as plain strings, in order.

Two details in that loop matter in real programs:

  • end="" stops print from adding a newline after every piece. The pieces already contain their own spaces and newlines; adding more would scramble the text.
  • flush=True forces Python to write to the terminal immediately. Without it, output may sit in a buffer and appear in bursts, which defeats the purpose of streaming.

To see the pieces themselves rather than the assembled sentence, print each one with repr. In the mock, each piece is a word plus its trailing space. The real API's pieces are not words: they are whatever chunk of tokens was ready, sometimes part of a word, sometimes several words. Never write code that assumes a piece is a whole word.

Here is the same code against the real API. The only change from the mock is how the client is created:

import anthropic

client = anthropic.Anthropic()   # reads ANTHROPIC_API_KEY from the environment

with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "In one sentence, what does streaming do?"}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
print()

A common mistake is collecting every piece into a list and printing it at the end. That works, but it throws away the benefit: you have rebuilt a blocking call with more code. If you need the complete text and want to show progress, print each piece as it arrives and also keep it (or ask the stream for the final message, as the next sections show).

Remember: with client.messages.stream(...) as stream: then for text in stream.text_stream: print(text, end="", flush=True). Pieces are arbitrary chunks of text, not words.

Stream events: what actually comes over the wire

text_stream is a convenience. Underneath, the API sends a sequence of typed events that describe the whole Message being built: its start, each content block, the pieces of each block, the final stop reason, and the end. Recall from M02 that a response's content is a list of blocks, each with a type such as "text" or "tool_use". The events mirror that structure exactly.

A delta is a change to apply: "append this text to block 0". The index tells you which block the change belongs to. That is how one stream can carry several blocks, for example a sentence of text (block 0) followed by a tool call (block 1).

You can iterate the stream object itself to get these events. Run this and match each printed line to a row of the table:

Look at where stop_reason lives. In a plain call it is on the response; in a stream it arrives in message_delta, near the very end, because the model does not know why it will stop until it stops. Anything you would check on a finished response (stop_reason, the final usage.output_tokens) is only known after the content has streamed.

Always branch on event.type and silently skip types you do not handle. Do not write an else: raise for unknown events. The real SDK's helper can yield extra convenience event types alongside the raw ones, and a robust consumer treats any event it does not recognise as something to ignore, not an error.

Remember: one message_start; for each block a content_block_start, many content_block_deltas, and a content_block_stop; then message_delta (stop reason and output tokens) and message_stop. The index ties deltas to blocks.

Rebuilding the message by hand

The best way to understand events is to do what the SDK does: start with an empty message and apply each event until you have the full response. This is called accumulating the stream. You will rarely write it in production (the SDK does it for you), but once you have written it, nothing about streaming is mysterious, and you can handle any custom need (forwarding events to a web page, logging per block, cutting a stream short).

Notice the design: blocks[event.index] uses the index to find the block a delta belongs to, so the function stays correct when a response has more than one block. A tempting shortcut is a single text = "" that every delta is added to. It works for one text block and silently merges blocks when there are several.

Accumulation also handles the stop reasons from M03. When the output hits max_tokens, the stream simply ends early and message_delta says so. Predict what this prints. The mock truncates at about four characters per token, so max_tokens=4 keeps about 16 characters:

A person watching that stream saw text appear and then stop mid-word. Your program must still check the stop reason at the end: streaming does not remove the need for the handler you wrote in M03. If anything, it is easier to forget, because the text "looked fine" while it was arriving.

Remember: accumulate by index: start a block on content_block_start, append on each delta, read stop_reason and output_tokens from message_delta. Check the stop reason after the stream ends.

get_final_message() and conversation history

Writing an accumulator teaches the mechanism; in real code you call stream.get_final_message(). It consumes whatever is left of the stream and returns the complete Message: the same object, with the same content blocks, stop_reason, and usage, that messages.create would have returned. The usual pattern streams the text for display and then asks for the final message for everything else:

Everything you learned in M02 still holds. The API is stateless, so the second request sends the whole history. You append final.content (the list of blocks), not just the text, so that tool calls and other blocks survive. Streaming changes how the response arrives; it does not change what you do with it.

One trap catches almost everyone once. A stream is a one-way pipe: each event can be read once. If you iterate text_stream to the end and then iterate the stream again, there is nothing left. Predict the output:

The second loop sees no events because text_stream already consumed them. But get_final_message() still works: it returns the accumulated message no matter how much of the stream you have read. So the rule is: read the events one way (either text_stream or the events), then call get_final_message() for the complete result.

agentlab's Message has a .text property that joins all text blocks. The real SDK's Message does not. Code you intend to run against the real API should join text blocks itself: "".join(b.text for b in final.content if b.type == "text").

Errors behave as you would hope. The request is checked before any event is produced, so a bad request (a sampling parameter, an assistant message last, a missing max_tokens) raises the same BadRequestError or TypeError you saw in M03, at the moment the stream is opened, before any text appears:

Remember: display with text_stream, then final = stream.get_final_message() for content, stop_reason and usage. Append final.content to history. A stream can be iterated only once.

The raw iterator: create(stream=True)

There is a second way to stream: pass stream=True to the ordinary messages.create. Instead of a Message, it returns a plain iterator of the raw events from the table above. There is no text_stream, no get_final_message(), and no context manager: you get the events, and accumulating them is your job.

A classic mistake is to switch on stream=True and keep the rest of the code unchanged:

Which should you use?

messages.stream(...)

The default choice. Gives you text_stream for display, events if you want them, and get_final_message() so you never have to accumulate by hand. Use it in agents and chat interfaces.

create(..., stream=True)

The low-level choice. Use it when you are forwarding raw events somewhere else (for example relaying them to a browser), or when you want full control and fewer abstractions. You accumulate yourself.

The real SDK forms are the same calls on anthropic.Anthropic(); again the only change is the client:

import anthropic

client = anthropic.Anthropic()
events = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Describe the raw stream."}],
    stream=True,
)
for event in events:
    if event.type == "content_block_delta" and event.delta.type == "text_delta":
        print(event.delta.text, end="", flush=True)

Remember: create(stream=True) returns an iterator of raw events, not a Message. Prefer messages.stream(...) unless you need the raw events themselves.

Streaming tool calls: input_json_delta

Tools are the subject of Stage 2 (M07 onward), but you should see now how they look in a stream, because agents stream tool calls all the time. In brief: when a model wants to use a tool, its response contains a tool_use block with an id, a tool name, and an input dict of arguments, and the stop_reason is "tool_use".

In a stream, a tool_use block starts with content_block_start carrying the id and name and an empty input. The input then arrives as input_json_delta events, each holding a fragment of a JSON string in delta.partial_json. Only when you have all the fragments (at content_block_stop) do you have valid JSON to parse.

The fragments are pieces of a string, cut wherever the generator happened to be, not neat key-value pairs. A fragment such as ', "units": "cels' is not JSON on its own. Try to parse fragments early and you get exceptions:

The correct pattern: keep one string buffer per block index; append each partial_json; on content_block_stop, json.loads the buffer once. (Some tools have no arguments; a buffer that is still empty at the stop event means the input is {}.) You will write exactly this in the practice section. With messages.stream(...), get_final_message() does it for you and gives you ToolUseBlocks whose input is already a dict.

Why would anyone handle tool deltas by hand? A user interface can show "Calling get_weather..." as soon as content_block_start names the tool, long before the arguments finish. For tools with large inputs (a whole file to write, say), that early signal matters. For running the tool itself, always wait for the complete block.

Remember: a tool_use block's id and name come in content_block_start; its input comes as input_json_delta fragments. Buffer them by index and parse once at content_block_stop.

Measuring time to first token

Latency is something you measure, not guess. For a streamed call you want two numbers: TTFT (request sent to first text delta) and total time (request sent to message_stop). In a local script you take timestamps with time.perf_counter(), a clock meant for measuring short intervals:

In the browser the mock replays instantly, so real clocks would show zero. Instead, simulate a model with a fake clock: a generator that pretends the first token takes 0.8 seconds (the model reading your prompt and starting) and each later piece 0.05 seconds. This separates the shape of latency from any real network.

Same total, very different experience. What drives the two numbers (from M01): TTFT grows with the size of the input the model must read and with network distance; total time grows mainly with the number of output tokens. A huge prompt with a one-word answer has slow TTFT and a short tail; a short prompt asking for an essay has fast TTFT and a long tail. Higher output_config.effort can also add time before the visible answer starts, because the model may think first.

Measure TTFT at the first text delta, not at message_start. message_start arrives before any content and makes your numbers look better than what a person experiences.

Remember: TTFT = first text delta minus request start; total = last event minus request start. Use time.perf_counter() locally. Input size drives TTFT, output length drives the tail.

Why agents stream

From M09 on you will build agents: a loop that calls the model, runs any tools it asks for, and calls it again until it ends its turn. Each iteration is one request. A run of ten iterations with no streaming is ten silent waits in a row; a user sees a frozen screen for a minute and then a wall of text. Streaming every iteration lets the interface show the model's words and each tool call as they happen.

The loop logic itself does not change. Streaming is a different way of receiving each response; the agent still looks at final.stop_reason and final.content. Here is one iteration's worth, written so that the display and the loop logic are cleanly separated:

The display code reacts to events; the agent code reads the final message. Keep those two jobs apart and adding streaming to an existing agent becomes a small, safe change.

Remember: agents stream for visibility, not for different logic. React to events for display; make decisions from get_final_message().

Write stream_text(client, prompt). It sends prompt as a single user message with model=al.MODEL and max_tokens=512 using client.messages.stream, prints each text piece as it arrives (no extra newlines or spaces), and returns the complete text.

Hint

Open the stream with with client.messages.stream(...) as stream:, loop over stream.text_stream, print with end="", and append each piece to a list you join at the end.

Show solution 
import agentlab as al

def stream_text(client, prompt):
    pieces = []
    with client.messages.stream(
        model=al.MODEL,
        max_tokens=512,
        messages=[{"role": "user", "content": prompt}],
    ) as stream:
        for text in stream.text_stream:
            print(text, end="", flush=True)
            pieces.append(text)
    return "".join(pieces)

Write count_events(events) that takes any iterable of stream events and returns a dict mapping each event type to how many times it occurred, plus a key "text_deltas" counting only the deltas whose delta.type is "text_delta".

For a single text block streamed in three pieces the result is {"message_start": 1, "content_block_start": 1, "content_block_delta": 3, "content_block_stop": 1, "message_delta": 1, "message_stop": 1, "text_deltas": 3}.

Hint

Start with counts = {"text_deltas": 0}. For each event, increase counts[event.type] with counts.get(event.type, 0) + 1, and also increase "text_deltas" when event.type == "content_block_delta" and event.delta.type == "text_delta".

Show solution 
def count_events(events):
    counts = {"text_deltas": 0}
    for event in events:
        counts[event.type] = counts.get(event.type, 0) + 1
        if event.type == "content_block_delta" and event.delta.type == "text_delta":
            counts["text_deltas"] += 1
    return counts

Write accumulate(events) that rebuilds a response from raw events (no get_final_message available: the tests pass you the iterator from create(stream=True)). Return a dict with:

  • "text": all text from text blocks, joined in order
  • "stop_reason": from message_delta
  • "output_tokens": from message_delta's usage
  • "blocks": the list of block types in order, such as ["text"]
Hint

Record event.content_block.type on each content_block_start. Append event.delta.text only for text_delta deltas. On message_delta, read event.delta.stop_reason and event.usage.output_tokens.

Show solution 
def accumulate(events):
    result = {"text": "", "stop_reason": None, "output_tokens": 0, "blocks": []}
    for event in events:
        if event.type == "content_block_start":
            result["blocks"].append(event.content_block.type)
        elif event.type == "content_block_delta" and event.delta.type == "text_delta":
            result["text"] += event.delta.text
        elif event.type == "message_delta":
            result["stop_reason"] = event.delta.stop_reason
            result["output_tokens"] = event.usage.output_tokens
    return result

Write rebuild_tool_calls(events) that returns a list of dicts {"id": ..., "name": ..., "input": {...}}, one per tool_use block, in order. Take the id and name from content_block_start, buffer each block's partial_json fragments by index, and parse the buffer with json.loads at content_block_stop. An empty buffer means the input is {}. Ignore text blocks.

Hint

Keep two dicts keyed by index: starts (the block from content_block_start, only when its type is "tool_use") and buffers (a string). On content_block_stop, if the index is in starts, parse buffers[index] or "{}" and append the dict.

Show solution 
import json

def rebuild_tool_calls(events):
    starts = {}
    buffers = {}
    calls = []
    for event in events:
        if event.type == "content_block_start" and event.content_block.type == "tool_use":
            starts[event.index] = event.content_block
            buffers[event.index] = ""
        elif event.type == "content_block_delta" and event.delta.type == "input_json_delta":
            buffers[event.index] += event.delta.partial_json
        elif event.type == "content_block_stop" and event.index in starts:
            block = starts[event.index]
            calls.append({"id": block.id, "name": block.name, "input": json.loads(buffers[event.index] or "{}")})
    return calls

Write latency(timed_events). It receives a list of (seconds, event) pairs, where seconds is the arrival time measured from when the request was sent. Return a tuple (ttft, total): ttft is the time of the first text_delta (or None if there is no text at all), and total is the time of the last event (0.0 for an empty list).

Hint

Loop over the pairs. Set ttft the first time you see a content_block_delta whose delta.type is "text_delta"; update total on every pair.

Show solution 
def latency(timed_events):
    ttft = None
    total = 0.0
    for seconds, event in timed_events:
        if ttft is None and event.type == "content_block_delta" and event.delta.type == "text_delta":
            ttft = seconds
        total = seconds
    return ttft, total

Write stream_turn(client, history, user_text, on_text) for a streaming chat program. It must:

  1. append {"role": "user", "content": user_text} to history (mutate the list you are given);
  2. stream a reply with model=al.MODEL, max_tokens=1024 and the whole history, calling on_text(piece) for every text piece;
  3. append the assistant turn using the final message's content blocks;
  4. return the final message.
Hint

Append the user message first, then open client.messages.stream(..., messages=history). Loop over text_stream calling on_text, then call stream.get_final_message() before leaving the with block.

Show solution 
import agentlab as al

def stream_turn(client, history, user_text, on_text):
    history.append({"role": "user", "content": user_text})
    with client.messages.stream(model=al.MODEL, max_tokens=1024, messages=history) as stream:
        for piece in stream.text_stream:
            on_text(piece)
        final = stream.get_final_message()
    history.append({"role": "assistant", "content": final.content})
    return final

Structure

  • make_client(): try al.get_client(); on al.LiveModelUnavailableError return a MockClient with a responder= function that echoes the user's last message.
  • stream_turn(client, history, user_text, on_text, clock=time.perf_counter): your exercise m04-e6 solution, extended to return a small stats dict (ttft, total, output_tokens, stop_reason). Taking clock as a parameter lets tests pass a fake clock.
  • main(): a loop that reads a line, streams the answer to the terminal, then logs one structured event per turn with structlog (for example log.info("turn", ttft=..., total=..., output_tokens=...)). Structured logs give you machine-readable numbers you can aggregate later, which a print line does not.
  • Answers appear piece by piece, with flush=True, and no stray newlines between pieces
  • The history list holds every turn and the assistant turns store final.content
  • TTFT is measured at the first text piece, total at the end of the stream
  • A max_tokens stop prints a visible "(answer truncated)" note
  • The program runs offline with the mock fallback and online with a real key, with no code changes
  • A test file checks stream_turn with a MockClient and a fake clock
  • No API key appears anywhere in the code; it comes from the environment

Quiz

Recap

  • Streaming delivers a response as server-sent events while it is generated. It cuts time to first token; it does not change total time, tokens, cost, or the final answer.
  • with client.messages.stream(...) as stream: takes the same arguments as create. stream.text_stream yields text pieces; print them with end="" and flush=True.
  • Events: message_start, then per block content_block_start / content_block_delta (text_delta or input_json_delta) / content_block_stop, then message_delta (stop reason, output tokens) and message_stop.
  • Accumulate by index. get_final_message() does it for you and returns the same Message create would.

  • create(stream=True) returns raw events with no helpers; prefer messages.stream unless you need the raw events.
