One Tool Call by Hand

In M07 you described tools to the model. Now you will complete one tool call from start to finish, slowly, by hand: read the model's request, run the Python function yourself, and send the result back so the model can answer. Every agent ever built repeats exactly this round trip, so it pays to know each step and each way it can break.

⏱ ~1.5 hoursPrerequisites: M02 The Messages API, M07 Tools as Contracts
  • Describe the five moves of a tool round trip and which side (your code or the model) performs each one
  • Read a tool_use block's id, name, and input from a response, even when text comes first
  • Dispatch a tool call to a Python function through a name-to-function registry
  • Build a correct tool_result block whose tool_use_id matches the call
  • Send the assistant turn and the result back, and read the final answer
  • Recognize the exact BadRequestError produced by each pairing mistake, and fix it

The round trip in five moves

A tool, as you saw in M07, is a contract: a name, a description, and an input schema. The model never runs your code. It can only ask you to run a tool by writing a special content block called tool_use. Your program does the work and replies with a tool_result block. The model then continues with that result in front of it.

One complete exchange, which we will call a round trip, has five moves:

  1. Offer the tools. Your code sends the user's question and the tool definitions.
  2. Read the request. The model replies with stop_reason="tool_use" and a tool_use block: an id, the tool name, and an input dict.
  3. Run the tool. Your code looks up the Python function by name and calls it with the input.
  4. Wrap the result. Your code builds a tool_result block that repeats the same id as tool_use_id.
  5. Send it back. Your code appends the model's turn and the result to the history and calls the API again. This time the model answers in text and stops with end_turn.
sequenceDiagram
    participant C as Your code
    participant M as Model (API)
    participant T as Python function
    C->>M: 1. messages + tools
    M-->>C: 2. tool_use (id, name, input), stop_reason=tool_use
    C->>T: 3. get_weather(city="Paris")
    T-->>C: "18°C, light rain"
    Note over C: 4. tool_result with tool_use_id = id
    C->>M: 5. history + assistant turn + tool_result
    M-->>C: text answer, stop_reason=end_turn

Notice that there are two API requests, not one. The first ends with the model asking for something. The second carries the answer to that ask. Because the API is stateless (it remembers nothing between requests, as you learned in M02), the second request must re-send everything: the question, the model's tool request, and your result.

Remember: the model asks, your code acts. A tool round trip is two requests: one that ends in tool_use, and one that carries the tool_result and ends in end_turn.

Move 1: offer the tools

We will use one tool throughout this module: get_weather. Its definition follows the M07 rules: a clear name, a description that says what it returns and when to use it, and an object schema.

TOOLS = [{
    "name": "get_weather",
    "description": (
        "Get the current weather for one city. Returns temperature in Celsius and conditions. "
        "Use it whenever the user asks about current weather; do not guess."
    ),
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string", "description": "City name, e.g. 'Paris'"}},
        "required": ["city"],
    },
}]

You pass the list as tools= on messages.create. Everything else is the request you already know: model, max_tokens, and messages. In this course the model is agentlab's MockClient, which follows a script: a list of responses, one per request. Here the script says "first ask for the weather in Paris, then answer".

The response has stop_reason="tool_use". That value is the model's way of saying "I am not done; I paused because I want a tool run." The content holds one ToolUseBlock. Nothing has been executed. If you stopped here and printed the text, you would print nothing at all, which is the most common first bug in tool code: treating a tool_use response as a final answer.

The mock fills in ids like toolu_mock_0001. The real API uses ids like toolu_01A2b3.... Never invent or predict ids; always copy the one the model gave you.

Remember: check stop_reason before reading content. "tool_use" means "run something and come back", not "here is my answer".

Move 2: read the tool_use block

A tool_use block has exactly the three fields you need:

FieldExampleWhat you do with it
id"toolu_mock_0001"Copy it into your tool_result as tool_use_id. It is how the API pairs a result with its request.
name"get_weather"Choose which Python function to call.
input{"city": "Paris"}Pass as keyword arguments. It is already a parsed dict, not a JSON string.

The tool_use block is not always the first block. The model may write a sentence before the call ("Let me check the weather."). So never write response.content[0].input. Instead, select blocks by their type:

tool_uses = [block for block in response.content if block.type == "tool_use"]

Predict what this cell prints before you run it. The script puts text before the call.

Two blocks: a text block and then the tool_use block. Code that read content[0].input would crash with AttributeError, because text blocks have no input.

Three more facts about input:

  • It is a dict. Do not call json.loads on it. The SDK has already parsed the JSON the model wrote. Do not do string matching on serialized input either; work with the dict.
  • It follows your schema, usually. With "strict": True (M07) the API guarantees it validates. Without strict, a field may occasionally be missing or the wrong type. Validating input before running a tool is part of M10.
  • It is model-written data. Treat it like any untrusted input: a path argument could point anywhere. Your tool decides what is allowed.

Remember: find tool calls by block.type == "tool_use", never by position. Keep the id; use name to pick a function; pass input as keyword arguments.

Move 3: run the function yourself

The model gave you a name. You need a function. The simplest correct mapping is a dict from tool name to Python callable, called a registry:

def get_weather(city: str) -> str:
    return {"Paris": "18°C, light rain", "Oslo": "4°C, cloudy"}.get(city, f"No data for {city}")

REGISTRY = {"get_weather": get_weather}

Running the tool is then a lookup and a call. Turning the tool name into a function call is called dispatch:

func = REGISTRY[block.name]
output = func(**block.input)        # get_weather(city="Paris")

Why a dict instead of if statements, or globals()[block.name]?

  • An explicit allow-list. Only functions you put in the registry can ever run. Looking a name up in globals() would let the model call any function in your module, including ones you never meant to expose. The registry is a security boundary, not just a convenience.
  • One place to change. Adding a tool means adding one definition and one registry entry. The dispatch code never changes.
  • The schema matches the signature. Because the input schema's property names are the function's parameter names, func(**block.input) just works. If you generated the schema from the signature (M07), they cannot drift apart.

Tool results go back to the model as text, so convert whatever your function returns into a string. Plain strings pass through; anything structured (a dict, a list, a number) becomes JSON with json.dumps, which the model reads well.

Two things can go wrong here, and both belong to M10: the model can name a tool that is not in the registry (KeyError), and the tool itself can raise. In M10 you will turn both into a tool_result with is_error: true so the model can recover. For now, just know that the function runs in your process, with your files, your network, and your credentials. The model chose the arguments; you are responsible for what the call does.

Never eval or exec anything from block.input, and never look tool names up in globals(). A registry dict is the allow-list.

Remember: registry[block.name](**block.input), then make the output a string (json.dumps for structured data).

Move 4: build the tool_result block

A tool_result is a content block you write in a user message. It has three required keys:

{
    "type": "tool_result",
    "tool_use_id": "toolu_mock_0001",   # copied from block.id, character for character
    "content": "18°C, light rain",      # what the tool returned, as text
}
  • type is always the string "tool_result".
  • tool_use_id is the id of the tool_use block it answers. Not the tool name, not a counter you keep: the exact id.
  • content is the result. A string is simplest. It may also be a list of content blocks such as [{"type": "text", "text": "..."}], which you will see when a tool returns several pieces.

There is one optional key you will meet in M10: "is_error": True, which tells the model the tool failed and the content is an error message.

Why does the id matter so much? Because a single response can contain several tool_use blocks (parallel tool calls, the subject of M09). The id is the only thing that says which result belongs to which call. The API therefore checks the pairing strictly, and refuses requests where it does not line up.

al.format_block renders one block on one line, the same way al.format_transcript shows it inside a whole conversation. The id in square brackets is the pairing key; when you debug, line the brackets up.

Remember: a tool_result is {"type": "tool_result", "tool_use_id": block.id, "content": text}, placed in a user message.

Move 5: send the turn and the result back

The second request needs the history in exactly this shape:

  1. the original user message (the question);
  2. an assistant message whose content is response.content: the model's whole turn, including the tool_use block;
  3. a new user message whose content is a list starting with the tool_result block(s).

The second item is the one people get wrong. You must append the content blocks, not just the text. The API checks that each tool_result answers a tool_use in the previous assistant message. If that message does not contain the tool_use block, the result answers nothing.

Read the transcript printed at the end. It is the conversation exactly as the model saw it on the second request, plus the final response:

user: What's the weather in Paris?
assistant: tool_use get_weather {"city": "Paris"} [toolu_mock_0001]
user: tool_result [toolu_mock_0001] 18°C, light rain
assistant: It's 18°C with light rain in Paris, so take an umbrella.
(stop_reason=end_turn)

The id in brackets appears twice, once on the call and once on the result. That is a correctly paired round trip. A few details worth noticing:

  • Send tools again on the second request. The API is stateless; the tool definitions are part of every request. The conversation contains tool_use blocks, and the model may want to call a tool again.
  • The final text is collected from text blocks. The pattern "".join(b.text for b in final.content if b.type == "text") works with both the mock and the real SDK. The mock also has a .text convenience property, but the real SDK's Message does not, so code you want to port should not rely on it.
  • Appending response.content works directly. Both the mock and the real SDK accept the block objects back in messages; you do not have to convert them to dicts.

You can also look at exactly what was sent. client.requests records every request the mock accepted, with blocks converted to plain dicts. Exercise tests use it to check your work.

Remember: history for request 2 is [question, {"role": "assistant", "content": response.content}, {"role": "user", "content": [tool_result]}], sent with the same tools.

When pairing goes wrong: the exact errors

The API validates the shape of every request before the model sees it. A request whose tool calls and results do not line up is rejected with HTTP 400, raised in Python as BadRequestError. A 400 means your request is wrong: retrying the same request will fail again, every time. You fix the code, not the network. (Which errors are worth retrying is in M10.)

The good news: the messages are specific. Each names the position of the bad message (messages.2 is the third message, counting from zero) and what is wrong. Learn to recognize these four, because you will see them while building every agent.

Each cell below starts from the same first request, then builds a broken second request. They use a small helper, start(), that performs Move 1 and returns the pieces.

Mistake 1: no tool_result after a tool_use

You append the model's turn correctly, but then send a plain text follow-up instead of the result. Perhaps you forgot to run the tool, or you assumed the model already had the answer.

400 messages.2: tool_use ids were found without tool_result blocks immediately after: toolu_mock_0001. Each tool_use block must have a corresponding tool_result block in the next message.

Read it as: the message at index 2 should have answered toolu_mock_0001, and it did not. Every tool_use needs its tool_result in the very next message. "Immediately after" is literal: you cannot put another exchange in between and answer later.

Mistake 2: the wrong tool_use_id

You send a result, but with an id that is not the one the model gave: a hard-coded example id copied from documentation, the tool's name, or an id from an earlier turn.

400 messages.2: tool_use ids were found without tool_result blocks immediately after: toolu_mock_0001. Each tool_use block must have a corresponding tool_result block in the next message.

Read it as: the same error as Mistake 1, and that is the clue. From the API's point of view, a result with the wrong id does not exist; toolu_mock_0001 is still unanswered. When you see this error even though you did send a result, compare the ids character by character. The fix is always "tool_use_id": block.id.

Mistake 3: text before the tool_result

You want to add an instruction along with the result, and you put the text first.

400 messages.2: tool_result blocks must come before any other content
after the fix: end_turn

Read it as: in the user message that answers tool calls, the tool_result blocks come first. Text after them is allowed, and is the right place for an extra instruction.

Mistake 4: appending only the text instead of response.content

This is the most common one, because it works perfectly in a plain chat (M02) and only breaks once tools appear. You store the assistant turn as its text, dropping the tool_use block.

400 messages.2: tool_result blocks must answer tool_use blocks in the previous assistant message

Read it as: the result is fine, but the assistant message before it has no tool_use to answer. The transcript makes it visible: the assistant line says Let me check. with no tool_use line under it. When the model writes no text before a call, the same mistake fails differently: the text is an empty string, and the API rejects empty text with messages.1.content: text content must be non-empty. Both have one fix: {"role": "assistant", "content": response.content}.

Two related slips

  • Sending the result without the assistant turn at all. The history goes question → tool_result. The error is messages.1: tool_result blocks must answer tool_use blocks in the previous assistant message.
  • Appending the assistant turn and calling again with nothing after it. The last message is then an assistant message, which the API reads as prefill (asking the model to continue your text), and prefill is not supported on current models: messages: the final message must not be an assistant message; prefilling the assistant response is not supported on this model.
Error text (start)Likely causeFix
tool_use ids were found without tool_result blocks immediately after: <id>No result sent, or the result's id is wrongSend a tool_result for every call with tool_use_id=block.id
tool_result blocks must come before any other contentText placed before the resultsResults first, text after
tool_result blocks must answer tool_use blocks in the previous assistant messageAssistant turn stored as text, or missingAppend response.content as the assistant turn
text content must be non-emptyStored the (empty) text of a tool-only turnAppend response.content

When an agent fails with one of these, do not stare at the code first. Print al.format_transcript(messages) just before the failing call and read the ids in brackets. Pairing bugs are visible in the transcript in seconds and nearly invisible in the code.

Remember: pairing errors are 400s; never retry them. The rule behind all of them: the assistant turn holds the tool_use blocks, and the very next user message starts with one tool_result per call, each carrying the matching id.

The same round trip against the real API

Everything you wrote above runs unchanged against Claude. The only change is the line that creates the client: anthropic.Anthropic() instead of al.MockClient([...]). The real model decides for itself whether to call the tool, so there is no script.

import anthropic

client = anthropic.Anthropic()   # reads ANTHROPIC_API_KEY (or an `ant auth login` profile) from the environment

TOOLS = [{
    "name": "get_weather",
    "description": "Get the current weather for one city. Returns temperature and conditions.",
    "input_schema": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
}]
REGISTRY = {"get_weather": lambda city: f"18°C, light rain in {city}"}

messages = [{"role": "user", "content": "What's the weather in Paris?"}]
response = client.messages.create(model="claude-opus-5-5", max_tokens=1024, tools=TOOLS, messages=messages)

if response.stop_reason == "tool_use":
    messages.append({"role": "assistant", "content": response.content})
    results = []
    for block in response.content:
        if block.type == "tool_use":
            output = REGISTRY[block.name](**block.input)
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})
    messages.append({"role": "user", "content": results})
    response = client.messages.create(model="claude-opus-5-5", max_tokens=1024, tools=TOOLS, messages=messages)

print("".join(b.text for b in response.content if b.type == "text"))
pixi add anthropic
pixi run python round_trip.py

Notice the small generalization: the loop over response.content answers every tool_use block, not just the first, and puts all results in one user message. The real model may ask for two cities at once; that is M09's subject, and this code already handles it. Also notice that it does exactly one round trip. If the model wanted a second tool after seeing the first result, this script would print an empty answer. Fixing that properly is what turns this script into an agent loop.

Never paste an API key into code, a notebook, or a lesson cell. The client reads it from the environment. See M00 for key hygiene.

Remember: the mock and the SDK share one surface. Code that uses block.type, block.id, block.name, block.input, and appends response.content ports without edits.

Practice

Four exercises, from a single block to a full round trip and a debugging task. Tests build their own MockClient scripts and inspect client.requests, so your functions must take the client as an argument rather than creating one.

Write build_tool_result(tool_use_id, output) that returns a tool_result dict with exactly the keys type, tool_use_id, and content.

  • If output is a string, use it as the content unchanged.
  • Otherwise (dict, list, number, bool, None), use json.dumps(output).
Hint

Use isinstance(output, str) to decide, and a conditional expression for the content. Return a dict literal.

Show solution
import json

def build_tool_result(tool_use_id, output):
    content = output if isinstance(output, str) else json.dumps(output)
    return {"type": "tool_result", "tool_use_id": tool_use_id, "content": content}

Write dispatch(name, tool_input, registry):

  • Look up name in the registry dict and call the function with tool_input as keyword arguments.
  • Return the output as a string: strings unchanged, anything else through json.dumps.
  • If name is not in the registry, raise ValueError with a message containing unknown tool and the name. (M10 will turn this into an error result instead.)
Hint

Check if name not in registry first and raise. Then output = registry[name](**tool_input), and convert as in the previous exercise.

Show solution
import json

def dispatch(name, tool_input, registry):
    if name not in registry:
        raise ValueError(f"unknown tool: {name}")
    output = registry[name](**tool_input)
    return output if isinstance(output, str) else json.dumps(output)

Write answer_with_tools(client, question, tools, registry) that performs at most one round trip and returns the final answer text.

  1. Send question as the first user message, with model=al.MODEL, max_tokens=1024, and tools=tools.
  2. If stop_reason is not "tool_use", return the response's text (join every text block). Only one request is made.
  3. Otherwise run every tool_use block through the registry, append the assistant turn (response.content) and one user message holding all the results, make the second request, and return its text.

You may reuse ideas from the previous exercises; define any helpers you need in this cell.

Hint

Write a tiny text_of(response) helper that joins b.text for blocks whose type == "text". For the tool branch, build a results list in a loop over response.content, then append two messages and call create again with the same arguments.

Show solution
import json
import agentlab as al

def text_of(response):
    return "".join(b.text for b in response.content if b.type == "text")

def answer_with_tools(client, question, tools, registry):
    messages = [{"role": "user", "content": question}]
    response = client.messages.create(model=al.MODEL, max_tokens=1024, tools=tools, messages=messages)
    if response.stop_reason != "tool_use":
        return text_of(response)
    results = []
    for block in response.content:
        if block.type == "tool_use":
            output = registry[block.name](**block.input)
            content = output if isinstance(output, str) else json.dumps(output)
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": content})
    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content": results})
    final = client.messages.create(model=al.MODEL, max_tokens=1024, tools=tools, messages=messages)
    return text_of(final)

Hint

In the transcript: the assistant line has no tool_use (so the turn was stored as text); the text line comes before the result; and the bracketed id is a tool name. Each maps to one line of code.

Show solution
import agentlab as al

TOOLS = [{"name": "get_weather", "description": "Weather for a city.",
          "input_schema": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}}]

def get_weather(city):
    return {"Oslo": "4°C, cloudy"}.get(city, "unknown")

def ask_weather(client):
    messages = [{"role": "user", "content": "What's the weather in Oslo?"}]
    response = client.messages.create(model=al.MODEL, max_tokens=1024, tools=TOOLS, messages=messages)
    block = next(b for b in response.content if b.type == "tool_use")
    output = get_weather(**block.input)
    messages.append({"role": "assistant", "content": response.content})          # fix 1
    messages.append({"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": block.id, "content": output},      # fix 3
        {"type": "text", "text": "Answer in one sentence."},                      # fix 2: text after
    ]})
    final = client.messages.create(model=al.MODEL, max_tokens=1024, tools=TOOLS, messages=messages)
    return "".join(b.text for b in final.content if b.type == "text")

Mini-project: a one-shot tool CLI

Mini-projectclock.py: ask what time it is anywhere

Build a small command-line program that answers questions like "What time is it in Tokyo?" with exactly one tool round trip. The tool is real: it uses the standard library's zoneinfo to read the clock, so the model cannot know the answer without calling it.

mkdir clock && cd clock
pixi init
pixi add python=3.14 anthropic structlog
# write clock.py, then:
pixi run python clock.py "What time is it in Tokyo?"

What to build

  • A tool get_time(timezone: str) -> str that returns the current local time for an IANA timezone name such as "Asia/Tokyo", using datetime.now(ZoneInfo(timezone)).
  • A TOOLS definition whose description tells the model to pass an IANA name (and gives an example), and a REGISTRY dict.
  • A function ask(client, question) -> str that does one round trip, built from your build_tool_result and dispatch from the exercises.
  • A client chooser: try al.get_client() (the real API, if anthropic is installed and a key is in the environment); if it raises al.LiveModelUnavailableError, fall back to an al.MockClient scripted to call get_time with "Asia/Tokyo".
  • Structured logging with structlog: log one event per tool call with the tool name, input, and tool_use_id. Logs, not prints, because later you will want to search and filter what your agent did; key=value lines are easy to grep and to ship to a log store.
  • The program runs with pixi run python clock.py "..." and prints one answer
  • Without the real API available, the mock fallback runs the same ask function end to end
  • Every request uses model="claude-opus-5-5" (or al.MODEL) and an explicit max_tokens
  • The assistant turn is appended as response.content, and every tool_result uses block.id
  • Tools are looked up only through the registry dict
  • One structlog event per tool call includes tool, input, and tool_use_id
  • No API key appears anywhere in the code or the repository

Stretch goals: print al.format_transcript(messages, final) when a --debug flag is given; make the tool return JSON with both the time and the UTC offset; ask "What time is it in Tokyo and in Lima?" against the real API and see whether your code handles two tool_use blocks in one response.
