What an LLM Call Is

Before you can build an agent you need an accurate picture of the single call at its center: what the model does with your text, what it costs, how much it can read, how long it takes, and why the same request can come back different. Every design decision in later modules rests on these numbers.

Next-token prediction, in one picture

A language model does one thing: given a sequence of text, it produces a probability for every possible next piece of text. To write an answer, the system picks one piece according to those probabilities, appends it to the sequence, and asks again. It repeats until the model produces a special "end of turn" marker or hits a length limit. This is called autoregressive generation: each step's output becomes part of the next step's input.

flowchart LR
  A["Your request text"] --> M["Model: probabilities for the next token"]
  M --> P["Pick one token"]
  P --> Q{"End of turn or limit?"}
  Q -- no --> AP["Append token to the sequence"] --> M
  Q -- yes --> R(["Response"])

You do not need the mathematics to build agents, but this picture explains four facts you will meet constantly:

  • Output is produced one piece at a time, so long answers take longer than short ones. That is why output length dominates latency and why streaming (M04) exists.
  • Every step reads the whole sequence, so everything in the request (instructions, history, tool definitions) influences every word of the answer.
  • Picking is probabilistic, so the same request can produce different answers.
  • The model has no memory between calls. It sees only what is in the request. Conversation "memory" is history you send again each time (M02).

Here is a toy version you can run. It "predicts" the next word from a hand-written table of probabilities. A real model computes these probabilities from billions of learned parameters, over a vocabulary of tens of thousands of pieces, but the loop is the same shape.

Run it a few times with different seeds, and set max_words=3. Notice the two ways generation ends: the model chooses to stop ("end_turn"), or it runs into your limit ("max_tokens") and the answer is cut off mid-thought. The real API reports exactly these two reasons in stop_reason; M03 covers them and the others.

Common misconception: "the model looks up the answer". It does not retrieve stored documents; it generates plausible continuations. When it needs facts it does not reliably have, the fix is to put those facts in the request, or give it a tool to fetch them. That is the whole reason agents exist.

Remember: generation is a loop of "predict a distribution, pick a token, append". Length costs time, everything in the request matters, and picks vary.

Tokens

The pieces the model reads and writes are tokens, not characters or words. A tokenizer splits text into tokens from a fixed vocabulary: common words are often one token, rarer words split into several, and punctuation and spaces are folded in. Tokens matter for three reasons: you pay per token, limits are measured in tokens (both the context window and max_tokens), and latency grows with output tokens.

For English prose, a useful rule of thumb is about four characters per token, or roughly three-quarters of a word. al.estimate_tokens(text) applies exactly that rule: ceil(len(text) / 4). It is an estimate for reasoning about orders of magnitude; real tokenizers differ by model.

Things that usually cost more tokens per character than English prose: source code and JSON (lots of punctuation and indentation), long numbers and identifiers, unusual words, and many non-English languages. When the number matters (a budget, a limit, a bill), measure it with count_tokens instead of estimating (see below).

Type into the meter to see how text breaks into chunks, what share of the context window it uses, and what it would cost as input across many requests. Switch models to compare prices.

Think: a 60-token system prompt seems free. In an agent that sends it on every one of 10,000 daily requests, it is 600,000 input tokens a day. Change the meter's request count to see what that costs on each model. Small, repeated text adds up; this is why later stages care about prompt length and caching.

Remember: a token is roughly four characters of English. Code, JSON, numbers, and other languages usually cost more. Estimate to reason, count to decide.

The context window

The context window is the maximum amount of text the model can work with in one request, measured in tokens. For the current Claude models it is 1M (one million) tokens. Everything you send counts toward it: the system prompt, the tool definitions, and every message in the conversation. The output the model writes in that turn has to fit too, and max_tokens (at most 128K on these models) caps it.

A million tokens is roughly 4 million characters of English, several long novels. A single question will never come close. The window matters because of how agents and chats work: the API is stateless, so each request carries the whole history again. Every turn adds the previous answer and the new question, so the request grows, and you pay for the entire history on every call.

Each request's input grows linearly with the number of turns, so the total billed across the conversation grows roughly with the square of the turns. Five turns of a short chat bill about 1,800 input tokens; an agent that reads documents with tools can add tens of thousands of tokens per step. al.estimate_request_tokens(messages, system=..., tools=...) estimates a whole request: it serializes tools and message content, applies the four-characters rule, and adds a few tokens per message for structure.

Budgeting a window

To budget, add up what you will send and what you will allow the model to write:

needed = estimate_request_tokens(messages, system=SYSTEM, tools=TOOLS) + max_tokens
if needed > 1_000_000:
    ...  # trim or summarize history before sending

Long before you hit the hard limit, a big request costs more and takes longer, and burying the important part in a pile of irrelevant text makes it harder for the model to focus on. Treat the window as a budget to spend deliberately, not a bucket to fill. Strategies for managing long histories (trimming, summarizing, memory) are Stage 3 material on the roadmap; exercise 3 below has you write the simplest one.

Common mistake: forgetting tool definitions. Tool schemas and descriptions are sent on every request and count as input tokens. An agent with twenty detailed tools can spend thousands of tokens per call before the conversation even starts.

Remember: window = system + tools + all messages + this turn's output, up to 1M tokens. History is re-sent every turn, so input cost grows as a conversation runs.

Counting tokens exactly: count_tokens and usage

Two sources give you real numbers instead of estimates.

Before sending, client.messages.count_tokens(...) takes the same model, messages, system, and tools you would send to create, and returns an object whose input_tokens is what that request would read. It generates nothing. Use it to check a budget or to decide whether to trim history.

After sending, every response carries usage: input_tokens (what the request read) and output_tokens (what the model wrote). These are the numbers you are billed for. The usage object also has cache_creation_input_tokens and cache_read_input_tokens, which stay zero unless you use prompt caching, a later topic.

One short tool definition more than tripled the input. In the mock, both numbers are estimates computed with the four-characters rule, so they agree with each other exactly. Against the real API, count_tokens and usage come from the model's real tokenizer. The call looks the same:

import anthropic

client = anthropic.Anthropic()
count = client.messages.count_tokens(
    model="claude-opus-5-5",
    system=SYSTEM,
    tools=TOOLS,
    messages=messages,
)
print(count.input_tokens)

As always, the only change from the mock is the line that creates client.

Remember: count_tokens before a call for planning, response.usage after a call for accounting. Log usage on every request in anything you ship; it is the raw material for cost budgets in M11.

Why output varies

Because each token is picked from a probability distribution, two runs of the same request can take different paths. Once one early token differs, everything after it is conditioned on a different sequence, so small differences grow. Ask the same question twice and you may get the same facts in different words, a different structure, or occasionally a different conclusion.

Older APIs exposed sampling knobs such as temperature to make output more or less random. On the current models and API versions those parameters (temperature, top_p, top_k) are rejected with a 400 error. You steer behavior with the prompt and with output_config={"effort": ...} instead; M03 explains effort. For a fixed format, use structured output (M05), not randomness controls.

The mock can demonstrate variation on purpose. al.one_of("a", "b", ...) is a script step that picks one of its answers using the client's seeded random generator. A seed fixes the sequence of random choices, so a run is reproducible: same seed, same picks. responder= answers every request once the script is empty.

The identical request returns different answers within one run, while re-running with the same seed reproduces the sequence. The real API has no seed: its variation is genuine. That has direct consequences for how you build and test:

  • Test properties, not exact strings. Check that the answer parses, mentions the required fields, or stays under a length, rather than comparing it to one fixed sentence.
  • Use a mock for unit tests. Your code should be deterministic given a model response; script the responses (including the awkward ones) and test the code. That is how every exercise in this course works.
  • Measure the model with many samples. One good answer proves little. Evaluation, running a prompt many times and scoring the results, is Stage 5 on the roadmap.

Common mistake: "fixing" variation by adding temperature=0. On current models the request fails outright. Tighten the prompt, add examples, or demand a schema instead.

Remember: output varies because tokens are sampled. Sampling knobs are gone; steer with prompts, effort, and schemas, and test code with scripted responses.

What a call costs

You pay per token, at separate rates for input and output. Prices are quoted in US dollars per million tokens (MTok):

ModelModel idInput / MTokOutput / MTok
Claude Opus 5.5claude-opus-5-5$4.00$20.00
Claude Sonnet 5.5claude-sonnet-5-5$2.00$10.00
Claude Haiku 5.5claude-haiku-5-5$0.10$0.50

The formula is the same for every request:

cost = input_tokens / 1_000_000 * input_price + output_tokens / 1_000_000 * output_price

Two patterns follow from the table. First, output costs five times as much as input on every model, so a verbose answer costs more than a long question. Second, in an agent the opposite is usually true of the bill: because the whole history is re-sent at every step, input tokens pile up much faster than output tokens, and input often dominates the total.

A single request costs about two cents on Opus and well under a cent on Sonnet or Haiku. The eight-step run reads about 100,000 input tokens to produce 2,400 output tokens, and more than 85% of its cost is input. Multiply by thousands of runs a day and the choice of model, the length of tool results, and the size of the history become real money.

Choosing a model: claude-opus-5-5 is the default in this course and the most capable. claude-sonnet-5-5 costs half as much, and claude-haiku-5-5 costs 40 times less than Opus for input. A common production pattern is to use a smaller model for simple, high-volume steps (classifying, routing, extracting) and the larger model where quality matters most. Use model ids exactly as shown; there are no date suffixes.

Remember: cost = input tokens × input price + output tokens × output price, per million. Output is 5× input per token, but agents re-send history, so input usually dominates a run.

What makes a call slow

Latency is the time from sending a request to having the response. Thinking in terms of next-token prediction tells you where the time goes:

Output tokens

The biggest driver. Tokens are generated one after another, so time grows with the length of the answer. Asking for concise output is the most effective speed-up you have.

Input tokens

The model must read the whole request before writing the first token. Reading is much faster per token than writing, but a very large context still adds noticeable time.

Effort and thinking

Higher effort lets the model reason more before and while answering, which can produce more output tokens and take longer. Lower effort is faster for simple tasks.

Model size

Smaller models generally respond faster. Haiku-class models suit latency-sensitive steps.

Round trips

An agent makes one request per step. Ten steps means ten full calls in sequence; fewer, better tools mean fewer round trips (M12).

Network and retries

Connection time, rate limits, and retries after errors add time outside the model (M10).

Two different numbers matter. Time to first token is how long until the model starts writing; total time is how long until it finishes. Without streaming, your user waits for the total. With streaming (M04), text appears as it is generated, so perceived latency drops to time to first token. Very long outputs (large max_tokens values) need streaming anyway, to avoid request timeouts.

Think: a request has 50,000 input tokens and produces 1,000 output tokens. Another has 2,000 input tokens and produces 4,000 output tokens. Which is likely slower, and which is more expensive on Opus? (The second is likely slower: four times the generated tokens. The first costs more: $0.20 + $0.02 = $0.22 versus $0.008 + $0.08 = $0.088.) Cost and latency are driven by different tokens.

Remember: output length drives latency; input length drives most of an agent's cost. Shorter answers, lower effort for easy tasks, smaller models, fewer steps, and streaming are your levers.

Practice

These exercises use the published prices and agentlab's token estimates. Each one is a small, reusable function you would actually keep in an agent project.

Write cost_usd(usage, model="claude-opus-5-5") that returns the dollar cost of one response from its usage.input_tokens and usage.output_tokens, using the prices per million tokens: Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 5.5 $0.10/$0.50. Raise ValueError for an unknown model id. Do not round.

Hint

Look the model up in PRICES (raise ValueError if it is missing), then compute input_tokens / 1_000_000 * input_price + output_tokens / 1_000_000 * output_price.

Show solution 
import agentlab as al

PRICES = {
    "claude-opus-5-5": (4.00, 20.00),
    "claude-sonnet-5-5": (2.00, 10.00),
    "claude-haiku-5-5": (0.10, 0.50),
}

def cost_usd(usage, model="claude-opus-5-5"):
    if model not in PRICES:
        raise ValueError(f"unknown model: {model}")
    input_price, output_price = PRICES[model]
    return usage.input_tokens / 1_000_000 * input_price + usage.output_tokens / 1_000_000 * output_price

Write estimate_cost(prompt, expected_output_tokens, model="claude-opus-5-5", calls=1) that estimates the total dollars for sending prompt calls times, using al.estimate_tokens(prompt) for input tokens and expected_output_tokens for output tokens per call. Use the same prices as exercise 1 (define them again here; each exercise runs on its own).

Hint

Per call: al.estimate_tokens(prompt) * input_price / 1e6 + expected_output_tokens * output_price / 1e6. Multiply by calls.

Show solution 
import agentlab as al

PRICES = {
    "claude-opus-5-5": (4.00, 20.00),
    "claude-sonnet-5-5": (2.00, 10.00),
    "claude-haiku-5-5": (0.10, 0.50),
}

def estimate_cost(prompt, expected_output_tokens, model="claude-opus-5-5", calls=1):
    input_price, output_price = PRICES[model]
    per_call = al.estimate_tokens(prompt) / 1e6 * input_price + expected_output_tokens / 1e6 * output_price
    return per_call * calls

A chat history alternates user and assistant messages and ends with a user message. Write trim_history(messages, budget) that returns a new list with the oldest messages removed, two at a time (one user, one assistant), until al.estimate_request_tokens(result) is at most budget. Never remove the final message, even if it alone is over budget. Do not modify the input list. Because you remove pairs, the result still starts with a user message.

Hint

Copy the list, then loop: while len(result) > 1 and al.estimate_request_tokens(result) > budget: result = result[2:].

Show solution 
import agentlab as al

def trim_history(messages, budget):
    result = list(messages)
    while len(result) > 1 and al.estimate_request_tokens(result) > budget:
        result = result[2:]
    return result

Write sample_answers(client, prompt, n) that sends the same single-message request n times (a fresh one-message conversation each time, not a growing history) and returns a dict mapping each distinct answer text to how many times it appeared. Use model=al.MODEL and any max_tokens. The tests use al.one_of to make the mock vary.

Hint

Loop n times, build the messages list inside the loop, and update a dict with counts[text] = counts.get(text, 0) + 1 (or use collections.Counter and convert it with dict(...)).

Show solution 
import agentlab as al

def sample_answers(client, prompt, n):
    counts = {}
    for _ in range(n):
        response = client.messages.create(
            model=al.MODEL,
            max_tokens=100,
            messages=[{"role": "user", "content": prompt}],
        )
        text = response.content[0].text
        counts[text] = counts.get(text, 0) + 1
    return counts

Write usage_report(client, questions, model="claude-opus-5-5") that asks each question as its own single-message request with the given model, and returns a dict with the totals across all responses: "requests", "input_tokens", "output_tokens", and "cost_usd" (at the published prices, unrounded). Read the numbers from each response.usage; do not estimate them yourself.

Hint

Keep running totals of response.usage.input_tokens and response.usage.output_tokens inside the loop, then apply the prices once at the end.

Show solution 
import agentlab as al

PRICES = {
    "claude-opus-5-5": (4.00, 20.00),
    "claude-sonnet-5-5": (2.00, 10.00),
    "claude-haiku-5-5": (0.10, 0.50),
}

def usage_report(client, questions, model="claude-opus-5-5"):
    input_tokens = output_tokens = 0
    for question in questions:
        response = client.messages.create(
            model=model,
            max_tokens=500,
            messages=[{"role": "user", "content": question}],
        )
        input_tokens += response.usage.input_tokens
        output_tokens += response.usage.output_tokens
    input_price, output_price = PRICES[model]
    return {
        "requests": len(questions),
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "cost_usd": input_tokens / 1e6 * input_price + output_tokens / 1e6 * output_price,
    }

Mini-project: a prompt cost meter

Mini-projectcostmeter: tokens and dollars for a prompt file

Build a small command-line tool that reads a prompt from a text file and reports its token count, its share of the context window, and its estimated cost per request and per 1,000 requests on each model. When an API key is available it uses the real count_tokens; otherwise it falls back to the four-characters estimate and says so. You will reuse this meter whenever you write a system prompt.

pixi init costmeter
cd costmeter
pixi add python=3.14 structlog anthropic
# write costmeter.py, then:
pixi run python costmeter.py prompt.txt --output-tokens 400

What to write (type hints and a Google-style docstring on each function):

  • estimate_tokens(text: str) -> int: ceil(len(text) / 4), the same rule as agentlab.
  • count_tokens(text: str) -> tuple[int, str]: try the real anthropic.Anthropic().messages.count_tokens(model="claude-opus-5-5", messages=[...]) and return (count, "exact"); on anthropic.AuthenticationError or anthropic.APIConnectionError, log the fallback and return (estimate, "estimate").
  • cost_usd(input_tokens: int, output_tokens: int, model: str) -> float with the published prices, raising ValueError for an unknown model.
  • main() -> None: parse arguments with argparse (file path, --output-tokens, --calls defaulting to 1,000), and print a small table, one row per model.

Log events (the fallback, the file size, the token source) with structlog as key-value pairs, and keep print for the table the user asked for. Logs are for operators and log aggregators; the table is the program's output. Separating them is a habit worth forming now.

  • The project is its own Pixi workspace; dependencies were added with pixi add
  • It runs with pixi run python costmeter.py prompt.txt and prints one row per model
  • Costs match the published prices: Opus $4/$20, Sonnet $2/$10, Haiku $0.10/$0.50 per million tokens
  • Each row shows input cost, expected output cost, and the total for --calls requests
  • The context-window share is computed against 1,000,000 tokens
  • With no API key it still works, labels counts as estimates, and logs why with structlog
  • No API key appears anywhere in the code or the repository

Stretch goals: accept --system and --tools tools.json and count them too; compare the estimate with the exact count for prose, code, and JSON samples and note the ratio for each; add a --budget flag that exits with a non-zero status when the cost per 1,000 calls exceeds it, so it can run in CI.

Quiz

Recap

  • A model generates one token at a time: predict a distribution, pick a token, append, repeat until end of turn or max_tokens.
  • A token is about four characters of English; code, JSON, numbers, and other languages usually cost more. al.estimate_tokens estimates; count_tokens measures.
  • The context window is 1M tokens and holds system, tools, all messages, and this turn's output (up to 128K).
  • The API is stateless: history is re-sent each request, so input grows every turn.
  • response.usage reports input_tokens and output_tokens, the numbers you are billed for.
  • Output varies because tokens are sampled. temperature, top_p, top_k are rejected; steer with prompts, effort, and schemas, and test code with scripted responses.
  • Prices per MTok: Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 5.5 $0.10/$0.50. Output costs 5× input; agents are usually input-dominated.
  • Latency is driven mainly by output tokens, then input size, effort, model size, and the number of round trips.
