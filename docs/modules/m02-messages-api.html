The Messages API

Every agent in this course, from a two-line script to a multi-agent system, is built on one endpoint: you send a list of messages, the model sends back one more. This module takes that request and response apart field by field, shows why the API remembers nothing between calls, and ends with a small chat wrapper that owns the conversation history. Every loop you write later builds on that wrapper.

⏱ ~2 hoursPrerequisites: M01 What an LLM Call Is

Anatomy of a request

The Messages API is the HTTP endpoint you use to talk to Claude. A request is one call to it: you send some JSON, the model generates a reply, and the API sends the reply back as a response. The official Python package, anthropic, wraps that HTTP call in a method, client.messages.create(...), whose keyword arguments are the fields of the request.

Three fields are required on every request:

  • model: which model answers, as a model id string. This course uses "claude-opus-5-5", available in lesson code as al.MODEL. Use the id exactly as written; model ids do not take date suffixes.
  • max_tokens: the most tokens the model may generate in this reply. It is a ceiling, not a target. If the model reaches it, the reply is cut off. You met tokens in M01; M03 covers what happens at the limit and how to detect it.
  • messages: the conversation so far, as a list of dicts. Each dict has a role ("user" or "assistant") and some content.

Here is the smallest useful request against the course's mock model. al.MockClient has the same messages.create method as the real client, but answers from a script you give it, so it runs in the browser with no network and no API key. The script below has one step, so the client can answer exactly one request.

The same request against the real API differs in exactly one line: you build the client from the anthropic package instead of the mock. The client reads your key from the ANTHROPIC_API_KEY environment variable; it never appears in code.

import anthropic

client = anthropic.Anthropic()   # the only change from the mock

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=256,
    messages=[{"role": "user", "content": "What is the capital of France?"}],
)
print(response.content[0].text)

Under the hood the SDK sends this JSON body in an HTTP POST. Seeing it once makes clear that there is nothing magic in the client: it is a typed wrapper around a JSON document.

{
  "model": "claude-opus-5-5",
  "max_tokens": 256,
  "messages": [
    {"role": "user", "content": "What is the capital of France?"}
  ]
}

Leave out a required field and the call fails before anything is sent. The SDK raises TypeError for a missing keyword argument, and the mock does the same:

Why must you choose max_tokens yourself? Output tokens cost money and time (M01), and only you know how long a useful answer can be. A classifier that answers one word needs a few tokens; a report generator needs thousands. The current models can produce up to 128K output tokens in one reply, and very large values need streaming (M04).

Remember: a request is model + max_tokens + messages, plus optional fields. The SDK method's keyword arguments are the JSON fields. The mock and the real client share the same method, so code written against one runs against the other.

Roles and turns

Each message has a role saying who produced it. There are two:

  • user: input from your side: what a person typed, a document you want summarized, and later in the course the results of tools your code ran.
  • assistant: output from the model: replies it gave on earlier calls.

A turn is one message from one role. A conversation is a sequence of turns, normally alternating user, assistant, user, assistant, and always ending with the user turn you want answered. The model reads the whole list and writes the next assistant turn.

messages = [
    {"role": "user", "content": "Suggest a name for a black cat."},
    {"role": "assistant", "content": "How about Ink?"},
    {"role": "user", "content": "Something longer, please."},   # the turn to answer
]

The API enforces a few rules about this list. Breaking one gets you a 400 Bad Request error, which the SDK raises as anthropic.BadRequestError. The mock raises al.BadRequestError with the same kind of message, so you can see each rule fail safely.

Rule 1: the first message is a user message

A conversation starts with input. Chat interfaces often show a greeting such as "Hi! How can I help?" before the person types anything. If you store that greeting in your history as the first message, the next request fails:

The message names the exact field: messages.0.role, that is, the role of the message at index 0. Error messages from the API use this dotted path style; read them literally. The fix is to keep display-only text, such as a greeting, out of the history you send. If the model should know about the greeting, describe it in the system prompt (next sections).

Rule 2: text content must not be empty

A message with an empty string (or only whitespace) is rejected. This usually happens when a person presses Enter on an empty input box and your code appends it without checking:

Validate input before it reaches the history: if not text.strip(): .... Rejecting it at the edge of your program gives a friendlier message than a 400 from the API, and it never pollutes the stored conversation.

Rule 3: the last message is the one to answer

On current models, the list must not end with an assistant message. Ending with a partial assistant reply used to be a technique called prefill, and it is now rejected. M03 explains what to use instead. In normal chat code this rule takes care of itself: you always append the new user turn before calling.

Consecutive messages with the same role

Strict alternation is the normal shape, but it is not an error to send two user messages in a row. The API merges consecutive messages with the same role into a single turn. That is convenient (you can add a reminder as a separate message), but it can surprise you when a bug duplicates a message: the model sees one turn containing both texts, and nothing fails.

client.requests is a mock-only list of every request the client accepted, in order. Each entry is an al.Request whose .messages holds the history exactly as it was sent. You will use it constantly in exercises to check that your code sent what you meant to send.

Remember: two roles, user and assistant. Start with user, end with the user turn to answer, never send empty text. A BadRequestError (400) means the request itself is wrong: read the field path in the message, fix the code, and do not retry the same request.

Content: a string or a list of blocks

So far every content has been a plain string. That is a shorthand. The general form of content is a list of content blocks, where each block is a dict with a type field. A text block looks like {"type": "text", "text": "..."}. These two messages mean the same thing to the API:

{"role": "user", "content": "Summarize this."}

{"role": "user", "content": [{"type": "text", "text": "Summarize this."}]}

Why have blocks at all? Because a turn can hold more than one thing, and not everything is text. A user turn can carry several pieces of text (an instruction and a document, kept separate), and other block types carry images and, from M08 on, the results of tools your code ran. An assistant turn can hold text followed by a request to call a tool. The block list is how the API keeps those parts separate and in order.

When should you use which form? Use a string when a turn is a single piece of text you wrote: it is shorter and easier to read. Use blocks when a turn has several parts, when a part is not text, or when you are sending back blocks the model produced. That last case matters most, and the section on history returns to it.

Each text block must be non-empty, just like string content. A list that contains {"type": "text", "text": ""} is rejected with a path such as messages.0.content.1, pointing at the block at index 1. An empty list is rejected too.

Remember: string content is shorthand for one text block. Blocks let a turn hold several parts of different types, in order. Every block has a type.

The system prompt

A system prompt is text that sets the model's role, rules, and context for the whole conversation: "You are a support assistant for Acme's billing product. Answer in two sentences or fewer." It is not a turn in the conversation; it frames all of them. In the Messages API it is a separate top-level field, system, next to messages, not a message with a special role.

A common mistake, especially for people who have used other chat APIs, is to put the system prompt in the message list as {"role": "system", ...}. The system prompt belongs in the top-level system field, and a conversation must start with a user turn, so a leading system message fails:

The system prompt can be a string or a list of text blocks, the same two shapes as message content. You send it on every request, because, as the next sections show, the API keeps nothing between calls. What makes a good system prompt is the subject of M06; here the point is only where it goes.

The system prompt is part of the input on every request, so it costs input tokens every time (M01). A 2,000-token system prompt in a 30-turn chat is read 30 times. What does that suggest about how long a system prompt should be?

Remember: the system prompt goes in the top-level system field, never in messages. Send it with every request.

The response object

messages.create returns a Message object: the model's new turn plus some metadata. Its fields, all of which you will use in this course:

FieldWhat it holdsWhy you care
idA unique id for this response, such as msg_...Log it; it identifies the call when you debug or report a problem.
type, roleAlways "message" and "assistant"Confirms this is the model's turn.
modelThe model that answeredLog it alongside the id.
contentA list of content blocks, in orderThe answer itself: text blocks, and in Stage 2 tool requests.
stop_reasonWhy generation stopped, such as "end_turn" or "max_tokens"Tells you whether the answer is complete and what to do next. Check it before reading content.
stop_sequenceThe stop sequence that ended the reply, or NoneCovered in M03.
usageinput_tokens, output_tokens (and cache counters)What the call cost, and how full the context is getting.

The response's content is always a list of blocks, even when the request used a string. That is why the first example read response.content[0].text: the text of the first block.

Reading the text safely

response.content[0].text is fine for a quick experiment, but it makes two assumptions that break in real programs: that there is at least one block, and that the first block is text. A reply can start with a text block and continue with a tool request; a refused request (M03) can come back with no blocks at all. The robust way is to look at each block's type and join the text blocks:

def text_of(response):
    """Join the text of every text block; return "" if there are none."""
    return "".join(block.text for block in response.content if block.type == "text")

Do not worry about tools yet; M07 and M08 cover them. The point here is the shape: content is a list, blocks have types, and code that assumes "one text block" breaks as soon as anything else appears.

agentlab's Message has a .text property that joins the text blocks for you. The real SDK's Message does not have it. Use it for quick printing in lesson cells, but write text_of(response) (or the equivalent loop) in code you intend to run against the real API. The exercises check that you do.

Remember: a response is a Message with id, content (a list of typed blocks), stop_reason, and usage. Read text by filtering on block.type == "text", never by assuming content[0] exists.

The API is stateless

Chat products make it look as if the model remembers you. The API does not. It is stateless: each request is processed on its own, using only what that request contains. Nothing from the previous call is kept on the server for the next one. If you want the model to "remember" the earlier conversation, you send the earlier conversation again, every time.

The cell below makes that concrete. The mock is given a responder, a Python function that receives each request and returns a reply, instead of a fixed script. This responder behaves the way the real model must: it can only know your name if your name appears somewhere in the request it is handed.

The second call fails to recall the name because its messages list contains only "What is my name?". A real model behaves the same way, for the same reason. Statelessness sounds like a limitation, but it is what makes the API simple to reason about and to build on:

  • You control the context completely. The model sees exactly the list you send. You can edit it, trim it, summarize old turns, or inject information, and there is no hidden server state to get out of sync.
  • Any request can be replayed. Save the request and you can resend it to reproduce a problem, or send it to a different model to compare.
  • Agents are just loops over a list. In M09 the agent loop is nothing more than "append to the list, call again" until the model is done.

The cost is that history grows. Every turn you keep is re-sent, and re-billed as input tokens, on every later request. Long conversations get slower and more expensive per turn, and eventually approach the context window (1M tokens on current models). M11 shows how agents budget for this.

Remember: the API remembers nothing. The model's entire world on each call is system + messages (+ tools). Memory is the list you send.

History is a list you own

Since the API keeps no state, your program does. The pattern is short, and every chat program and every agent in this course uses it:

  1. Append the new user turn to your list.
  2. Send the whole list.
  3. Append the model's reply as an assistant turn whose content is response.content.
  4. Repeat.
sequenceDiagram
    participant C as Your code (owns messages)
    participant A as Messages API
    Note over C: messages = [user 1]
    C->>A: create(messages=[user 1])
    A-->>C: response 1
    Note over C: append assistant 1, then user 2
    C->>A: create(messages=[user 1, assistant 1, user 2])
    A-->>C: response 2
    Note over C: append assistant 2, then user 3
    C->>A: create(messages=[user 1, assistant 1, user 2, assistant 2, user 3])
    A-->>C: response 3

Each request is longer than the last, and every request is complete on its own. Here is the pattern with the honest responder from the previous section. This time the name is remembered, because it is in the list.

al.format_transcript(messages) prints one line per block, which is the quickest way to see what a conversation actually contains. Use it whenever a multi-turn program does something you did not expect. Notice also that input_tokens grows every turn: that is the whole history being re-read.

Two properties of al.Request appeared in the responder: request.last_user_text (the text of the most recent user turn) and request.turn (how many assistant turns the history already holds). They are mock-only helpers for writing responders and tests; the agentlab reference lists them all.

Append response.content, not the text

Step 3 is where most bugs live. It is tempting to store only the reply's text:

messages.append({"role": "assistant", "content": text_of(response)})   # loses information

For a plain chat that happens to work, which is why the habit forms. But it throws away every non-text block. In Stage 2 the model's reply will contain tool_use blocks, and the API requires each one to appear in the history so that your tool_result can answer it. Drop them and the next request is rejected. Appending response.content keeps every block, exactly as the model produced it. The SDK accepts its own block objects back in messages, so there is nothing to convert.

The text-only version has silently lost the tool request. You will see exactly which error that causes in M08.

Appending the response object itself (messages.append(response)) is wrong: a history entry is a dict with role and content. Forgetting to append the reply at all makes the next request contain two user turns in a row. As you saw, that is merged rather than rejected, so nothing fails; the model simply never sees its own earlier answer, and the conversation feels forgetful. al.format_transcript makes both mistakes obvious.

Remember: append user turn, send the full list, append {"role": "assistant", "content": response.content}. The list is your program's memory; keep it valid and complete.

A minimal chat wrapper

Every program that talks to the model more than once ends up repeating the same few lines: append, call, append, extract text. Wrapping them in a small class keeps the rules in one place. A good wrapper has one more responsibility that is easy to miss: the history must stay valid no matter what happens. If the API call fails after you appended the user turn, that turn is now in the list with no reply. The next send would add a second user turn, and the model would see both questions merged into one. The fix is to roll back: remove the user turn if the call does not succeed.

Walk through what the wrapper guarantees:

  • Empty input never reaches the API. It raises ValueError at the edge, before the history is touched.
  • A failed call leaves no trace. al.fail(al.RateLimitError()) is a script step that makes that request raise the same error a real 429 would. The wrapper pops the user turn and re-raises, so the caller decides what to do (here: retry). The history after the failure is exactly what it was before. M10 covers which errors deserve a retry.
  • Anything other than a complete answer is refused for now. A reply cut off at max_tokens, a refusal, or a tool request each need their own handling, which is M03's subject. Raising is better than silently storing a half-answer.
  • The assistant turn keeps every block, and the system prompt is sent on every call.

The except Exception: ...; raise pattern catches everything only to undo a change, then re-raises the same exception. It does not swallow errors. That is different from except Exception: pass, which hides failures and is never acceptable.

Notice that the wrapper takes the client as a parameter instead of creating one. This is dependency injection: tests hand it a MockClient, production hands it anthropic.Anthropic(), and the class never knows the difference. Every exercise in this course relies on it, and so will your own test suites.

Remember: a chat wrapper owns the list, validates input, sends the system prompt every time, appends response.content, and rolls back the user turn when a call fails.

Reading request errors

You have now seen most of the ways a request can be malformed. They share one property: the request is wrong, so sending it again will fail again. Fix the code (or the data) instead of retrying. Here they are in one place, each with the exception your code receives:

MistakeExceptionFix
Missing model or max_tokensTypeError (raised before sending)Pass both on every call.
First message is not userBadRequestError (400)Keep greetings and other display text out of the history.
Empty or whitespace-only textBadRequestError (400)Validate input before appending it.
{"role": "system"} as the first messageBadRequestError (400)Use the top-level system field.
History ends with an assistant turnBadRequestError (400)Append the user turn before calling; see M03.
Unknown model idNotFoundError (404)Use an exact id such as claude-opus-5-5.

import agentlab as al

def run_chat(client, turns):
    messages = []
    for text in turns:
        messages.append({"role": "user", "content": text})
        response = client.messages.create(model=al.MODEL, max_tokens=256, messages=messages)

Write clean_history(saved) that returns a new list (do not modify saved) with every message whose content is a string that is empty or only whitespace removed, and then every leading assistant message removed, so the result starts with a user turn. Keep all other messages, in order. Then write resume(client, saved, text) that cleans the history, appends text as a user turn, sends it (model=al.MODEL, max_tokens=256), and returns the reply text.

Hint

Build the list with a comprehension that keeps a message unless its content is a string whose .strip() is empty. Then drop items from the front while the first one has role "assistant". In resume, the cleaned list is already a new list, so appending to it does not touch saved.

Show solution 
import agentlab as al

def clean_history(saved):
    kept = [m for m in saved if not (isinstance(m["content"], str) and not m["content"].strip())]
    while kept and kept[0]["role"] == "assistant":
        kept.pop(0)
    return kept

def resume(client, saved, text):
    messages = clean_history(saved)
    messages.append({"role": "user", "content": text})
    response = client.messages.create(model=al.MODEL, max_tokens=256, messages=messages)
    return "".join(block.text for block in response.content if block.type == "text")

Write a class Conversation with:

  • __init__(self, client, system=None, max_tokens=1024), storing an empty self.messages list.
  • send(self, text): raise ValueError without calling the API if text is empty or whitespace. Otherwise append the user turn, call messages.create with model=al.MODEL, the stored max_tokens, the full history, and system only when it is not None. On success, append {"role": "assistant", "content": response.content} and return the joined reply text. If the call raises, remove the user turn and re-raise the same exception.
  • reset(self): clear the history.
Hint

Build the keyword arguments in a dict and add "system" only when it is set. Wrap the create call in try/except Exception:, and in the handler call self.messages.pop() and then a bare raise.

Show solution 
import agentlab as al

class Conversation:
    def __init__(self, client, system=None, max_tokens=1024):
        self.client = client
        self.system = system
        self.max_tokens = max_tokens
        self.messages = []

    def send(self, text):
        if not text.strip():
            raise ValueError("message is empty")
        self.messages.append({"role": "user", "content": text})
        kwargs = {"model": al.MODEL, "max_tokens": self.max_tokens, "messages": self.messages}
        if self.system is not None:
            kwargs["system"] = self.system
        try:
            response = self.client.messages.create(**kwargs)
        except Exception:
            self.messages.pop()
            raise
        self.messages.append({"role": "assistant", "content": response.content})
        return "".join(block.text for block in response.content if block.type == "text")

    def reset(self):
        self.messages = []

import os
import agentlab as al

def make_client():

Spec

  • A loop reads a line with input("you> "), sends it, and prints the reply. Empty lines are ignored without calling the API.
  • Commands: /reset clears the history, /history prints al.format_transcript(chat.messages), /save FILE writes the history as JSON, /load FILE reads it back, /quit exits.
  • A --system command-line option (use argparse) sets the system prompt.
  • Saving converts each content block to a plain dict with al.as_dict(block), since SDK block objects are not JSON-serializable. Loading validates the file: the first message is user, roles are only user/assistant, and no text is empty.
  • After each reply, log one structured event with structlog: the response id, stop_reason, input_tokens, and output_tokens. Structured logs (key=value or JSON) can be searched and summed later; plain prints cannot. Keep print for the chat text the person reads.
  • API errors print a short message and leave the history unchanged (your rollback does this).
  • The program runs against the mock with no API key set
  • With a key set, it holds a real multi-turn conversation that remembers earlier turns
  • Every request sends model, max_tokens, the full history, and the system prompt when given
  • Assistant turns are stored as response.content, never as plain text
  • Empty input never reaches the API
  • /save then /load restores a conversation that can be continued without a BadRequestError
  • Loading a file whose first message is an assistant greeting is rejected with a clear message
  • Each reply logs id, stop_reason, and token counts as one structlog event
  • No API key appears anywhere in the code or the saved files

Quiz

Recap

  • A request is model + max_tokens + messages, plus optional fields such as system. The SDK's keyword arguments are the JSON fields.
  • Conversations are built from user and assistant turns, with the system prompt in its own system field. The first message is user, the last is the user turn to answer, and consecutive same-role messages are merged.
  • Content is a string (shorthand for one text block) or a list of typed blocks. Text must never be empty.
  • The system prompt goes in the top-level system field, on every request.
  • The response is a Message: id, content (a list of blocks), stop_reason, usage. Read text by filtering blocks on type.
  • The API is stateless. History is a list you own: append the user turn, send everything, append response.content as the assistant turn.
  • A chat wrapper validates input, sends the system prompt, keeps every block, and rolls back on failure.
  • TypeError, 400 and 404 mean the request is wrong: fix it, do not retry it.
